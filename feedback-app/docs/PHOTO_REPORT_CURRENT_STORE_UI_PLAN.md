# План реализации: «Зараз працюю в магазині» в Фото звіті

## 1. Цель

Сделать выбор магазина для фотоотчёта понятным без обучения продавца.

Обычный сценарий:

1. Продавец входит под своим PIN.
2. Приложение уже знает его **основной магазин** из карточки сотрудника.
3. В «Фото звіті» крупно и однозначно показано: **«Зараз працюю в магазині: Шкільна»**.
4. Если продавец сегодня на замене, он открывает отдельный нижний блок **«Працюю на заміні?»**, выбирает разрешённый магазин и только тогда текущим магазином становится, например, **«Роша»**.
5. Отчёт сохраняется за тем магазином, который показан в верхнем блоке в момент отправки. Сервер повторно проверяет это право.

Цель не меняет основной магазин сотрудника, его PIN, права на другие категории заявок или график смен.

## 2. Зафиксированные продуктовые правила

| Правило | Решение |
|---|---|
| Основной сценарий | Основной магазин выбирается автоматически при загрузке формы. Продавец не обязан открывать список. |
| Что считается текущим магазином | Верхний блок всегда показывает именно магазин, за который будет отправлен текущий фотоотчёт. |
| Замена | В нижнем блоке показываются только активные разрешения `seller_store_permissions`, с суффиксом `— заміна`. |
| Возврат | Если выбрана замена, доступна явная кнопка «Повернутися до основного магазину». |
| Новый вход / новая форма | Выбор замены не сохраняется как новый основной магазин. При новом открытии форма снова начинает с основного магазина. |
| Серверная истина | Браузер передаёт `store_id`, но API заново разрешает только основной магазин или активную замену текущего продавца. |
| Отсутствие основного магазина | Автоматически ничего не выбирается. Форма просит выбрать разрешённый магазин для замены; отправка без выбора невозможна. |
| Нет доступных магазинов | Показывается понятная ошибка «Для вас не призначено магазин для фото звіту. Зверніться до адміністратора.»; отправка блокируется. |
| Терминология | «Магазини для заміни» дают право на фотоотчёт. Они не подтверждают реальную смену и не являются табелем. |

## 5. Целевой контракт API

Текущий маршрут `GET /api/auth/photo-report-stores` должен вернуть структурированный ответ вместо того, чтобы заставлять UI угадывать порядок массива:

```ts
type PhotoReportStoresResponse = {
  home_store: { id: number; name: string } | null;
  replacement_stores: Array<{ id: number; name: string }>;
};
```

Правила контракта:

1. `home_store` берётся только из актуальной `users.store_id` текущего активного продавца.
2. `replacement_stores` содержат только активные записи разрешений текущего продавца.
3. Если основной магазин также есть среди разрешений, он не дублируется в `replacement_stores`.
4. Список замен сортируется стабильно по названию магазина, чтобы UI и тесты не зависели от порядка БД.
5. Маршрут не возвращает PIN, PIN-хеш, чужих пользователей, чужие разрешения или весь список сети.
6. При невалидной/неактивной сессии ответ не должен раскрывать магазины.

## 6. Целевая логика формы

1. После загрузки `home_store` становится `currentStore` по умолчанию.
2. `replacementStoreId` по умолчанию равен `null`; это означает «не на замене».
3. После выбора замены `currentStore` становится выбранным магазином и верхняя карточка немедленно обновляется.
4. При нажатии «Повернутися до основного магазину» `replacementStoreId` очищается, `currentStore` возвращается к `home_store`.
5. В JSON отправляется `currentStore.id`, а не имя магазина и не состояние старого hidden-поля.
6. При обновлении вкладки форма заново получает данные, выбор замены сбрасывается, основной магазин снова становится текущим.
7. Для продавца без основного магазина, но с заменами, верхняя карточка до выбора нейтральна: «Оберіть магазин, де працюєте зараз»; список замен доступен.
8. Для продавца без любых разрешений upload и submit disabled. Текст объясняет, что нужно обратиться к администратору.
9. Во время загрузки данных показывается skeleton, а не кратковременно неправильный магазин или пустой select.

## 7. Пошаговое выполнение с обязательными воротами

Переход к следующему шагу запрещён, пока проверка предыдущего не пройдена и не зафиксирована в рабочем отчёте.

### Шаг U-01. Зафиксировать исходное состояние

**Действия**

1. Зафиксировать SHA ветки, версию приложения и текущий контракт маршрута.
2. Read-only проверить текущую структуру `seller_store_permissions` и наличие активного тестового продавца с основным магазином и хотя бы одной заменой.
3. Зафиксировать, что действующий API отправки всё ещё повторно авторизует магазин на сервере.

**Проверка / готово, когда**

- В отчёте есть SHA, пути файлов и вывод read-only запросов.
- Нет изменений в базе данных и Production.

### Шаг U-02. Написать тесты контракта API до изменения UI

**Действия**

1. Добавить route-тесты для нового явного ответа `home_store` / `replacement_stores`.
2. Зафиксировать негативные сценарии до начала рефакторинга.

**Ворота**

- Новые тесты сначала должны падать по ожидаемой причине: новый контракт ещё не реализован.
- Существующие тесты приложения проходят без регрессий.

### Шаг U-03. Реализовать и проверить read-маршрут

**Действия**

1. Обновить только `photo-report-stores/route.ts`.
2. Отделить основной магазин от замен, удалить дубликат, обеспечить стабильную сортировку.
3. Не добавлять никаких прямых browser-доступов к Supabase и не ослаблять RLS.

**Ворота**

- Все контрактные тесты U-02 проходят.
- Проверка показывает, что маршрут возвращает только данные сессии текущего продавца.

### Шаг U-04. Выделить локальное состояние текущего магазина

**Действия**

1. В `FeedbackForm` разделить `homeStore`, `replacementStores`, `replacementStoreId` и вычисляемый `currentStore`.
2. При наличии `homeStore` устанавливать его сразу после успешной загрузки.
3. Не использовать «первый элемент массива» как default.

**Ворота**

- Unit-тест доказывает, что домашний магазин выбран даже если он не первый в данных.
- TypeScript проходит без ошибок.

### Шаг U-05. Реализовать верхнюю карточку текущего магазина

**Действия**

1. Добавить компактную, хорошо читаемую карточку с текстом «Зараз працюю в магазині».
2. Отображать название, объяснение атрибуции и badge `Заміна` только при выбранной замене.
3. Не показывать «Роша» в карточке, пока пользователь не выбрал её.

**Ворота**

- Визуальный тест и ручная проверка подтверждают состояния A и C из раздела 3.
- Карточка доступна с клавиатуры и имеет достаточный цветовой контраст.

### Шаг U-06. Реализовать отдельный блок замен

**Действия**

1. Под верхней карточкой добавить блок «Працюю на заміні?».
2. Селект содержит только `replacement_stores`, каждый с суффиксом `— заміна`.
3. После выбора показать «Повернутися до основного магазину».
4. При reset вернуть домашний магазин без перезагрузки и без сетевого запроса.

**Ворота**

- Визуально проверены состояния A, B и C.
- Основной магазин не появляется в списке замен и не дублируется.

### Шаг U-07. Связать выбранный магазин с отправкой

**Действия**

1. Отправлять в payload только `currentStore.id`.
2. Заблокировать submit, если текущий магазин не определён.
3. Сохранить все действующие ограничения: 1–15 фото, серверную авторизацию, rollback частичной загрузки и логирование.

**Ворота**

- Интеграционный тест сравнивает видимый магазин в карточке с `store_id` в запросе.
- Негативный server-side тест доказывает, что подмена `store_id` браузером остаётся отклонённой.

### Шаг U-08. Обработать крайние состояния

## 10. Логирование и наблюдаемость

Существующие события фотоотчёта сохраняются. Для нового UI не нужно логировать лишние персональные данные. Разрешены только технические события без PIN и без фото:

| Событие | Поля |
|---|---|
| `photo_report.store_context_loaded` | `has_home_store`, `replacement_store_count`, `request_id` |
| `photo_report.replacement_selected` | `store_id`, `request_id` |
| `photo_report.replacement_cleared` | `home_store_id`, `request_id` |
| `photo_report.store_unavailable` | причина: `no_access`, `revoked`, `inactive`, `request_id` |

Перед добавлением этих событий нужно проверить существующую схему логирования. Нельзя писать полное имя продавца, PIN/PIN-хеш, base64-фото, Telegram init data или несанкционированный `store_id` в клиентские логи.

## 11. Критерии приёмки

Функция принимается только если одновременно выполнено всё ниже:

1. Основной магазин активного продавца по умолчанию крупно показан как текущий магазин.
2. Выбор замены расположен отдельным нижним блоком и содержит только разрешённые магазины с меткой `— заміна`.
3. После выбора замены верхняя карточка и отправляемый `store_id` совпадают.
4. Возврат к основному магазину очевиден и работает без перезагрузки.
5. Сервер отклоняет неразрешённый, отозванный и устаревший `store_id`.
6. Пройдены все T-01…T-25; отсутствующий staging/device-доступ оформлен как `blocked`, не как «пройдено».
7. Нет миграции, ослабления RLS, прямого browser-доступа к таблицам разрешений или регрессии лимита 1–15 фото.
8. Production-деплой приложения имеет статус `Ready` и прошёл smoke-check.
