# План реализации: минимум 6 фото для «Фото звіт»

## 1. Цель и результат

Для категории `photo_report` продавец должен иметь возможность отправить один отчёт только при наличии **от 6 до 15 фотографий включительно**.

После изменения:

- 0–5 фото — отчёт не отправляется;
- 6–15 фото — отчёт может быть отправлен при выполнении остальных действующих условий (авторизованный продавец, доступный фактический магазин, валидные изображения);
- 16 и более фото — по-прежнему не допускаются;
- ограничение нельзя обойти прямым запросом к `POST /api/feedback`.

## 2. Границы задачи

### Входит в задачу

1. Клиентская подсказка и блокировка отправки в `feedback-app/src/components/FeedbackForm.tsx`.
2. Явный минимум в API-валидации `feedback-app/src/lib/feedbackValidation.ts`.
3. При необходимости — отображение минимума в `feedback-app/src/components/PhotoInput.tsx`, но без изменения компрессии, очереди обработки и лимита 15.
4. Unit-, route- и E2E-проверки приложения продавцов.
5. Обновление существующих тестов, где за успешный фотоотчёт принимается 1–5 фото.

### Не входит в задачу

- миграции Supabase, RLS, Storage, таблицы аналитики и админ-панель;
- изменение авторизации PIN, основного магазина или магазинов для замены;
- изменение лимита, сжатия или формата фото;
- изменение исторических отчётов: уже сохранённые отчёты с 1–5 фото остаются неизменными;
- отправка тестовых отчётов в production.

## 3. Зафиксированный контракт

| Параметр | Значение |
|---|---:|
| Категория | `photo_report` |
| Минимум | 6 фото |
| Максимум | 15 фото |
| Клиентское сообщение при 0–5 | `Додайте ще N фото. Мінімум — 6.` |
| API-ответ при 0–5 | HTTP 400 с локализованной понятной ошибкой без загрузки в Storage |
| Остальные категории | Не меняются; сохраняют свои текущие правила |
| Источник истины | Серверная `validateFeedbackPayload`, а не кнопка интерфейса |

`N = 6 - текущее количество фото`. Для нуля пользователь видит «Додайте ще 6 фото. Мінімум — 6.».

## 4. Проектное решение

1. В `feedbackValidation.ts` объявить именованную константу `PHOTO_REPORT_MIN_PHOTOS = 6` рядом с существующей `PHOTO_REPORT_MAX_PHOTOS = 15`.
2. Заменить проверку `rawPhotos.length === 0` на `rawPhotos.length < PHOTO_REPORT_MIN_PHOTOS` только для `photo_report`.
3. В `FeedbackForm.tsx` вычислять `missingPhotoReportPhotos = max(0, 6 - photos.length)`.
4. Пока минимум не достигнут:
   - оставить пользователю возможность добавлять и удалять фото;
   - показать счётчик и подсказку с оставшимся количеством;
   - сделать CTA «Надіслати» неактивной;
   - сохранить проверку в `handleSubmit` как защиту от устаревшего UI, ручного submit и будущих рефакторингов.
5. В `PhotoInput.tsx` не дублировать бизнес-валидацию. Допустимо передать только текстовый `hint`/`minPhotos` для единого отображения `Мінімум 6 · максимум 15`, если это не усложняет API компонента. Решение об окончательном варианте принять после просмотра текущих component-тестов.
6. Серверная проверка должна выполняться до обращения к Supabase Storage. Для 0–5 фото не должно быть upload, insert, записи аудита «completed» или осиротевших объектов.
7. Логи не должны содержать data URL, изображение, PIN, cookie или `init_data`. Допускаются `photo_count`, `min_photo_count`, `request_id`, `category` и код отказа.

## 5. Пошаговая реализация с обязательными воротами

Следующий шаг начинается только если пройден критерий предыдущего.

### Шаг 0. Зафиксировать исходное состояние

**Действия**

1. Проверить чистоту рабочей директории и текущую ветку.
2. Найти все проверки `photo_report`, лимита 15 и сообщения «хоча б одне фото».
3. Запустить текущие `npm.cmd test` и `npm.cmd run typecheck` в `feedback-app` как baseline.

**Критерий перехода:** текущие тесты и typecheck зелёные либо каждая существующая ошибка зафиксирована отдельно и не относится к этой задаче.

**Откат:** нет изменений — откат не требуется.

### Шаг 1. Добавить серверный минимум

**Файл:** `feedback-app/src/lib/feedbackValidation.ts`.

**Действия**

1. Добавить `PHOTO_REPORT_MIN_PHOTOS = 6` рядом с максимумом 15.
2. Отклонять `photo_report`, когда `rawPhotos.length < 6`.
3. Сохранить существующую проверку `rawPhotos.length > 15`.
4. Не менять правила категорий, отличных от `photo_report`.

**Критерий перехода:** чистая функция валидации возвращает 400 для 0–5 и `ok: true` для 6 и 15 валидных фото.

**Откат:** удалить только новую константу и связанную ветку проверки одним обратным коммитом.

### Шаг 2. Закрыть серверный контракт тестами

**Файл:** `feedback-app/src/lib/__tests__/feedback-route.test.ts` и, если потребуется, отдельный test file в `src/lib/__tests__/`.

**Действия**

1. Заменить устаревшее ожидание «at least one photo» на минимум шесть.
2. Добавить параметризованные тесты для границ 0, 1, 5, 6, 15, 16.
3. Проверить, что не-фото категории не приобрели минимум шесть.
4. Проверить POST-ветку: 5 валидных data URL возвращают 400 до любого `storage.upload` и `insert`.
5. Проверить POST-ветку: 6 фото проходит до существующей логики загрузки.

**Критерий перехода:** новые тесты проходят; 5 фото не создают строк и объектов Storage в моках.

**Откат:** удалить только тесты и код шага 1 одним обратным коммитом.

### Шаг 3. Изменить поведение формы

**Файл:** `feedback-app/src/components/FeedbackForm.tsx`.

**Действия**

1. Ввести локальную константу либо импортировать общую `PHOTO_REPORT_MIN_PHOTOS`, не создавая расхождение значения между формой и сервером.
2. Для `photo_report` отобразить под `PhotoInput` видимую подсказку:
   - 0–5: `Додайте ще N фото. Мінімум — 6.`;
   - 6–15: `Мінімум виконано: N/15 фото.`
3. В `handleSubmit` заменить проверку нуля на проверку `< 6`; вернуть ту же локализованную ошибку, что видит пользователь.
4. Отключать CTA при `submitting`, отсутствии разрешённого магазина и при `< 6` фото. Причины не должны скрывать подсказку.
5. Сохранять существующую очистку формы после успешной отправки и выбор магазина/замены.

**Критерий перехода:** в браузере при 5 фото кнопка неактивна и видна причина; после добавления шестого без перезагрузки кнопка активируется; после удаления до 5 снова блокируется.

**Откат:** обратный коммит только UI-изменений; серверный минимум остаётся лишь если задача уже принята как обязательная.

### Шаг 4. Проверить `PhotoInput` и доступность

**Файл:** `feedback-app/src/components/PhotoInput.tsx` (только если нужен UI-текст).

**Действия**

1. Не менять `maxPhotos=15`, `maxOutputBytes=280 KiB`, `maxDimension=1280`, `COMPRESS_CONCURRENCY=2` без отдельного решения.
2. Убедиться, что счётчик `N/15` остаётся корректен после добавления несколькими пакетами, удаления и обработки ошибки сжатия.
3. Проверить, что disabled CTA имеет доступную текстовую причину рядом, а не только цветовую индикацию.
4. Проверить навигацию клавиатурой: add-photo, удаление миниатюры, смена статуса кнопки.

**Критерий перехода:** ни один сценарий не позволяет скрыто отправить 0–5 фото и не ломает добавление до 15.

### Шаг 5. Локальная полная проверка

**Действия**

1. `npm.cmd test`
2. `npm.cmd run typecheck`
3. `npm.cmd run lint`
4. `npm.cmd run build`
5. `git diff --check`
6. Проверить локальную страницу `/feedback/photo_report` под тестовым продавцом без фактической отправки в production.

**Критерий перехода:** все пять команд завершаются с exit code 0, а ручная проверка соответствует контракту.

### Шаг 6. Preview и E2E

**Действия**

1. Создать отдельный commit после локальных зелёных проверок.
2. Отправить только целевую ветку в Preview.
3. Дождаться Vercel `Ready` и проверить HTTP 200 маршрута `/feedback/photo_report`.
4. Провести E2E в Preview с отдельной тестовой учётной записью и staging/изолированной базой.
5. Перед тестовой отправкой снять счётчики строк `photo_report` и объектов Storage; после — сравнить их с ожидаемым изменением.

**Критерий перехода:** Preview `Ready`, E2E прошёл, данные теста изолированы и подтверждены readback.

### Шаг 7. Production-приёмка

**Действия**

1. Не деплоить без явного подтверждения пользователя конкретного commit SHA.
2. После подтверждения продеплоить только `app.feedback.gb`; админ-проект не требует изменения.
3. Дождаться `Ready`, проверить HTTP 200 и выполнить ручный smoke без отправки боевого отчёта.
4. Записать SHA, deployment URL, время, результаты тестов и обнаруженные ограничения в итоговый отчёт.

**Критерий готовности:** production `Ready`; нет регрессии фотоотчёта 6–15; не было тестовых записей/фото в production без отдельного разрешения.

## 7. Readback после E2E

Выполнять только на staging/изолированной тестовой базе. Подставить UUID тестового продавца и дату теста.

```sql
select
  f.id,
  f.created_at,
  f.store_id,
  f.user_id,
  jsonb_array_length(coalesce(f.fields -> 'photo_urls', '[]'::jsonb)) as photo_count
from feedbackgb.feedback f
where f.category = 'photo_report'
  and f.user_id = :test_seller_id
  and f.created_at >= :test_started_at
order by f.created_at desc;
```

Ожидание для T-22/T-23: одна новая строка на одну подтверждённую отправку, `photo_count = 6`, `store_id` соответствует выбранному магазину. Для T-21: строк нет.

Проверка объектов Storage должна выполняться тем же service-role инструментом, который используется в действующих тестах. Нельзя подменять её успешным HTTP-ответом интерфейса.

## 8. Логирование и наблюдаемость

Добавить или уточнить только структурированные серверные события:

| Событие | Когда | Поля |
|---|---|---|
| `photo_report.rejected_min_photo_count` | 0–5 фото | `photo_count`, `min_photo_count: 6`, `request_id` |
| `photo_report.received` | 6–15 фото | существующие безопасные поля, `photo_count` |
| `photo_report.completed` | запись и все фото сохранены | существующие безопасные поля, `photo_count` |

Запрещено логировать data URL, binary, signed URLs, PIN, cookie, Telegram `init_data` или полный IP.

## 9. Риски и решения

| Риск | Мера |
|---|---|
| Блокировка существует только в UI | Серверная проверка и route-тесты до Storage |
| Разные значения «6» в форме и API | Одна импортируемая константа либо единый модуль констант |
| Пользователь не понимает, почему CTA заблокирован | Текст с точным числом недостающих фото рядом с CTA/PhotoInput |
| Регрессия лимита 15 или компрессии | Граничные тесты 15/16 и сохранение параметров `PhotoInput` |
| Тестовые фото попадают в production | E2E только Preview + staging/изолированная БД; production smoke без submit |
| Частичный upload при 6–15 | Не менять существующие all-or-nothing cleanup-тесты |

## 10. Definition of Done

Задача завершена только когда выполнено всё:

1. `photo_report` принимает исключительно 6–15 фото на сервере.
2. Интерфейс не позволяет отправить 0–5 и объясняет, сколько ещё добавить.
3. Прямой POST с 0–5 не создаёт ни Storage-объектов, ни записи `feedback`.
4. Все T-01…T-26 имеют статус `passed` либо явно `blocked` с причиной и доказательством; ни один критичный тест не `failed`.
5. `test`, `typecheck`, `lint`, `build`, `git diff --check` прошли.
6. Preview прошёл E2E и readback на изолированных данных.
7. Production-деплой выполнен только после отдельного подтверждения SHA; админка не затронута.
