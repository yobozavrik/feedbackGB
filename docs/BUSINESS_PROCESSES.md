# FeedbackGB — бизнес-процессы и правила данных

## 1. Отправка обращения продавцом

1. Продавец входит по PIN.
2. Выбирает категорию и заполняет форму.
3. Клиент выполняет первичную проверку, сервер — обязательную повторную проверку.
4. Сервер сохраняет фото в private Storage (если категория содержит фото), затем создаёт строку `feedback`.
5. Триггеры и аудит фиксируют событие; админ видит обращение в своей рабочей очереди.

При слабой сети приложение использует локальную очередь. Повторная отправка идемпотентна по `client_submission_id`; очередь не должна отправлять обращение от имени другого продавца на общем устройстве.

## 2. Обработка обращения администратором

1. Администратор открывает обращение в обзоре или «Мої завдання».
2. Меняет статус, назначает ответственного, при необходимости добавляет комментарий.
3. API валидирует действие, а `audit_log` и триггер на `feedback` фиксируют, кто и что изменил.
4. Продавец видит итог в «Мої зверненнях» и получает предусмотренные уведомления.

## 3. Фото звіт и замена магазина

### 3.1 Настройка доступа

1. Администратор создаёт или редактирует продавца в «Співробітники».
2. Основной магазин может быть задан в карточке сотрудника.
3. В поле «Магазини для заміни» администратор выбирает отдельные магазины либо все сразу.
4. Для каждого выбранного магазина создаётся активная запись `seller_store_permissions`; действие фиксируется в audit log.

### 3.2 Отправка

1. По умолчанию в форме фотозвита указан основной магазин — это самый простой путь для продавца.
2. Если продавец фактически на замене, он выбирает магазин в поле «Працюю на заміні».
3. Он прикладывает 6–15 фото и отправляет отчёт.
4. Сервер проверяет сессию, количество фото и право на выбранный магазин **до** сохранения факта.
5. В `feedback` сохраняется фактический магазин. Триггер создаёт `photo_report_attribution`: продавец, основной магазин, магазин отчёта и источник (`home_store` или `replacement_permission`).
6. Другой триггер обновляет `photo_report_seller_daily`: дата Kyiv, продавец, магазин, число звитов и фотографий.

### 3.3 Что можно и нельзя заключать из данных

| Факт | Что доказывает | Чего не доказывает |
|---|---|---|
| `photo_report_attribution` | кто под каким PIN отправил отчёт и для какого магазина | длительность или полный факт смены |
| `photo_report_seller_daily` | количество звитов/фото этого продавца в этот день и магазине | что в магазине не было других продавцов |
| разрешение на замену | право выбрать магазин для фотозвита | что замена реально состоялась |
| плановая смена | намерение поставить человека в график | фактическое присутствие |

## 4. Планирование графиков магазинов

1. Super admin создаёт период месяца в `work_schedule_periods`.
2. Администратор формирует смены в `store_work_shifts`: продавец, магазин, начало, конец и перерыв.
3. Для смены не в основном магазине API требует активное разрешение замены и сохраняет `is_replacement` с ссылкой на разрешение.
4. База не допускает пересечение активных смен одного продавца через exclusion constraint.
5. Из смен строятся календарная view и месячный агрегат по магазинам `v_store_schedule_store_month`.
6. Период проходит состояния `draft → published → locked → archived`. Lock фиксируется с причиной и автором.

График предназначен для планирования. Зарплата, импорт Google Sheets и табель фактического времени в текущей реализации не рассчитываются.

### 4.1 Контроль фотозвитом

После применения миграции `034_store_schedule_photo_report_control.sql` каждый новый фотозвит будет один раз сопоставляться с плановой сменой того же продавца, магазина и временного интервала. Сопоставление сохраняется неизменно: последующее редактирование графика не перепишет историю. Если подходящей смены нет, запись попадёт в отдельную view не сопоставленных звитов. Это операционный контроль дисциплины, а не табель или расчёт зарплаты.

## 5. Отсутствия

1. Администратор вносит для продавца отпуск, больничный или отгул.
2. Запись получает диапазон дат и привязку к магазину; при пустом магазине триггер подставляет основной магазин сотрудника.
3. База запрещает пересекающиеся активные отсутствия одного продавца.
4. Реестр хранится отдельно от HR-заявок: заявка от продавца — запрос, запись в `employee_absences` — административно зафиксированное отсутствие.

В текущем интерфейсе реализовано добавление и просмотр. Отмена записи предусмотрена схемой (`cancelled`), но отдельное UI/API-действие отмены ещё не реализовано.

## 6. Наблюдаемость и расследование ошибок

| Слой | Что фиксируется | Где смотреть |
|---|---|---|
| Бизнес-действия | создание/изменение сущностей, доступы замен, административные операции | `feedbackgb.audit_log`, вкладка «Журнал дій» |
| Фотозвит | приём, отказ по числу фото, загрузка Storage, очистка, завершение | structured server logs Vercel |
| Ошибки интерфейса | клиентские ошибки и техническая телеметрия | `/api/telemetry/client-error`, логи Vercel |
| База | ограничения, триггеры, RLS, миграции | Supabase SQL Editor / logs |

Для расследования сначала фиксируют request id, пользователя, время Kyiv и маршрут. Затем проверяют серверный лог, `audit_log`, запись `feedback`/агрегат и Storage. Не следует публиковать service-role ключи, PIN или подписанные URL в тикетах.

## 7. Состояние миграций, значимых для текущих экранов

| Миграция | Для чего | Зависимость |
|---|---|---|
| `028_photo_report_analytics_phase1.sql` | базовые правила и окна фотозвитов | фотозвиты |
| `029_photo_report_seller_daily.sql` | ежедневный агрегат продавца | аналитика фотозвитов |
| `030_seller_replacement_stores.sql` | разрешения замен и атрибуция | выбор магазина в фотозвите, замены |
| `031_store_work_schedules.sql` | периоды и смены | графики работы |
| `032_store_schedule_month_grid.sql` | месячная view по магазинам | вкладка «Статистика» графиков |
| `033_employee_absences.sql` | реестр отсутствий | вкладка «Графік відсутностей» |

Порядок обязателен. Если отсутствует `032`, экран статистики корректно показывает ошибку о неприменённой миграции, даже если `033` уже выполнена.
