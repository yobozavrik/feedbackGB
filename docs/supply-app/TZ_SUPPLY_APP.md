Версия 1.0 · 2026-07-23 · статус: **на согласование**

Документ описывает, **как команде работать** с двумя планами:
[REMEDIATION_PLAN.md](./REMEDIATION_PLAN.md) (30 пунктов исправлений) и

## 2. Решения, принятые до старта фазы 3

Три развилки закрыты [ADR 0004](./ADR/0004-hr-and-consumables-reuse-feedback.md).
Фаза 3 использует только зафиксированные в нём границы.

### Р-1. Можно ли HR и розхідні матеріали хранить в `feedback`

`SUPPLY_APP_IMPLEMENTATION_PLAN.md` §2 говорит: «Не использовать таблицу
`feedback` и категорию `consumables_request` как основу нового контура».
`HR_CONSUMABLES_BRIDGE_PLAN.md` предлагает именно `feedback` + `hr_question` /
`consumables_request`.

Формального противоречия нет: запрет §2 написан про **контур сырья**, где нужен
полноценный документооборот со статусами и проведением в учёт. HR и розхідні
матеріали — это перенос уже существующих seller-фич, у которых нет ни статусной
машины сырья, ни проведения на склад.

**Решение:** `ADR/0004-hr-and-consumables-reuse-feedback.md` фиксирует
границу: `feedback` — для HR и розхідних матеріалів; отдельные документные
таблицы (`supply_requests`, `raw_material_defects`, `incoming_documents`) — для
сырья. Без этого ADR ревьюер обоснованно заблокирует PR со ссылкой на §2.

### Р-2. Прямой вызов CRM или outbox

`SUPPLY_APP_IMPLEMENTATION_PLAN.md` §3: «`supply-app` не должен вызывать CRM
напрямую, все изменения идут через outbox». Мост розхідних матеріалів
переиспользует существующий **синхронный** server-to-server вызов из
seller-app: CRM вызывается до записи в журнал, чтобы пользователь не увидел
успех, если склад заявку не принял.

**Решение:** синхронный вызов допускается как исключение для
розхідних матеріалів (обоснование: поток уже в проде, идемпотентен по
`feedback_id`, пользователю нужен немедленный отказ) — **или** мост
переписывается под outbox, и тогда меняется UX (заявка «принята локально,
статус придёт позже») и растёт объём работ фазы 3 примерно вдвое.

Рекомендация: исключение с явной записью в ADR. Outbox остаётся обязательным
для контура сырья, где документы влияют на учёт остатков.

### Р-3. Словарь ролей и типов локаций

Расхождения между документами и уже написанной миграцией:

| Что | `SUPPLY_APP_IMPLEMENTATION_PLAN.md` | `20260723_001_supply_employees.sql` |
|---|---|---|
| Операционные роли | `supply_worker`, `supply_manager`, `receiver`, `quality_controller` | `worker`, `senior_worker` |
| `facilities.kind` | `production`, `warehouse` | `workshop`, `warehouse` |
| Где живёт роль | в `user_facility_memberships.role` | в `supply_employee_profiles.operational_role`, а в membership — `permission` |

**Решение:** до применения migration словарь приведён к ТЗ: `production |
warehouse`, а operational role хранится только в membership. Второй migration
и правка данных не требуются.

## 4. Рабочий процесс

### 4.1. Ветки

```
fix/supply-<номер>-<короткое-имя>       # пункты плана исправлений
feat/supply-<эпик>-<короткое-имя>       # фазы моста
chore/supply-<...>                      # инфраструктура, доки
```

Одна ветка = один тикет. Базовая ветка для PR — основная ветка репозитория
(сейчас `devin/1777397957-feedback-mini-app`), уточнить у тимлида перед первым PR.

### 4.2. Коммиты

Conventional Commits с областью, как уже принято в репозитории
(`feat(auth):`, `feat(supply):`, `test(app):`, `fix(app,admin):`):

```
fix(supply): app-scoped PIN verification via user_app_access

Closes SUP-001.
```

Область: `supply`, `app`, `admin`, `shared`, `db`, `docs`. Несколько областей
через запятую.

### 4.3. Pre-commit

Активен `gitleaks protect --staged` (см. `.husky/pre-commit`). Требует
установленного `gitleaks`. `--no-verify` запрещён без письменного согласования
тимлида.

К нему добавляется (задача SUP-019) вызов `scripts/check-shared-drift.sh`,
расширенного на три приложения.

### 4.4. Pull Request

Обязательное содержимое описания:

1. Номер пункта (`SUP-XXX`) и ссылка на раздел плана.
2. **Критерии приёмки из плана — скопированы чек-листом** с отметками.
3. Что проверено вручную и на каком окружении.
4. Влияние на seller-поток: «нет» или перечень затронутых файлов `shared/`.

Правила ревью:

* Любой PR, трогающий `shared/lib/*` → обязательное ревью владельца feedback-app.
* Любой PR, трогающий авторизацию (пункты 1–6) → обязательное второе ревью.
* Любой PR с миграцией → ревью Backend/DB + явное «применять / не применять».
* PR без прохождения CI-гейта (раздел 8) не мержится.

### 4.5. Размер PR

Один пункт плана — один PR. Исключения, где пункты объединяются намеренно
(зафиксировано в планах):

* SUP-001 + SUP-002 — чинятся одним куском кода;
* SUP-012 + SUP-013 + SUP-014 — один проход по Tailwind + один общий тест.

PR больше ~400 изменённых строк без согласования не принимается.

## 5. Окружения и секреты

| Окружение | Назначение | Supabase | Секреты |
|---|---|---|---|
| local | Разработка | Общий dev-контур через `npm run bootstrap:local-env` | Генерируются локально, `.env.local` в `.gitignore` |

Правила:

1. `SUPPLY_SESSION_SECRET` — уникален для каждого окружения, ≥32 символов,
   **никогда** не равен `SESSION_SECRET` seller-app.
2. `SUPABASE_SERVICE_ROLE_KEY` не попадает в клиентский бандл; проверяется
   поиском по `.next/static` в CI.
3. Копирование прод-секретов в preview запрещено (`RUNBOOK.md`).
4. Любой новый ключ добавляется в `.env.example` **и** в README тем же PR.

## 6. Процедура применения миграций

```
1. Разработчик пишет миграцию в supabase/migrations/YYYYMMDD_NNN_*.sql
2. PR с миграцией → ревью Backend/DB → мерж (миграция НЕ применена)
3. Тимлид даёт super_admin: файл + чек-лист проверок + план отката
4. super_admin применяет в Supabase SQL Editor на staging-контуре
5. QA прогоняет приёмочные проверки миграции
6. super_admin применяет на проде, фиксирует дату в supabase/migrations/README.md
7. Разработчик запускает пост-проверочные SQL-скрипты (раздел 8.4)
```

Каждая миграция обязана содержать: комментарий-шапку с назначением, явный
`set search_path`, идемпотентные `if not exists`, и **описанный откат** —
либо `down`-скрипт, либо явную пометку «откат невозможен, причина: …».

Изменения в схеме `household_chemicals` этой процедуре **не** подчиняются —
их выполняет CRM-команда в своём репозитории (раздел 9).

## 8. Критерии готовности и гейты

### 8.1. Definition of Ready (задачу можно брать)

* Пункт плана прочитан целиком, включая «Критерии приёмки» и «Тесты».
* Все зависимости из раздела 7 закрыты.
* Если задача трогает развилку из раздела 2 — соответствующий ADR принят.
* Понятно, нужна ли миграция и кто её применит.

### 8.2. Definition of Done (задача закрыта)

1. Все критерии приёмки соответствующего пункта плана выполнены и отмечены в PR.
2. Тесты из раздела «Тесты» этого пункта написаны и зелёные.
3. CI-гейт (8.3) пройден.
4. Ревью по правилам 4.4 получено.
5. Проверено на preview-окружении, в PR приложен результат (лог, скриншот или вывод `curl`).
6. Регресс seller-потока не сломан (для задач, трогающих `shared/`).
7. Затронутые документы обновлены **в том же PR**.

Формулировки «поправлю потом», «работает локально», «тест добавлю следующим PR»
основанием для мержа не являются.

### 8.3. CI-гейт (обязателен для мержа)

```bash
npm run lint && npm run typecheck && npm run test && npm run build
./scripts/check-shared-drift.sh
node scripts/check-tailwind-classes.mjs supply-app
node scripts/check-route-links.mjs supply-app
```

Плюс проверка, что `SUPABASE_SERVICE_ROLE_KEY` не встречается в `.next/static`.

### 8.4. Пост-миграционные проверки (после применения)

```bash
# гранты anon/authenticated на supply-таблицы — ожидание: 0 строк
psql -f scripts/check-supply-rls.sql
# facilities без crm_location_id — ожидание: 0 строк
psql -f scripts/check-supply-facility-mapping.sql
# продавцы без CRM-магазина — ожидание: 0 строк (существующий скрипт)
```

## 9. Работа с CRM-командой

Единственная задача на их стороне — **CRM-01**. Передать им нужно:

1. Готовый текст функции `rpc_create_feedbackgb_supply_consumables_order`
   (раздел «Р2» документа `HR_CONSUMABLES_BRIDGE_PLAN.md`) — это копия рабочей
   функции с заменой одного `SELECT`.
2. Обоснование, почему нельзя обойтись существующей функцией: у всех цехов и
   складов в `household_chemicals.shops` (id 25–39) `poster_spot_id IS NULL`,
   а функция резолвит точку именно по этому полю.
3. Требуемые тесты (раздел 6 того же документа): двойной вызов с одним
   `p_feedback_id`, таймаут после коммита, конкурентные вызовы одного цеха,
   неактивная точка.
4. Явное подтверждение, что мост розхідних матеріалів **не** подпадает под гейт
   ADR 0003 (он идемпотентен по `feedback_id` через
   `feedbackgb_order_contributions`), а гейт остаётся в силе для
   `rpc_create_employee_order`, `rpc_create_write_off_with_items`,
   `rpc_create_receipt_with_items`.

**Пока CRM-01 не готова:** эпик 6 не начинается, эпик 5 (HR) поставляется и
релизится независимо. Именно поэтому HR стоит в плане раньше.

Эскалация: если CRM-01 не подтверждена в течение спринта — тимлид выносит
вопрос на уровень владельца продукта, а команда переключается на эпик 7.

## 10. Релиз и откат

### Порядок выката

```
1. Эпики 0–1 → прод. Приложение доступно только admin/super_admin с явным
   user_app_access. Пользователей ещё нет.
2. Эпики 2–4 → прод. Внешне почти ничего не меняется, но код становится
   ревьюируемым и тестируемым.
3. Эпик 5 (HR) → пилот: один цех, 2–3 человека, одна неделя.
4. Расширение на все цеха и склады после недели без инцидентов.
5. Эпик 6 (розхідні) → пилот тем же составом, затем расширение.
6. Эпик 7 → по готовности.
```

### Признаки, что надо откатываться

* Рост `auth.login.failure` без объяснения.
* Любая seller-заявка, потерянная или задублированная после правок `shared/`.
* Расхождение количества `orders` и `feedback` по розхідних матеріалах.
* CSP ломает Telegram Mini App у продавцов.

### Как откатываться

* Код: revert PR и redeploy предыдущего билда в Vercel.
* Миграции: по `down`-скрипту либо по описанной в шапке причине невозможности.
* Доступы: `update feedbackgb.user_app_access set is_active=false, revoked_at=now()`
  — мгновенно отключает пользователей без деплоя.

### Что мониторим первые две недели (по `RUNBOOK.md`)

Ошибки входа, ошибки API, отказы CRM, расхождения заявок и заказов,
неназначенные заявки (`assigned_to IS NULL`).

## 11. Приёмка

Работа принимается тимлидом **по пунктам**, а не «в целом». Форма приёмки —
чек-лист из 30 строк, где каждая строка ссылается на PR и содержит отметку QA.

Приёмка эпиков 5 и 6 дополнительно требует сквозного прогона на staging силами
QA: один работник цеха проходит вход → 5 HR-заявок → заказ розхідних →
«Мої заявки» → изменение статуса на складе → уведомление админу; и отдельно —
полный регресс seller-потока в feedback-app.

Проект считается закрытым, когда:

* все 30 пунктов имеют статус «принято»;
* обе фичи работают на проде минимум две недели без инцидентов уровня P0/P1;
* `check-shared-drift.sh`, `check-supply-rls.sql` и оба mapping-скрипта дают
  нулевые расхождения;
* документы разделов 1 и 2 обновлены под фактическое состояние.

## 12. Чего делать нельзя

Список коротких запретов, каждый — следствие уже найденной проблемы:

1. Не копировать файл из `feedback-app` в `supply-app` — выносить в `shared/lib`
   (иначе третья копия и дрейф, пункт 19).
2. Не хардкодить CRM-идентификаторы в коде приложения — только env или БД
   (требование `READ_ONLY_AUDIT_2026-07-23.md`, пункт SUP-C01).
3. Не заполнять `shops.poster_spot_id` синтетическими значениями для цехов —
   это внешний ключ Poster.
4. Не менять сигнатуру работающей `rpc_create_feedbackgb_consumables_order` —
   seller-поток в проде.
5. Не применять миграции из кода приложения и не автоприменять их в CI.
6. Не добавлять `Link` на маршрут, которого нет — карточка «скоро» вместо 404
   (пункт 7).
7. Не расширять `ACCESSIBLE_ROLES` списком ролей — доступ определяется данными
   `user_app_access`, а не константой (пункт 1).
8. Не логировать PIN, куки, содержимое вложений и полные имена (SECURITY.md).
