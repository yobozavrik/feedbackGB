## Группа A. Безопасность и авторизация (P0)

### 1. Аутентификация не app-scoped

**Проблема.** `POST /api/auth/pin` вызывает глобальный `verify_pin_global` и
проверяет только `role ∈ {admin, super_admin}`. `user_app_access` и
`user_facility_memberships` не проверяются. Нарушены ADR 0002 и SECURITY.md:
PIN админа из seller-app является паролем от supply-app.

**Метод.**
1. Новая SECURITY DEFINER функция `feedbackgb.verify_pin_for_app(p_pin text, p_app_key text)`:
   выполняет ту же проверку bcrypt, что и `verify_pin_global`, но
   дополнительно требует активную строку `user_app_access(app_key = p_app_key)`
   и — для `role = 'supply_worker'` — хотя бы одну активную
   `user_facility_memberships`. Возвращает `jsonb`
   `{id, full_name, display_label, role, facility_id, facility_name}`, никогда
   не возвращает `pin_hash` (существующая `verify_pin_global` возвращает всю
   строку `users`, включая хеш, — этот дефект в новую функцию не переносим).
2. `route.ts` переходит на неё; `ACCESSIBLE_ROLES` удаляется как понятие —
   доступ определяется данными, а не константой в коде.
3. Гранты: `revoke all from public, anon, authenticated`, `grant execute to service_role`.

**Критерии приёмки.**
* Работник с ролью `supply_worker`, но без `user_app_access('supply_app')` → `401`.
* Админ без `user_app_access('supply_app')` → `401` (единое правило, без исключений для админов).
* Работник с доступом, но без активного membership → `401`.
* Ответ во всех отказных случаях байт-в-байт одинаков; отличается только `auth.login.failure` в аудите.

**Тесты.**
* Юнит на route c мок-RPC: 4 отказных ветки + 1 успешная.
* SQL-тест функции: 6 комбинаций (`is_active`, `has_pin`, `app_access`, `membership`, `locked_until`, роль).
* Регресс: `verify_pin_global` не изменена — seller-логин прогоняется на staging.

### 2. Отказанный вход меняет строку пользователя

**Проблема.** `verify_pin_global` при совпадении PIN делает
`update users set last_login = now(), failed_attempts = 0, locked_until = null`
и только потом возвращает строку. Supply-app отклоняет её по роли — но запись
уже изменена. Это даёт неавторизованный сброс `locked_until` чужого
seller-аккаунта и портит достоверность `last_login`.

**Метод.** Побочный эффект переносится за проверку доступа: в
`verify_pin_for_app` (пункт 1) `update` выполняется **только** на ветке, где
все проверки пройдены. Существующая `verify_pin_global` не трогается —
seller-поток остаётся как есть.

**Критерии приёмки.**
* PIN продавца, введённый в supply-app: ответ `401`, а `users.last_login`,
  `failed_attempts`, `locked_until` — без изменений (снимок до/после совпадает).
* Успешный вход supply-работника: `last_login` обновлён.

**Тесты.**
* SQL: `select last_login, failed_attempts, locked_until` до и после отказного вызова — равенство.
* Интеграционный: 3 подряд отказных попытки не сбрасывают счётчик, установленный вручную.

### 3. Нет middleware — защита только внутри страниц

**Проблема.** Единственная защита — `requireSupplyUser()` в теле страницы.
`/api/*` не закрыт на границе; любой новый роут без явного вызова открыт.

**Метод.** `supply-app/src/middleware.ts` по образцу feedback-app:
пропускать `/`, `/api/auth/*`, `/_next`, `/favicon.ico`, `/icons/*`; всё
остальное — проверка `supply_session`; для `/api/*` — JSON `401`, для страниц —
редирект на `/` с `?next=`. Matcher: `["/((?!_next/static|_next/image|favicon.ico).*)"]`.
`requireSupplyUser()` **остаётся** как defence-in-depth (так же, как в
feedback-app роут дублирует проверку сессии).

**Критерии приёмки.**
* `curl` без куки на `/api/*` → `401 {"error":"unauthenticated"}`.
* `curl` без куки на `/home/...` → `307` на `/?next=...`.
* Просроченная/подделанная кука обрабатывается как анонимная.
* `/` и `/api/auth/pin` доступны анониму.

**Тесты.**
* Юнит middleware: таблица из 10 путей × {без куки, валидная, испорченная}.
* Smoke в CI: подъём `next start`, 4 `curl` с проверкой кода ответа.

### 4. Деградировали заголовки безопасности

**Проблема.** Есть только `nosniff`, `Referrer-Policy`, `X-Frame-Options`.
Нет CSP, HSTS, `Permissions-Policy`. При этом `X-Frame-Options: SAMEORIGIN`
ломает Telegram Mini App, заявленный в README и ADR 0001; feedback-app
специально отказался от XFO в пользу `frame-ancestors`.

**Метод.** Портировать блок `headers()` из `feedback-app/next.config.mjs`:
HSTS, `Permissions-Policy`, CSP с `frame-ancestors 'self' https://web.telegram.org https://*.telegram.org`,
`form-action 'self'`, `object-src 'none'`, `base-uri 'self'`;
`connect-src` строится из `NEXT_PUBLIC_SUPABASE_URL`. `X-Frame-Options` удалить
вместе с поясняющим комментарием, почему.

**Критерии приёмки.**
* Ответ прод-сборки содержит `Content-Security-Policy`, `Strict-Transport-Security`, `Permissions-Policy`.
* `X-Frame-Options` отсутствует.
* Консоль браузера чиста от CSP-violations на всех страницах.
* Страница открывается во фрейме `web.telegram.org` и не открывается во фрейме постороннего домена.

**Тесты.**
* Юнит: импорт `nextConfig`, `headers()` → assert по набору ключей и по подстроке `frame-ancestors`.
* Ручная проверка во фрейме — до и после.

### 5. HMAC-ключ rate-limit падает на публичный дефолт

**Проблема.** `loginRateLimit.secret()` возвращает
`"supply-local-dev-secret-not-for-production"` без production-guard, тогда как
`session.ts` в проде бросает исключение. Пороги тоже разошлись: сессия требует
≥32 символов, rate-limit — любую длину.

**Метод.** Единственный источник секрета — экспортированный
`getSessionSecret()` из `session.ts` (ровно так это сделано в
`shared/lib/session.ts` + `rateLimit.ts`). `secret()` в `loginRateLimit.ts`
удаляется. Порог длины один — 32.

**Критерии приёмки.**
* `NODE_ENV=production` + пустой `SUPPLY_SESSION_SECRET` → приложение падает на
  первом обращении к секрету, а не работает на публичном ключе.
* Секрет длиной 31 символ в проде отклоняется обеими подсистемами одинаково.
* В коде остаётся ровно одно вхождение строки-дефолта.

**Тесты.**
* Юнит: 4 комбинации (`NODE_ENV` × наличие/длина секрета) для сессии и для `pinBucket`.
* `grep -c "supply-local-dev-secret"` по `src/` = 1.

### 6. Логин-страница не знает про сессию

**Проблема.** `/` всегда рендерит PIN-пад; авторизованный не редиректится на
`/home`. Обратно: `requireSupplyUser()` при протухшей сессии делает
`redirect("/")`, не сбрасывая битую куку.

**Метод.** На `/` — серверная проверка `verifySupplySession` и `redirect("/home")`
при валидной сессии. В `requireSupplyUser()` перед редиректом — очистка куки
(`cookies().set(SUPPLY_SESSION_COOKIE, "", { maxAge: 0 })`) либо редирект на
`/api/auth/logout` c последующим `303` на `/`.

**Критерии приёмки.**
* Авторизованный на `/` → `307` на `/home`.
* Пользователь с валидной подписью, но деактивированный в БД: редирект на `/`, куки в ответе нет.
* Повторный заход не зацикливается.

**Тесты.**
* Интеграционный: `is_active = false` → редирект + `Set-Cookie` с `Max-Age=0`.
* E2E: логин → `/` → `/home`.

## Группа B. Функциональные дефекты (P1)

### 7. Девять из десяти ссылок главного экрана ведут в 404

**Проблема.** `SupplyHomeGrid` ссылается на `/home/feedback/tech_issue`,
`consumables_request`, `supply_problem`, `store_idea`, `spotted_elsewhere`,
`customer_voice`, `/home/hr-menu`; шапка — на `/home/my-requests` и
`/home/notifications`. Сборка подтверждает: существуют только `/`, `/home`,
`/home/supply` и два API-роута.

**Метод.** Сетка перестраивается под реальную поверхность supply:
`Сировина для цеху` (есть), `Заявка на розхідні матеріали` и `Питання по HR`
(поставляются фазами 2–3 моста — см. `HR_CONSUMABLES_BRIDGE_PLAN.md`).
Всё, что ещё не реализовано, отображается карточкой с состоянием
«скоро» — `aria-disabled`, без `href`, с подписью, а не мёртвой ссылкой.
Категории seller-приложения (`store_idea`, `customer_voice`, `spotted_elsewhere`)
удаляются: они про торговый зал и к цеху отношения не имеют.

**Критерии приёмки.**
* Ноль `<Link>` на несуществующий маршрут.
* Карточки «скоро» не кликабельны и озвучиваются скринридером как недоступные.
* Скрипт-обход собирает список `href` из JSX и сверяет с деревом `src/app` — расхождений нет.

**Тесты.**
* Юнит: парс `SupplyHomeGrid`/шапки, каждый `href` резолвится в существующий `page.tsx`.
* E2E-smoke: клик по каждой активной карточке → `200`.

«Що сьогодні в магазині?», «чого не вистачає на полицях», «v1 • Галя Балувана».

* Название приложения в шапке и в `<title>` совпадает.

**Тесты.** Юнит: `grep` по скомпилированному `copy.ts` на стоп-лист терминов.

### 9. Logout показывает пользователю JSON

**Проблема.** `<form action="/api/auth/logout" method="post">`, а роут
возвращает `NextResponse.json({ok:true})` — браузер уходит на страницу с
текстом `{"ok":true}`.

**Метод.** Роут отвечает `303 See Other` с `Location: /` для навигационных
запросов (`Accept: text/html`) и сохраняет JSON для `fetch`. Кука гасится в
обоих случаях.

**Критерии приёмки.**
* Выход через форму приводит на `/`, JSON не показывается.
* `fetch('/api/auth/logout', {method:'POST'})` по-прежнему получает `{"ok":true}`.
* Кука `supply_session` удалена в обеих ветках.

**Тесты.** Юнит: два вызова роута с разным `Accept` → `303` / `200`, оба с `Max-Age=0`.

### 10. Выход не пишется в аудит

**Проблема.** Нет события `auth.logout` (в feedback-app оно есть с actor/ip/ua).

**Метод.** В logout-роуте прочитать сессию, при валидной — записать
`auth.logout` с `actor_user_id`, `ip`, `user_agent`, `meta.app_surface = 'supply_app'`.
Запись никогда не блокирует выход (ошибки проглатываются с логом).

**Критерии приёмки.**
* После выхода в `audit_log` появляется строка `auth.logout` с корректным `actor_user_id`.
* Выход без сессии не создаёт строку и не падает.
* Недоступность БД не мешает удалить куку.

**Тесты.** Интеграционный: мок `insert` бросает — ответ всё равно `303`/`200` и кука снята.

### 11. `/home/supply` — три мёртвые карточки

**Проблема.** Три `<div>` без ссылок, без disabled-состояния и без объяснения,
что модуль не готов. Админский preview честнее — там есть `Alert` «Очікує міграцію».

**Метод.** Добавить на страницу баннер состояния по образцу
`feedback-admin/.../admin/supply/page.tsx` и перевести карточки в явное
состояние «недоступно», с датой/условием разблокировки (гейт CRM из ADR 0003).

**Критерии приёмки.**
* Пользователь видит текст, объясняющий недоступность, а не молчаливую заглушку.
* Карточки помечены `aria-disabled="true"`.

**Тесты.** Юнит-рендер: наличие баннера и `aria-disabled` на всех трёх карточках.

## Группа C. Стили и UI

### 12. `bg-elev2` не существует (P1)

**Проблема.** `hover:bg-elev2` / `active:bg-elev2` (3 использования) — в
`tailwind.config.ts` нет цвета `elev2`, в `globals.css` нет `--elev-2`.
Проверено по собранному CSS: правило не сгенерировано.

### 14. `font-display` не существует, шрифты не подключены (P1)

**Проблема.** 7 использований `font-display`; в конфиге нет `fontFamily.display`,
`next/font` не подключён вообще. Не резолвятся ни `font-display`, ни `font-sans`.

**Метод.** В `app/layout.tsx` подключить `Inter` + `Manrope` через `next/font/google`
с сабсетами `cyrillic`, прокинуть `--font-sans` / `--font-display`, добавить
`fontFamily` в конфиг. Значения — те же, что в feedback-app.

**Критерии приёмки.**
* `getComputedStyle` заголовка возвращает Manrope, тела — Inter.
* Кириллица не подменяется системным шрифтом.

**Тесты.** Общий CI-скрипт `check-tailwind-classes.mjs`: собрать список
классов из `src/**/*.tsx` по префиксам (`bg-`, `text-`, `font-`, `animate-`),
проверить наличие каждого в выходном CSS; падать со списком отсутствующих.
Этот один скрипт закрывает пункты 12, 13, 14 и защищает от повторения.

### 17. Доступность PIN-пада (P1)

**Проблема.** Ошибка выводится в `<div>` без `role="alert"`; `aria-live="polite"`
висит на контейнере точек, где текста нет. Плюс гонка: `busy` снимается в
`finally` сразу, а `setPin("")` — через 200 мс, ввод в это окно затирается.

**Метод.** `role="alert"` + `aria-live="assertive"` на контейнере ошибки;
с точек `aria-live` снять, добавить `aria-label="Введено N з 6 цифр"`.
Гонку убрать: снимать `busy` только после завершения анимации и очистки
(один таймер, один переход состояния).

**Критерии приёмки.**
* Скринридер озвучивает ошибку сразу после отказа.
* Нажатия во время shake-анимации игнорируются, а не теряются.
* Клавиатурная навигация по кнопкам работает, фокус видим.

**Тесты.**
* Юнит на редьюсер состояния пада: последовательность `ввод×6 → отказ → ввод`
  даёт ожидаемое значение, без потерянных цифр.
* `axe` в компонентном тесте — ноль нарушений.

ссылок на `PinLogin`.

### 19. Дублирование вместо `shared/` (P1)

**Проблема.** `session.ts`, `loginRateLimit.ts`, `audit.ts`, `supabase.ts`
переписаны заново; `next.config.mjs` не включает `experimental.externalDir`;
`scripts/check-shared-drift.sh` не покрывает supply-app. Воспроизводится ровно
та проблема дрейфа, ради которой хук и написан.

**Метод.**
1. `experimental: { externalDir: true }` в `supply-app/next.config.mjs`.
2. Общая логика переезжает в `shared/lib/`; в supply-app остаются тонкие
   ре-экспорты (как `feedback-app/src/lib/categories.ts`).

### 22. Аудит пишет чужой формат `actor` (P2)

**Критерии приёмки.**

**Тесты.** Юнит на маппинг строки аудита; SQL-проверка после деплоя.

### 23. `ip` пишется в `inet` без валидации (P2)

молча проглатывается в `console.error`.

**Метод.** Нормализация перед записью: взять первый элемент цепочки, обрезать

**Критерии приёмки.**

**Тесты.** Табличный юнит на 8 вариантов заголовка.

## Группа E. Миграция `20260723_001_supply_employees.sql` (P1)

### 27. RLS включён, политик нет

**Проблема.** `enable` + `force` на всех четырёх таблицах, но ни одной политики.
Работает только потому, что у `service_role` есть `bypassrls`. Первый же
доступ под `authenticated` упрётся в пустой набор и будет отлажен неверно.

**Метод.** Зафиксировать намерение явно: комментарий в миграции «доступ только
server-side через service_role; политик нет намеренно» плюс `revoke all` от
`anon, authenticated` (уже есть — дополнить проверкой). Если позже понадобится
клиентский доступ — политики добавляются отдельной миграцией, а не молча.

**Критерии приёмки.**
* В миграции есть явный комментарий о модели доступа.
* Проверочный SQL показывает: у `anon`/`authenticated` нет ни одного гранта на 4 таблицы и вью.

**Тесты.** SQL-скрипт `check-supply-rls.sql` в `scripts/`: `information_schema.role_table_grants` по 4 таблицам — ожидание нуля строк для `anon`/`authenticated`.

### 28. `updated_at` без триггеров

**Проблема.** Колонки есть, обновляющих их триггеров нет — значение навсегда
равно `created_at`.

**Метод.** Общая функция `feedbackgb.touch_updated_at()` + `before update`
триггер на `facilities`, `supply_employee_profiles` (и на `feedback`, если

**Критерии приёмки.** `update` любой строки меняет `updated_at`; повторное
чтение подтверждает разницу.

**Тесты.** SQL: `update ... ; select updated_at > created_at` → true для каждой таблицы.

### 29. Слабое ограничение на `revoked_at`

**Проблема.** `check ((is_active and revoked_at is null) or (not is_active))`
разрешает `is_active = false` при `revoked_at IS NULL` — «отозвано, но
неизвестно когда».

**Метод.** Ужесточить до
`check ((is_active and revoked_at is null) or (not is_active and revoked_at is not null))`
для `user_app_access` и `user_facility_memberships`. Поскольку миграция ещё не
применена, правится на месте, без второй миграции.

**Критерии приёмки.** `insert` со `is_active=false, revoked_at=null` отклоняется;
корректные комбинации проходят.

**Тесты.** SQL: 4 комбинации на каждую таблицу — 2 успеха, 2 отказа.

### 30. Приложение не детектит непринятую миграцию

**Проблема.** Миграция намеренно не применена, но приложение это никак не
проверяет — оно просто молча работает на старой схеме.

**Метод.** Стартовая проверка `assertSupplySchema()` в `requireSupplyUser()`
(кэшируется на процесс): один запрос к `information_schema.tables` на наличие
`facilities` / `user_app_access`. Если таблиц нет — пользователю показывается
явный экран «Модуль ще не активовано», а не пустая или неправильно работающая
страница. Параллельно — `GET /api/health` c полями
`{ schema_ready, crm_reachable, session_secret_ok }`.

**Критерии приёмки.**
* На БД без Supply-миграции приложение показывает понятный экран, а не 500 и не
  «пустой, но рабочий» интерфейс.
* `/api/health` отдаёт `schema_ready: false` до применения и `true` после.
* Проверка выполняется не чаще одного раза на процесс (нет запроса на каждый рендер).

**Тесты.**
* Интеграционный с моком `information_schema`: обе ветки.
* Проверка кэша: два вызова `requireSupplyUser` → один запрос к схеме.
