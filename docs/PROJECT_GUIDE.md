# FeedbackGB — паспорт проекта

Актуально по коду ветки `design/app-cosmetic-refresh`. Этот документ описывает реализованный контур, а не является планом будущей разработки.

## 1. Назначение

FeedbackGB — внутренняя система сети «Галя Балувана» из двух независимых Next.js-приложений и общей базы Supabase:

| Контур | Папка | Пользователь | Назначение |
|---|---|---|---|
| Приложение продавца | `feedback-app` | продавец | PIN-вход, обращения, HR-заявки, фотозвиты, личные обращения |
| Админ-панель | `feedback-admin` | администратор / супер-администратор | обработка обращений, управление продавцами, графиками и аналитикой |
| Общий код | `shared` | оба контура | сессии, категории, Telegram, отчёты, валидация и общие типы |
| База | Supabase, схема `feedbackgb` | только серверные API | источник фактов, аудит, Storage и агрегаты |

Оба приложения развёртываются отдельными Vercel-проектами. Push в Git не означает, что оба приложения уже задеплоены: их статусы проверяются отдельно.

## 2. Технологии и границы

- Next.js 14, React 18, TypeScript.
- Приложение продавца: Tailwind, оптимизировано под мобильный WebView/браузер.
- Админ-панель: Ant Design и Pro Components; страницы в `feedback-admin/src/app/(admin)/admin`.
- Supabase Postgres и private Storage bucket для фото. Браузер не получает service-role ключ.
- Telegram используется для Mini App/идентификации и уведомлений; Google Drive и PostHog — подключаемые интеграции.
- Серверные API работают через `getServerSupabase()`; клиентские компоненты обращаются только к `/api/*`.

## 3. Роли и доступ

| Роль | Возможности |
|---|---|
| `seller` | Входит по PIN, создаёт только свои обращения и фотозвиты. Основной магазин берётся из учётной записи; доступные магазины для замены выдаются отдельно. |
| `admin` | Работает в админ-панели с операционными данными в пределах обычных административных прав. |
| `super_admin` | Полное администрирование, включая управление периодами графиков, системные журналы и раздел «Виробництво». |

Сессия подписывается сервером и хранится в cookie. PIN в базе хранится в виде хеша; открытый PIN не является данными отчёта или журнала.

## 4. Репозиторий

```text
feedbackGB/
├── feedback-app/          # продавецкое приложение
│   ├── src/app/           # экраны и API
│   ├── src/components/    # мобильные формы и элементы
│   └── docs/              # подробности контура продавца
├── feedback-admin/        # админ-панель
│   ├── src/app/           # страницы, API, cron
│   ├── src/lib/           # авторизация, аудит, аналитика
│   ├── supabase/          # последовательные SQL-миграции
│   └── docs/              # технические планы и runbook
├── shared/lib/            # общий код двух приложений
├── docs/                  # общая актуальная документация
└── scripts/               # служебные проверки
```

`feedback-admin/supabase/schema.sql` — базовая схема. Файлы с номерами в `feedback-admin/supabase/` — последовательные миграции. Файлы в `_deferred/` не считаются применёнными только потому, что лежат в репозитории.

## 5. Основные данные

| Сущность | Назначение | Источник истины |
|---|---|---|
| `feedbackgb.users` | учётные записи, роли, основной магазин, активность | Supabase |
| `feedbackgb.feedback` | обращения и фотозвиты | Supabase |
| `feedbackgb.audit_log` | журнал значимых действий | Supabase |
| `feedbackgb.seller_store_permissions` | разрешения продавцу работать на заменах | миграция 030 |
| `feedbackgb.photo_report_attribution` | неизменяемая привязка фотозвита к продавцу и фактическому магазину | миграция 030 |
| `feedbackgb.photo_report_seller_daily` | агрегат «продавец–магазин–дата»: число звитов и фото | миграция 029 |
| `feedbackgb.work_schedule_periods`, `store_work_shifts` | плановые графики магазинов | миграция 031 |
| `feedbackgb.v_store_schedule_store_month` | месячная статистика запланированных смен по магазинам | миграция 032 |
| `feedbackgb.employee_absences` | внесённые администратором отпуска, больничные, отгулы | миграция 033 |

`categories.spots` и `categories.products` — внешний справочный контур магазинов и товаров. Их не следует менять из этого репозитория без отдельного решения.

## 6. Реализованные функциональные контуры

Полный пользовательский путь и ограничения описаны в [BUSINESS_PROCESSES.md](./BUSINESS_PROCESSES.md), а состав экранов — в [MODULES_AND_ROUTES.md](./MODULES_AND_ROUTES.md).

Критичные различия:

- плановая смена в графике — не доказательство фактического выхода;
- отправленный фотозвит доказывает PIN-авторизованную отправку, но не заменяет табель учёта рабочего времени;
- разрешение на замену даёт право выбрать магазин для фотозвита, но само по себе не фиксирует смену;
- запись в реестре отсутствий создаётся администратором и не равна HR-заявке из приложения продавца;
- разделы «Виробництво» существуют в навигации как защищённые страницы-заглушки. Таблицы, импорт и рабочие процессы производства пока не подключены.

## 7. Локальный запуск и проверка

```powershell
cd feedback-app
npm.cmd install
npm.cmd run dev

cd ..\feedback-admin
npm.cmd install
npm.cmd run dev
```

Каждому приложению нужен собственный `.env.local` на основе `.env.example`. Секреты не коммитятся и не копируются между Preview и Production без осознанной настройки окружения.

Минимальная проверка изменённого контура:

```powershell
cd feedback-app; npm.cmd run typecheck; npm.cmd test
cd ..\feedback-admin; npm.cmd run typecheck; npm.cmd test
```

После SQL-миграции обязательны readback-запросы из конца её файла. Применение следующей миграции не доказывает применение предыдущей.

## 8. Как поддерживать документацию

При изменении функции обновить одновременно:

1. этот документ — если меняется архитектурная граница или состав модулей;
2. [MODULES_AND_ROUTES.md](./MODULES_AND_ROUTES.md) — если меняется экран или API;
3. [BUSINESS_PROCESSES.md](./BUSINESS_PROCESSES.md) — если меняется правило для пользователя;
4. миграционный документ или `DATA_MODEL.md` соответствующего приложения — если меняется Supabase;
5. тесты, которые подтверждают новое правило.
