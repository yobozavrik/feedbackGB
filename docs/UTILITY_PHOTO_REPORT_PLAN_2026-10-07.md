# «Надати показники»: актуальний план

Детальний бізнес- і технічний контракт, джерела даних, Mermaid-схеми, API та маршрут помилок: [UTILITY_PHOTO_REPORT_TECHNICAL_DOCUMENTATION_2026-10-07.md](UTILITY_PHOTO_REPORT_TECHNICAL_DOCUMENTATION_2026-10-07.md).

**Рішення власника, уточнено 2026-10-08:** це фотозвіт за чотирма категоріями. Користувач не вводить цифри й не обирає лічильник. Перше подання за місяць можливе з 28-го числа 00:00 до останнього дня місяця 23:59:59.999 за Києвом. Якщо подання для категорії й місяця вже є, користувач може в будь-який час зняти 1–3 нові фото й надіслати нову версію, навіть після перевірки або після дедлайну. Раніше подані місяці доступні нижче поточних карток; порожні старі місяці для першої подачі не відкриваються.

## 1. Маршрут користувача

1. На головній сторінці відкрити «Надати показники».
2. Обрати картку: «Електроенергія», «Вода», «Опалення» або «Інші послуги».
3. Усередині категорії зробити фото камерою або додати з галереї. Побачити мініатюри, видалити невдале фото. Можна додати необов'язковий коментар.
4. Натиснути «Надіслати фото». Успіх показувати після збереження в Supabase; доставка в Telegram має окремий статус.

Для магазину з кількома дозволеними точками користувач спершу обирає магазин. На одне подання допускається 1–3 фото. Мінімум шести фото чинного загального фотозвіту тут не застосовується: однієї квитанції може бути достатньо. Повтор у тій самій категорії й місяці створює нову версію; попередня зберігається в історії.

    Головна → Надати показники
                 ├─ 💡 Електроенергія → фото → надіслати
                 ├─ 💧 Вода          → фото → надіслати
                 ├─ ♨️ Опалення     → фото → надіслати
                 └─ 📄 Інші послуги → фото → надіслати

Не всі чотири категорії обов'язкові кожному магазину. Без окремо підтверджених правил відсутність фото в категорії не можна називати порушенням. Значення, тариф, суму й споживання система не розпізнає та не обчислює.

## 2. Supabase і доступ

| Об'єкт | Призначення |
|---|---|
| utility_periods | Внутрішній місячний ключ і deadline. Функція ensure_current_utility_period створює поточний місяць при першому авторизованому запиті. Початок першої подачі обчислюється як 28-ме число за Києвом, окреме поле не зберігається. |
| utility_submissions | Магазин, місяць, категорія, автор, коментар, версія, статус перевірки та idempotency ID. Старі версії не стираються. |
| utility_uploads | Тимчасовий приватний файл, власник, категорія, MIME, hash і термін очищення. |
| utility_photos | Прикріплені до подання фото та їхній порядок. |
| utility_delivery_jobs | Черга Telegram, спроби, стани й message IDs. |
| utility_events | Аудит подання та перевірки. |

Міграції `056_utility_readings.sql` і `057_utility_resubmission_and_three_photos.sql` застосовані власником у production. Read-only перевірка після 057 підтвердила текст нової RPC і права; фактичне подання не перевірене. Окремий bucket utility-reading-photos приватний. Прямі права anon/authenticated на таблиці відсутні; API використовує серверний service role. Фото в адмінці відкриваються через короткі signed URL. Необроблені тимчасові файли очищаються після 24 годин.

**Міграція 058 застосована власником 08.10.2026:** `feedback-admin/supabase/058_utility_initial_window.sql` додає перевірку 28-го числа тільки до першої подачі в `submit_utility_photos`. Read-only звірка встановленої RPC, прав і календарних меж пройшла; подробиці у [протоколі](UTILITY_READINGS_PRODUCTION_READBACK_2026-10-07.md). 056 і 057 повторно не запускати.

## 3. API

| Маршрут | Контракт |
|---|---|
| GET /api/utility-readings/stores | Лише домашній магазин і активні дозволи на заміну. |
| GET /api/utility-readings?store_id=... | Поточний місяць, deadline, поточні категорії та сторінка історії раніше поданих місяців (`history_offset`, 20 записів за раз). |
| POST /api/utility-readings/uploads | Одне фото JPEG/PNG/WebP до 2 МБ; перевірка магазину, місяця й категорії. |
| POST /api/utility-readings/submissions | Категорія, 1–3 upload IDs, коментар, idempotency ID. SQL RPC атомарно створює подання, фото й delivery job. |
| GET /api/admin/utility-readings/config | Поточний місяць, список усіх створених періодів і активні магазини (до 1000; понад ліміт — явна помилка). |
| GET /api/admin/utility-readings/coverage | Магазин × категорія: фото є/немає, кількість фото, перевірка, Telegram. |
| GET/POST /api/admin/utility-readings/submissions | Деталь із фото та версіями; підтвердження або повернення з причиною. |
| GET /api/cron/utility-dispatch | Надсилання одного job до окремого Telegram-чату. |
| GET /api/cron/utility-cleanup | Видалення незакріплених фото після 24 годин. |

Сервер щоразу перевіряє активну сесію, роль і право магазину. SQL RPC повторно перевіряє ці права, строк, категорію та власника кожного фото. Повтор того самого idempotency ID і payload повертає той самий submission ID; інший payload є конфліктом.

## 4. Адмінка й Telegram

На першому етапі адмінка має «Огляд фото» і «Подання». Огляд показує чотири рядки для кожного магазину, але не підсумовує це як обов'язкове 4/4. У деталі є коментар, фото, історія версій та перевірка. Адміністратор обирає будь-який створений місяць у списку, щоб побачити повторні подання старих місяців. Вкладка та колонка «Доставка в Telegram» з'являються лише після налаштування chat ID і включення worker; до того адмінка прямо повідомляє, що пересилання ще не налаштоване.

**Оновлення 08.10:** власник обрав доставку від робочого Telegram-акаунта, який уже є в групі, без додавання бота. Bot API не бачить групу `-5364085383` (`400 chat not found`), тому старий Vercel dispatcher залишається вимкненим. Підготовлено окремий однопроцесний MTProto worker у `services/utility-telegram-worker`: він читає задачі Supabase, надсилає текст і 1–3 фото, записує message IDs. Його ще не розгорнуто й не авторизовано на VPS; ID групи через робочий акаунт не підтверджено. Потрібні SSH-доступ, одноразовий вхід на сервері, тест повідомлення й readback job. Сесія акаунта зберігатиметься лише в захищеному volume; паралельні worker не допускаються. Деталі — TD-002 і README сервісу.

Розпізнавання чисел зі знімків спроєктоване окремо: [UTILITY_METER_OCR_DESIGN_2026-10-08.md](UTILITY_METER_OCR_DESIGN_2026-10-08.md). Воно не активне; очікуються приклади фото лічильників.

## 5. Перевірки та запуск

Усі міграції у staging і production застосовує лише власник проєкту. Виконавець цього плану готує SQL, перевіряє його без запису й після повідомлення власника звіряє фактичний стан бази; сам міграцію не запускає.

1. Плановий порядок був: staging перед production. Фактично власник підтвердив застосування 056 і 057 у production; read-only readback структури 056 і тексту RPC після 057 пройдено. Ізольований staging і фактичні сценарії ще треба перевірити. 056 у production повторно не запускати.
2. Перевірити rollback при чужому фото, простроченні, відкликаному праві магазину, повторі idempotency ID і дублі фото.
3. На Android/iOS у Telegram WebView пройти всі чотири картки: камера, галерея, видалення, 1 і 3 фото, повторне подання в поточному й старому місяці, повільна мережа, повторне натискання. Перевірити читабельність фото після стискання.
4. У staging перевірити seller/home, seller/replacement і admin, підписані URL, повернення та нову версію. Перевірити відсутність прямого доступу anon/authenticated.
5. Після отримання окремого chat ID перевірити текст і всі фото в тестовому чаті, 429/5xx/timeout/часткову доставку й readback message IDs. Cron Telegram-доставки не зареєстрований у production: його розклад, пікове навантаження та накопичену чергу треба перевірити перед окремим включенням worker.
6. Прогнати регресію звичайного фотозвіту, typecheck і build обох застосунків. Перший етап app/admin увімкнений за замовчуванням; явне `NEXT_PUBLIC_UTILITY_READINGS_ENABLED=false` вимикає його. `UTILITY_READINGS_ENABLED` залишити вимкненим до готовності чату й окремої перевірки доставки. Cleanup працює від прапорця адмінки, тому його cron і авторизацію потрібно перевірити до приймання першого етапу.

## 6. Фактичний стан

Код і міграції 056/057 створені; власник підтвердив їх застосування у production. Read-only перевірка підключеної БД підтвердила 6 таблиць, 4 RPC, RLS, права й приватний bucket; після 057 — новий ліміт 3, відсутність старої заборони повтору після підтвердження, окрему гілку першої подачі й права RPC. Межі перевірки — у [протоколі readback](UTILITY_READINGS_PRODUCTION_READBACK_2026-10-07.md). Додаткова read-only перевірка RPC перегляду підтвердила обмеження «тільки поточна неперевірена версія». Станом на 08.10 у підключеній БД один період і жодного подання; перевірку кількості фото цього дня не проводили. Staging не підтверджено; Telegram не надсилався. SQL-вираз останнього дня місяця перевірено read-only для 28/29/30/31 і київського переходу часу; установлену RPC з реальними поданнями не викликали. Ручний UI-тест на пристроях і наскрізний staging тест не проводилися.

**Локальна перевірка 08.10.2026:** 203/203 тести застосунку, 1090/1090 тести адмінки, typecheck і production build обох пройшли. Власник застосував 058; read-only звірка пройшла. Це не підтверджує авторизовану подачу фото в production; потрібен наскрізний тест.

Крок 8 частково виконано локально: seller/admin API та cron повертають `x-request-id`, пишуть безпечні JSON-події; cleanup рахує помилки. Потрібні staging-перевірка логів, моніторинг `uncertain`/`sending`/черги та відповідальний за реакцію. Деталі й обмеження — у технічній документації, розділ 7.

Продовження 07.10.2026: спільний `checkCronAuth` змінено так, що production без `CRON_SECRET` завжди повертає `503`, навіть із заголовком `x-vercel-cron: 1`. Це закриває локальний обхід захисту cleanup cron; наявність секрету в розгорнутому середовищі та фактичний виклик cron ще не перевірені. Локально повторно пройшли typecheck і production build обох застосунків, 194/194 тестів seller app і 1083/1083 тестів admin. Один застарілий тест розкладу адмінки скориговано: частий cron майбутньої Telegram-доставки не є нічним foodcost worker. Наскрізне подання фото, staging і ручна перевірка на пристроях залишаються відкритими.

Після цього до `.env.example` обох застосунків додано явні вимкнені за замовчуванням прапорці першого етапу; адмінський приклад окремо залишає Telegram worker вимкненим і chat ID порожнім. Два нові цільові тести адмінського огляду перевірили відмову при `forbidden` від контексту доступу та чотири рядки категорій із правильною кількістю фото. Ці тести використовують імітацію БД і не замінюють перевірку фактичного Supabase-запиту й UI у staging.

Read-only перевірка Vercel 07.10.2026: production-деплої `app.feedback.gb` і `admin.feedback-gb` мають commit `d11cf15` з іншої гілки; код цього модуля у production не розгорнуто. Preview застосунку для `codex/utility-photo-report` має `d1af539` і стан `READY`; preview адмінки для цієї гілки не знайдено. У списках env обох проєктів немає `NEXT_PUBLIC_UTILITY_READINGS_ENABLED`, тому розділ не ввімкнено. `NEXT_PUBLIC_SUPABASE_URL` та `SUPABASE_SERVICE_ROLE_KEY` мають записи, призначені одночасно production і preview; отже, preview не можна вважати ізольованим staging без окремої перевірки фактичного адресата. Значення env не читалися. Це перевірка деплоїв і метаданих, не тест користувацького маршруту.

Бізнес-правило повторного подання зафіксовано: перше фото за категорію/місяць дозволене з 28-го числа до кінця поточного місяця за Києвом; якщо запис уже є, нова версія дозволена без строку й незалежно від статусу перевірки. Код застосунків оновлено, production RPC після 058 містить перевірку початку вікна в гілці першої подачі. Поведінку з реальними даними ще треба перевірити.

Після першого production-деплою користувач показав скриншот без картки «Надати показники»: публічний прапорець не був заданий, а код вимагав буквального `true`. Правило змінено на увімкнення за замовчуванням з аварійним вимкненням через явне `false` в app/admin. До перевірки нового деплою на пристрої це виправлення є лише кодом, а не підтвердженням користувацького маршруту.

Після наступного деплою адмінська сторінка відкрилася, але огляд показував «Не вдалося завантажити подання» і хибні нулі. Причина в коді: `GET /api/admin/utility-readings/coverage` зберіг стару перевірку `flag === "true"`, тоді як решта першого етапу перейшла на правило «увімкнено, якщо не задано `false`». Маршрут виправлено і додано тест для відсутнього прапорця та явного `false`. Поки огляд не завантажено, KPI й таблиця не показуються як нулі. Фактичне подання фото та перегляд під авторизованим адміністратором ще потребують перевірки.

Корінний `.gitignore` мав загальне правило `coverage`, яке ховало однойменний каталог API від `rg` і заважало адресному `git add`. Правило звужено до каталогів результатів тестового покриття; це дозволяє наступним перевіркам знаходити вихідний маршрут `coverage`.

| 9 | Повторити typecheck, production build і регресію звичайного «Фотозвіту» після staging-прийомки. Міграції в production вже застосовані; 056 не повторювати. Перший етап app/admin працює за замовчуванням; Telegram worker вмикати окремо після його приймання. | Нова функція збереження й адмін-перевірки працює у цільовому середовищі; доставку підтверджують окремо на другому етапі. |

Якщо цільовий запуск не пройшов перевірку, вимкнути прапорці застосунків та worker, зберегти записи й фото для розбору. Міграцію не видаляти автоматично: це знищило б подані дані.

## 8. Модель процесу і даних

```
Продавець → категорія → фото → тимчасове завантаження в приватний bucket
         → атомарне подання в Supabase → job доставки → окремий Telegram-чат
                                        ↓                   ↓
                              адмін перевіряє      бухгалтер читає фото
                              / повертає           (це не статус перевірки)
```

Один магазин має максимум одне **поточне** подання для кожної пари «місяць + категорія». Нове подання створює наступну версію; попереднє лишається в історії. Одне нове подання має 1–3 фото і один job доставки. Перший запис після дедлайну не створюється; вже існуючий можна замінити незалежно від статусу й дати. Відсутність фото — інформація, а не автоматична заборгованість: обов'язковість категорій для конкретного магазину ще не задано.

Схема відповідальності: продавець створює фото, Supabase надійно зберігає оригінальний факт подання, worker копіює матеріали в чат, адміністратор перевіряє та може повернути з причиною, бухгалтер отримує матеріали у звичному робочому каналі. Вартість Telegram і зберігання поки не оцінена: для розрахунку потрібні кількість магазинів, середня кількість фото, фактичний розмір після стискання та політика зберігання.

«Реєстр» тут означає простий список записів, як класний журнал: рядок показує магазин, місяць, послугу, чи є фото, і його стан. Реєстр сам не читає цифри з лічильника.
