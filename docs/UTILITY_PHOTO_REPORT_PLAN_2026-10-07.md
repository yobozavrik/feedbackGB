# «Надати показники»: актуальний план

**Рішення власника, 2026-10-07:** це фотозвіт за чотирма категоріями. Користувач не вводить цифри й не обирає лічильник. Місяць зберігається технічно, без вибору у формі. Крайній строк — останній день місяця, 23:59:59.999 за Києвом.

## 1. Маршрут користувача

1. На головній сторінці відкрити «Надати показники».
2. Обрати картку: «Електроенергія», «Вода», «Опалення» або «Інші послуги».
3. Усередині категорії зробити фото камерою або додати з галереї. Побачити мініатюри, видалити невдале фото. Можна додати необов'язковий коментар.
4. Натиснути «Надіслати фото». Успіх показувати після збереження в Supabase; доставка в Telegram має окремий статус.

Для магазину з кількома дозволеними точками користувач спершу обирає магазин. На одне подання допускається 1–15 фото. Мінімум шести фото чинного загального фотозвіту тут не застосовується: однієї квитанції може бути достатньо. Повтор у тій самій категорії й місяці створює нову версію.

    Головна → Надати показники
                 ├─ 💡 Електроенергія → фото → надіслати
                 ├─ 💧 Вода          → фото → надіслати
                 ├─ ♨️ Опалення     → фото → надіслати
                 └─ 📄 Інші послуги → фото → надіслати

Не всі чотири категорії обов'язкові кожному магазину. Без окремо підтверджених правил відсутність фото в категорії не можна називати порушенням. Значення, тариф, суму й споживання система не розпізнає та не обчислює.

## 2. Supabase і доступ

| Об'єкт | Призначення |
|---|---|
| utility_periods | Внутрішній місячний ключ і deadline. Функція ensure_current_utility_period створює поточний місяць при першому авторизованому запиті. |
| utility_submissions | Магазин, місяць, категорія, автор, коментар, версія, статус перевірки та idempotency ID. Старі версії не стираються. |
| utility_uploads | Тимчасовий приватний файл, власник, категорія, MIME, hash і термін очищення. |
| utility_photos | Прикріплені до подання фото та їхній порядок. |
| utility_delivery_jobs | Черга Telegram, спроби, стани й message IDs. |
| utility_events | Аудит подання та перевірки. |

Міграція: feedback-admin/supabase/056_utility_readings.sql. Окремий bucket utility-reading-photos приватний. Прямі права anon/authenticated на таблиці відсутні; API використовує серверний service role. Фото в адмінці відкриваються через короткі signed URL. Необроблені тимчасові файли очищаються після 24 годин.

## 3. API

| Маршрут | Контракт |
|---|---|
| GET /api/utility-readings/stores | Лише домашній магазин і активні дозволи на заміну. |
| GET /api/utility-readings?store_id=... | Автоматично визначений поточний місяць, deadline і поточні версії по категоріях. |
| POST /api/utility-readings/uploads | Одне фото JPEG/PNG/WebP до 2 МБ; перевірка магазину, місяця й категорії. |
| POST /api/utility-readings/submissions | Категорія, 1–15 upload IDs, коментар, idempotency ID. SQL RPC атомарно створює подання, фото й delivery job. |
| GET /api/admin/utility-readings/config | Поточний місяць і активні магазини. |
| GET /api/admin/utility-readings/coverage | Магазин × категорія: фото є/немає, кількість фото, перевірка, Telegram. |
| GET/POST /api/admin/utility-readings/submissions | Деталь із фото та версіями; підтвердження або повернення з причиною. |
| GET /api/cron/utility-dispatch | Надсилання одного job до окремого Telegram-чату. |
| GET /api/cron/utility-cleanup | Видалення незакріплених фото після 24 годин. |

Сервер щоразу перевіряє активну сесію, роль і право магазину. SQL RPC повторно перевіряє ці права, строк, категорію та власника кожного фото. Повтор того самого idempotency ID і payload повертає той самий submission ID; інший payload є конфліктом.

## 4. Адмінка й Telegram

Адмінка має «Огляд фото», «Подання» і «Доставка в Telegram». Огляд показує чотири рядки для кожного магазину, але не підсумовує це як обов'язкове 4/4. У деталі є коментар, фото, історія версій та перевірка. Місяць лишається в БД для історії; MVP адмінки показує поточний місяць.

Окремий worker надсилає назву магазину, категорію, місяць, автора, коментар, версію, ID подання й усі фото. Для 2–10 фото використовується Telegram [sendMediaGroup](https://core.telegram.org/bots/api#sendmediagroup); 11–15 фото діляться на дві групи, одне фото надсилається через sendPhoto. Фото відповідають на головне текстове повідомлення; після кожної групи worker записує всі message IDs. Адресат береться лише з TELEGRAM_UTILITY_CHAT_ID, без fallback на чат звичайного фотозвіту. ID і остаточний адресат ще не надані; це TD-002 у feedback-admin/docs/TECHNICAL_DEBT.md. Стани sending після втрати worker та uncertain потребують ручної звірки перед повтором, щоб не створити дубль.

## 5. Перевірки та запуск

1. Застосувати міграцію спершу у staging і виконати feedback-admin/supabase/056_utility_readings_readback.sql: шість таблиць, чотири функції, RLS, приватний bucket.
2. Перевірити rollback при чужому фото, простроченні, відкликаному праві магазину, повторі idempotency ID і дублі фото.
3. На Android/iOS у Telegram WebView пройти всі чотири картки: камера, галерея, видалення, 1 і 15 фото, повільна мережа, повторне натискання. Перевірити читабельність фото після стискання.
4. У staging перевірити seller/home, seller/replacement і admin, підписані URL, повернення та нову версію. Перевірити відсутність прямого доступу anon/authenticated.
5. Після отримання окремого chat ID перевірити текст і всі фото в тестовому чаті, 429/5xx/timeout/часткову доставку й readback message IDs. Поточний cron бере один job раз на п'ять хвилин; пікове навантаження треба виміряти.
6. Прогнати регресію звичайного фотозвіту, typecheck і build обох застосунків. Після успішного readback цільової БД увімкнути NEXT_PUBLIC_UTILITY_READINGS_ENABLED в обох деплоях і UTILITY_READINGS_ENABLED у worker.

## 6. Фактичний стан

Локальні код і міграція створені. Міграція не застосована ні в staging, ні в production; Telegram не надсилався, прапорці не вмикалися. TypeScript typecheck і production build обох застосунків пройшли після переробки. Пройшли 43 тести застосунку (включно з API нового модуля й регресією фотозвіту), 7 тестів фотозвіту адмінки та 2 тести відповіді Telegram-альбому. Після цього окремо пройшли ще 2 тести обмеження multipart-запиту без Content-Length; повний набір після останньої правки повторно не запускався. SQL-вираз останнього дня місяця перевірено read-only у PostgreSQL для 28/29/30/31 і київського переходу часу; саму функцію міграції ще не виконували. Ручний UI-тест на пристроях і наскрізний staging тест не проводилися.

Відкрите бізнес-правило: подання після кінця місяця зараз блокується, у тому числі якщо адміністратор повернув фото на виправлення вже після deadline. Причину повернення співробітник бачить на картці, але порядок пізнього виправлення треба визначити до production запуску; довільний пільговий строк у код не додано.

| 7 | Оцінити чергу: поточний cron обробляє один job кожні 5 хвилин. За потреби перед запуском збільшити контрольовану пропускну здатність. | Піковий обсяг магазинів вкладається в прийнятний час доставки; залишок черги й помилки видно адміністратору. |
| 8 | Повторити typecheck, production build і регресію звичайного «Фотозвіту». Після цього застосувати міграцію в цільовій БД, зробити readback і лише потім увімкнути прапорці. | Нова функція працює у цільовому середовищі, звичайний фотозвіт працює, тестова доставка пройшла саме в окремий чат. |

Якщо цільовий запуск не пройшов перевірку, вимкнути прапорці застосунків та worker, зберегти записи й фото для розбору. Міграцію не видаляти автоматично: це знищило б подані дані.

## 8. Модель процесу і даних

```
Продавець → категорія → фото → тимчасове завантаження в приватний bucket
         → атомарне подання в Supabase → job доставки → окремий Telegram-чат
                                        ↓                   ↓
                              адмін перевіряє      бухгалтер читає фото
                              / повертає           (це не статус перевірки)
```

Один магазин має максимум одне **поточне** подання для кожної пари «місяць + категорія». Нове подання створює наступну версію; попереднє лишається в історії. Одне подання має 1–15 фото і один job доставки. Відсутність фото — інформація, а не автоматична заборгованість: обов'язковість категорій для конкретного магазину ще не задано.

Схема відповідальності: продавець створює фото, Supabase надійно зберігає оригінальний факт подання, worker копіює матеріали в чат, адміністратор перевіряє та може повернути з причиною, бухгалтер отримує матеріали у звичному робочому каналі. Вартість Telegram і зберігання поки не оцінена: для розрахунку потрібні кількість магазинів, середня кількість фото, фактичний розмір після стискання та політика зберігання.

«Реєстр» тут означає простий список записів, як класний журнал: рядок показує магазин, місяць, послугу, чи є фото, і його стан. Реєстр сам не читає цифри з лічильника.
