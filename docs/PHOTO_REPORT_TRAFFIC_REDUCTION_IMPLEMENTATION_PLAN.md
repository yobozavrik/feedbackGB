# План внедрения: снижение трафика фото-отчётов

**Дата:** 06.10.2026
**Система:** `app.feedback.gb`, приложение `feedback-app`
**Статус:** временный аварийный план на 10 дней; изменений в коде и инфраструктуре этим документом не вносится.
**Граница работ:** пользовательский сценарий, количество фото (6–15), один `JSON + base64` запрос и серверный API-контракт сохраняются. Прямая загрузка из клиента в Storage и multipart в эту поставку не входят.

## 1. Решение и границы достоверности

Предлагаемая поставка: для категории `photo_report` временно сжимать снимки до максимальной стороны `768 px`, ограничивать **декодированный** файл `50 KiB` и кодировать его в WebP при поддержке браузером; иначе использовать JPEG. Если лимит не достигнут, фото автоматически уменьшается вплоть до `1×1 px`, а не отклоняется по размеру. Срок режима — максимум 10 дней, возврат к обычному качеству только отдельным явным решением владельца.

Это безопасное узкое изменение клиента. Сервер уже принимает `image/jpeg`, `image/png` и `image/webp`, определяет расширение WebP и сохраняет корректный MIME. Изменять route, миграции, Storage или интерфейс для этого не нужно.

Однако WebP нельзя считать гарантированной экономией. Safari/iOS не поддерживает кодирование WebP через `canvas.toDataURL("image/webp")`: браузер вернёт PNG, поэтому клиент обязан распознать это и выбрать JPEG. Лимит `50 KiB` — потолок декодированного файла; итоговый JSON содержит base64. Бюджет рассчитывается как если бы все устройства использовали JPEG. WebP на поддерживаемых Android/Chrome — дополнительный, но не обещанный выигрыш.

| Показатель при 69 отчётах/сутки и 15 фото | Сейчас: 280 KiB | Аварийный режим: 50 KiB |
|---|---:|---:|
| Максимальный декодированный размер отчёта | 4.10 MiB | 0.73 MiB |
| Максимальный base64 JSON-размер фото | 5.47 MiB | 0.98 MiB |
| Максимум в сутки только для клиентского POST | 377 MiB | 67 MiB |
| Максимум за 10 суток | 3.68 GiB | 0.66 GiB (`≈0.71 GB`) |
| Максимум за 30 суток | 11.05 GiB | 1.97 GiB (`≈2.12 GB`) |

Формула: `reports × photos × decoded_limit × 4/3`. Префиксы `data:image/...;base64,` и прочие поля JSON добавляют небольшой объём сверх результата.

**Следствие.** При 69 отчётах/сутки аварийный режим ограничивает только фото-POST примерно `0.71 GB` за 10 суток. Это делает общий бюджет `1.0–1.5 GB` технически достижимым, если весь прочий трафик аккаунта за тот же период не превышает примерно `0.29–0.79 GB`. Поскольку baseline собран с фильтром `All Projects`, это не гарантия общего лимита: расход прочих проектов надо контролировать каждый день.

## 4. Изменение кода

**Ветка:** отдельная от фактической production-ветки; production ref необходимо проверить до создания ветки.
**Разрешённая область:** два файла ниже и тесты/документация. Изменение server route, миграций или UI запрещено без отдельного решения.

### Шаг 1. Уменьшить параметры только фото-отчёта

В `feedback-app/src/components/FeedbackForm.tsx` заменить только props `PhotoInput` для `isPhotoReport`:

```tsx
maxOutputBytes={isPhotoReport ? 50 * 1024 : undefined}
maxDimension={isPhotoReport ? 768 : undefined}
```

**Проверка изменения:**

1. Убедиться поиском, что `PHOTO_REPORT_MAX_PHOTOS` не изменён.
2. Убедиться, что props с `undefined` для обычной обратной связи остались прежними.
3. Проверить, что серверный `PHOTO_REPORT_MAX_PHOTO_BYTES = 280 * 1024` не изменён.

**Аргументация:** клиент перестаёт создавать крупные новые файлы, но уже открытые вкладки и старый релиз продолжают проходить серверную валидацию.

### Шаг 2. Добавить WebP с контролируемым JPEG-fallback

В `feedback-app/src/components/PhotoInput.tsx`:

1. Вынести кодирование canvas в локальную функцию, принимающую `canvas`, MIME и quality.
2. Один раз для данной операции проверить поддержку WebP: результат `canvas.toDataURL("image/webp", quality)` должен начинаться с `data:image/webp;`.
3. Если поддержка подтверждена, использовать WebP на всех итерациях цикла качества; иначе JPEG на всех итерациях.
4. Сохранить quality `0.82 → 0.34` шагом `0.08`, уменьшение обеих сторон `×0.75` и `COMPRESS_CONCURRENCY = 2`; **только для фото-отчёта** продолжать уменьшение до `1×1 px`. При потолке `50 KiB` это исключает отказ по размеру: в крайнем случае отправится почти нечитаемое фото, но лимит не будет превышен. Ошибка остаётся лишь для технического сбоя Canvas/чтения файла.
5. Сравнивать с лимитом именно декодированный размер через существующий `dataUrlByteLength`, а не длину строки base64.
6. Не подменять fallback PNG: отсутствие WebP должно привести к JPEG, поскольку PNG может увеличить трафик.

**Проверка изменения:**

- data URL в WebP-пути имеет MIME `image/webp`;
- в fallback-пути — `image/jpeg`, в том числе на iOS/Safari; PNG не отправляется;
- каждый возвращённый файл имеет decoded size `≤ 51200` байт;
- алгоритм выбрасывает понятную ошибку, если даже при минимальном размере лимит недостижим;
- фото с альфа-каналом и поворотом обрабатываются так же, как текущая реализация. Если поворот уже неверен на реальном устройстве, это отдельный дефект, не маскировать его данной поставкой.

## 5. Автоматические проверки до ручных устройств

### Шаг 3. Добавить тестируемую границу компрессии

Сейчас `compressImage` не экспортируется и покрытие компонента отсутствует. Перед или вместе с изменением вынести чистую часть выбора MIME/проверки data URL в тестируемую функцию либо добавить компонентный тест в jsdom. Не нужно тестировать браузерный Canvas моками как реальный кодек; тесты должны проверять контракт алгоритма.

Минимальный набор:

| Тест | Ожидаемый результат |
|---|---|
| WebP поддерживается | выбран `image/webp`; результат проходит MIME-проверку |
| WebP не поддерживается | выбран `image/jpeg`, не PNG |
| Результат ровно на границе | принимается при `≤ 50 KiB` |
| Результат выше границы | следующая quality/итерация уменьшения запускается |
| Сложный кадр на пороге | алгоритм уменьшает вплоть до `1×1 px`, но не возвращает файл `> 50 KiB` и не отклоняет его по размеру |
| Обычная форма | не получает `50 KiB`/`768 px`, остаётся на дефолтах |
| `photo_report` | до 15 фото и минимум 6 не меняются |

Запустить из `feedback-app` кроссплатформенно:

```powershell
npm run typecheck
npm test
npm run build
```

Перед `build` составить инвентарь переменных окружения из `.env.example` и настроек deployment. В репозитории `.env.example` перечисляет 17 переменных; это не доказывает число variables в хостинге. Для production-проверки должны быть доступны все обязательные production variables, включая `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `TELEGRAM_BOT_TOKEN` и `SESSION_SECRET`; секреты в лог или документ не выводить.

**Критерий перехода:** все три команды успешны в среде с необходимыми переменными. Если Windows sandbox даёт `spawn EPERM`, это фиксируется как ограничение среды и тест повторяется в разрешённой среде; нельзя объявлять тест пройденным без успешного запуска.

## 6. Проверка в preview до production

### Шаг 4. Поднять preview без изменения BotFather и production URL

1. До deploy проверить targets всех environment variables: Preview и Production. Нельзя предполагать, что preview изолирован: без отдельных Preview variables он может использовать production Supabase/Telegram и записать тестовый отчёт в боевую БД.
2. Задеплоить отдельный preview текущей ветки только после этой проверки.
3. Если Preview использует production data, тестировать исключительно на заранее выделенном тестовом магазине и только разрешёнными неперсональными снимками; иначе настроить изолированную тестовую среду.
4. Открыть приложение именно во встроенном Telegram WebView и в обычном мобильном браузере, потому что поддержка Canvas/WebP зависит от runtime, а не только от ОС.

### Шаг 5. Выполнить матрицу приёмочного тестирования

Для каждого успешного теста сохранить: устройство, ОС, Telegram/browser, MIME каждой фотографии, decoded bytes, полный `Content-Length` запроса, HTTP-статус, наличие фото в seller UI и admin UI.

| Сценарий | Шаги | Ожидаемый результат |
|---|---|---|
| iPhone / Telegram WebView | 15 типичных фото, отправить | JPEG-fallback; нет PNG; все фото открываются; запрос `< 8 MiB` |
| Android / Telegram WebView | то же | то же |
| Обычный мобильный браузер | то же | WebP или JPEG-fallback в зависимости от фактического Canvas; нет PNG |
| Принудительный fallback | замокать/эмулировать возврат не-WebP | формируются JPEG; нет PNG; каждое фото `≤50 KiB` |
| Тёмный снимок и мелкий ценник | добавить 15 сложных снимков | отправка проходит при `≤50 KiB`; визуальная читаемость не является критерием аварийного режима, но результат фиксируется |
| Вертикальное фото | загрузить с камеры | корректная ориентация в форме и админке |
| Минимум | отправить 6 фото | отчёт принимается |
| Максимум | отправить 15 фото | отчёт принимается одним запросом |
| Обычная обратная связь | добавить до 5 фото | параметры фото не изменились |
| Негативный размер | подготовить неподходящее фото | понятная ошибка клиента, без частичного отчёта |

Дополнительно проверить Runtime Logs для каждого удачного отчёта:

1. Есть `photo_report.received` с корректным `photo_count` и `request_bytes`.
2. Есть `photo_report.storage_complete` и `photo_report.completed`.
3. Нет `photo_report.storage_partial_failure`.
4. В admin gallery подписанные URL возвращают и показывают все изображения.

**Критерий перехода:** 100% успешных сценариев для поддерживаемых устройств, отсутствие регрессии обычной формы, и p95 полного JSON-запроса меньше заранее установленного порога. Гарантированный верхний порог: `≤ 0.98 MiB` без малого JSON-overhead; практический контролируемый предел запроса — `< 1.05 MiB`.

**Стоп-условия:** любая частичная загрузка, неподдерживаемый MIME на сервере, ухудшение ориентации, рост ошибок отправки или неприемлемое качество ценников. Сначала исправить и повторить всю затронутую строку матрицы.

### Шаг 8. Ежедневный контроль и выход из аварийного режима

Каждый день в течение 10 дней фиксировать Fast Origin Transfer (Incoming/Outgoing/всего), число фото-отчётов и ошибки отправки. Неполный день не сравнивать с полным.

Формат отчёта:

1. Период, часовой пояс, единицы панели и состав метрики.
2. Количество `received`, `completed`, ошибок, средний/p95 `request_bytes` до и после.
3. Доля WebP и JPEG-fallback: в этой поставке — только результаты контролируемой выборки устройств. Текущий `photo_report.received` не логирует MIME, а server route по границам поставки не меняется. Добавление безопасного агрегированного MIME-лога — отдельная явно согласованная серверная правка.
4. Fast Origin Transfer до/после при сопоставимых днях недели.
5. Заключение: `VERIFIED`, `PARTIALLY VERIFIED` или `NOT VERIFIED`.

**Условие окончания аварийного режима:** истекли 10 дней и владелец отдельно разрешил возврат параметров. Не возвращать качество автоматически. Перед возвратом сохранить итоговый расход и подтвердить, что общий лимит больше не под угрозой.

1. Вернуть `280 KiB / 1280 px / JPEG` или задеплоить предыдущий проверенный релиз.
2. Проверить production deployment и один новый фото-отчёт.
3. Зафиксировать период, причину, затронутые устройства и показатели до/после.
4. Не удалять сохранённые фотографии как часть отката.

## 9. Решение о следующем шаге

Multipart либо direct-to-Storage могут дополнительно убрать base64-overhead, но это отдельная архитектурная поставка: другой клиентский запрос, другой server route, безопасность upload и новые failure modes. Их нельзя включать скрыто в текущую правку.

Если даже аварийный режим `50 KiB / 768 px` не укладывается в общий бюджет:

1. Сначала проверить реальную причину: частота отчётов, размер запросов, JPEG-fallback, выдача изображений или другой вид трафика.
2. При подтверждённо плохом качестве рассматривать более высокий потолок только вместе с пересчитанным JPEG worst case и остатком общего аккаунтного бюджета; не на основании усреднённой оценки WebP.
3. При необходимости гарантированно убрать base64 — подготовить отдельный согласованный план multipart с новой нагрузочной и security-проверкой.
