# План реализации: «Графіки роботи» и раздел «Виробництво» в админ-панели

## 1. Цель

Расширить текущую админ-панель двумя функциональными контурами:

1. В существующей группе **«Мережа»** добавить страницу **«Графіки роботи»** — графики сотрудников магазинов.
2. Создать отдельную группу **«Виробництво»** с тремя страницами:
   - **«Графіки роботи»** — графики сотрудников производства;
   - **«Цехи»** — справочник и рабочее состояние цехов;
   - **«Постачання»** — контроль заявок/поставок для производства.

Это план и макеты. Код навигации, миграции, Supabase и production в рамках этого документа не меняются.

## 2. Основание в текущем дизайне

Текущий sidebar строится из `feedback-admin/src/lib/admin/menu.tsx`, а общий каркас — `AdminShell` на Ant Design ProLayout. Действующие группы: `Робота`, `Мережа`, `Аналітика`, `Система`.

Новые пункты должны использовать тот же визуальный и технический паттерн:

- sidebar с группами и иконками;
- `AdminPageContainer` с единым header, subtitle, tabs и action-кнопками;
- таблицы `ProTable` с фильтрами/сортировкой/пагинацией;
- Drawer для деталей, а не новая визуальная система;
- mobile/tablet адаптация через существующую responsive раскладку Ant Design.

## 3. Новая структура боковой панели

Названия — на украинском, как и текущая админка. Два пункта с одинаковым названием различаются смыслом и маршрутом: первый — персонал магазинов, второй — персонал производства.

## 4. Роли и доступ

Права не должны быть скрыты только на уровне sidebar. Каждый server page и API route проверяют сессию и роль.

| Функция | Admin | Super admin | Решение до реализации |
|---|---|---|---|
| Смотреть графики магазинов | Да, в своём разрешённом контуре | Да, все | Уточнить, есть ли у admin ограничения по направлениям/магазинам |
| Редактировать график магазина | Только при явном праве | Да | Нужна матрица прав и audit |
| Смотреть производство | Нет по умолчанию | Да | До утверждения — super-admin-only |
| Редактировать цеха/графики производства | Нет по умолчанию | Да | Позже отдельная роль `production_manager`, если понадобится |
| Смотреть/создавать поставки | Нет по умолчанию | Да | Зависит от источника поставок и процесса утверждения |

Рекомендация первой поставки: все страницы «Виробництво» доступны только `super_admin`; для обычного admin их нет ни в меню, ни по прямому URL. Расширение прав делается отдельной миграцией/решением, а не «на всякий случай».

## 6. Функции по страницам

### 6.1 Сетевые графики

| Функция | Описание | Условие |
|---|---|---|
| Недельный/дневной период | Переключение дня, недели и произвольного периода | Нужен единый timezone `Europe/Kyiv` |
| Фильтры | Магазин, сотрудник, статус | Данные фильтруются на сервере |
| Создание смены | ФИО, магазин, начало, конец, комментарий | Только после утверждения прав редактирования |
| Конфликт-контроль | Пересечение смен одного сотрудника, несуществующий магазин, конец раньше начала | Проверка в БД, не только UI |
| Замена | Отдельное поле «заміна» с исходным/фактическим магазином | Не меняет основной магазин сотрудника |
| Журнал | Кто и когда создал/изменил/отменил смену | Append-only audit |

### 6.2 Графики производства

Повторяют базовую механику графика, но `workshop_id` обязателен вместо `store_id`. Нельзя разрешить одну запись, которая одновременно относится к магазину и цеху.

### 6.3 Цехи

MVP справочника:

- название, код, active/inactive, адрес/локация при наличии;
- ответственный сотрудник (nullable до назначения);
- текущий operational status: `active`, `limited`, `paused`, `inactive`;
- комментарий к статусу;
- история изменения статуса.

Поля «мощность», «план выпуска», «фактический выпуск», «остатки» и «эффективность» не добавлять, пока не утверждены методика и источники данных.

### 6.4 Поставки

MVP ручного процесса:

1. Создать черновик заявки для цеха.
2. Добавить позиции с названием, единицей, количеством, комментарием.
3. Перевести по явному workflow: `draft → submitted → approved|rejected → ordered → received|cancelled`.
4. Каждая смена статуса сохраняет автора, время и комментарий.
5. Получение не меняет складские остатки автоматически.

Интеграция с закупками/Poster/warehouse CRM — отдельный этап после подтверждения идентификаторов, направлений синхронизации, владельца данных и правил отмены.

## 7. Данные и миграции

### 7.1 Критический gate: источник истины

В текущем `feedbackGB` контуре подтверждены пользователи, магазины, feedback и фотоотчёты. Не подтверждены действующие таблицы цехов, производственных сотрудников, графиков смен или поставок.

До написания migration нужно документально ответить:

1. Где сейчас ведутся цеха, сотрудники производства и графики — Supabase, Poster, CRM или вручную?
2. Что именно считается сменой: время начала/конца, тип смены, задача, факт присутствия или только план?
3. Может ли сотрудник работать одновременно в магазине и цеху?
4. Какие статусы поставки реальны и кто их переводит?
5. Есть ли существующие идентификаторы цеха/поставки в внешней системе?

Без этих ответов миграцию не создавать: иначе появится параллельный справочник и неверная интеграция.

### 7.2 Предлагаемая схема после gate

Все объекты создаются в `feedbackgb`, RLS включён, `anon`/`authenticated` не получают прямых прав. Номера миграций выбираются только после readback последней применённой migration.

| Таблица | Назначение | Минимальные поля |
|---|---|---|
| `workshops` | Справочник цехов | `id`, `name`, `code`, `is_active`, `operational_status`, `manager_id`, `created_at`, `updated_at` |
| `work_schedules` | Единая таблица плановых смен | `id`, `employee_id`, `scope_kind (store/workshop)`, `store_id nullable`, `workshop_id nullable`, `starts_at`, `ends_at`, `status`, `is_replacement`, `created_by`, `updated_by` |
| `work_schedule_events` | Append-only история смен | `id`, `schedule_id`, `event_type`, `actor_id`, `occurred_at`, `before`, `after`, `reason` |
| `supply_requests` | Шапка заявки производства | `id`, `workshop_id`, `status`, `needed_by`, `created_by`, `approved_by`, `received_at`, `comment` |
| `supply_request_items` | Позиции заявки | `id`, `request_id`, `item_name`, `external_product_id nullable`, `unit`, `quantity_requested`, `quantity_received nullable`, `comment` |
| `supply_request_events` | История статусов поставки | `id`, `request_id`, `event_type`, `actor_id`, `occurred_at`, `before`, `after`, `reason` |

### 7.3 Ограничения

1. Ровно один из `store_id`/`workshop_id` заполнен в `work_schedules`.
2. `starts_at < ends_at`.
3. `scope_kind = 'store'` соответствует ненулевому `store_id`; `scope_kind = 'workshop'` — `workshop_id`.
4. Исключающее ограничение по временному диапазону запрещает пересечение активных смен одного сотрудника, если политика не разрешит параллельные роли.
5. `supply_request_items.quantity_requested > 0`; unit обязательна.
6. Переходы статусов проводятся database function/серверным service, а не свободным PATCH.
7. Системный audit дополняется событиями `admin.schedule.*`, `admin.workshop.*`, `admin.supply.*`; history-таблицы содержат полный before/after.

## 8. API и технический контур

| Маршрут | Операция | Правило |
|---|---|---|
| `GET /api/admin/network/schedules` | Серверная выборка графика магазинов | Дата, store, employee, pagination; RBAC до query |
| `POST /api/admin/network/schedules` | Создать смену магазина | Проверка конфликта в транзакции |
| `PATCH /api/admin/network/schedules/:id` | Изменить/отменить | Optimistic concurrency + audit |
| `GET /api/admin/production/schedules` | График производства | super admin в MVP |
| `GET/POST/PATCH /api/admin/production/workshops` | Справочник цехов | super admin в MVP |
| `GET/POST/PATCH /api/admin/production/supplies` | Заявки/статусы | только workflow endpoint, не свободный статус |

Требования ко всем routes: Node runtime, `requireAdminSession`, request ID, schema validation, max body size, pagination/cursor, error codes без утечки данных, audit успешных и отказанных критичных действий.

## 9. Последовательность реализации

Не переходить к следующему этапу без проверки текущего.

### Этап 0. Утвердить функциональный контур

1. Ответить на пять вопросов из раздела 7.1.
2. Утвердить статусные модели, права и первую страницу MVP.
3. Подтвердить язык labels: украинский (`Графіки роботи`, `Виробництво`, `Цехи`, `Постачання`).

**Готово, когда:** есть согласованная матрица прав, workflow и источник данных.

### Этап 1. Навигационный каркас без данных

1. Добавить группу `Виробництво` и четыре маршрута в `admin/menu.tsx`.
2. Добавить breadcrumbs и super-admin filtering.
3. Создать PageContainer-заглушки с честным состоянием «Дані ще не підключено», без фальшивых KPI.
4. Проверить desktop, collapsed sidebar и mobile drawer.

**Готово, когда:** ссылки и прямые маршруты работают, `admin` не видит/не открывает production routes, active item/breadcrumb корректны.

### Этап 2. Миграции и аудит

1. Readback PostgreSQL, последней migration, RLS/grants.
2. Создать forward-only migration после согласования схемы.
3. Применить на staging, затем проверить таблицы, constraints, RLS и grants readback.
4. Добавить audit actions и history tables.

**Готово, когда:** нет direct browser access, constraints не дают создать пересечение/некорректную смену, audit event есть на каждом изменении.

### Этап 3. Сетевые графики

1. Реализовать server query/filter/date range.
2. Реализовать недельную таблицу с текстовым статусом и Drawer.
3. Реализовать создание/редактирование/отмену смены в транзакции.
4. Добавить проверки замены, часового пояса и конфликтов.

**Готово, когда:** фактический schedule readback совпадает с UI, конфликт невозможно сохранить ни UI, ни API.

### Этап 4. Цехи и графики производства

1. Реализовать справочник workshops и status history.
2. Реализовать production schedules с `workshop_id`.
3. Добавить tab/Drawer «графік» в деталях цеха.
4. Проверить, что магазинная и производственная записи не смешиваются.

**Готово, когда:** цехи, смены и аудит связаны корректными FK; обычный admin не имеет production доступа в MVP.

### Этап 5. Поставки MVP

1. Реализовать ручные заявки, позиции, workflow и timeline.
2. Добавить проверку количества/единиц, concurrency и статусов.
3. Не подключать внешнюю синхронизацию.

**Готово, когда:** заявка имеет непрерывную history chain; received не меняет внешний склад.

### Этап 6. Интеграции и автоматизации — отдельное решение

Только после MVP и отдельного ТЗ: Poster/CRM sync, уведомления, расчёт мощности, прогнозы, AI-помощник. Для каждого — источник, направление синхронизации, idempotency, retry, audit, rollback и staging acceptance.

### Этап 7. Приёмка и релиз

1. Unit/route/component tests, typecheck, lint, build, `git diff --check`.
2. Staging E2E с двумя admin, super admin, конфликтом смен и поставкой.
3. Проверка RLS/grants/audit readback.
4. Preview visual QA, затем production после явного подтверждения SHA.

## 11. Риски и запреты

| Риск | Мера |
|---|---|
| Появится второй «источник правды» графиков | Сначала подтвердить источник и процесс, затем migration |
| Смешение магазина/цеха | `scope_kind` + ровно один FK + DB constraints |
| Admin видит производство по URL | Server-side RBAC, а не только скрытие меню |
| Фальшивые KPI производства | Показать `Немає даних`, пока источник/формула не утверждены |
| Автопоставка изменит остатки | MVP без внешних write-интеграций |
| Нет истории правок | Append-only history + общий audit |
| Неправильное время смен | Хранить `timestamptz`, отображать `Europe/Kyiv` |

## 12. Definition of Done

Функция считается принятой только когда:

1. Sidebar и routes соответствуют разделу 3 и текущему дизайну.
2. Все страницы имеют server-side RBAC и не раскрывают данные обычному admin сверх согласованного scope.
3. Схема графиков/цехов/поставок основана на утверждённом источнике, а не догадке.
4. Каждое изменение смены, цеха или поставки audited и имеет history.
5. Нельзя сохранить пересекающиеся/некорректные смены или некорректный workflow поставки.
6. RLS/grants readback подтверждает отсутствие public/browser-доступа.
7. Все тесты из раздела 10 имеют `passed`, либо документированный `blocked` с причиной; критичных `failed` нет.
8. Production-деплой выполнен только после отдельного подтверждения commit SHA.
