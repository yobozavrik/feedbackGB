| Gate 3 — сервис/API | Локально есть чистая модель и read-only loader **одного дня** | Нет многодневной SQL-агрегации, API, авторизации маршрутов, пагинации и контрактных тестов. Код чтения не вызывается из приложения. Не начат как пользовательская функция. |
| Gate 4 — основные экраны | Существующий пилот продукта 121 не удалён | Нет обзорной страницы по всей сети, категорий/позиций и вкладки «Фудкост» в карточке продукта; нет URL-фильтров и E2E новых экранов. |
| Gate 5 — аналитика | Макеты и правила в плане | Матрица, тепловая карта, цели/сценарии не реализованы; цветовые пороги не утверждены. |
| Gate 6 — выпуск | Есть операторский журнал и SQL-readback | Нет Excel, наблюдаемости, staging E2E/нагрузки, feature flag и отчёта Poster↔БД↔API↔UI↔Excel. |

Из 35 проверок плана **локальные unit-проверки и часть D/readback покрыты**, но это не 35/35: T02–T04 и T14 проверены в пределах четырнадцатидневного снимка; T33 подтверждён schema-readback; T34 фактически усилен до 26 точек × 14 дат на момент проверки. T05–T13, T15–T32 и T35 нельзя целиком засчитать без соответствующих API/UI/стенда и граничных данных. Повторный профильный прогон в этом аудите: 5 файлов, **42/42 passed**; typecheck — exit 0; `npm.cmd run build` — exit 0, с прежними lint-warning в `network/absences` и `network/schedules`. Первое выполнение Vitest было остановлено sandbox `spawn EPERM`, повтор с разрешённым дочерним процессом прошёл.

**Решение по следующему шагу:** не запускать новые записи, массовый backfill или показ KPI как готового. Сначала восстановить доступность Poster и получить staging для проверки `EXPLAIN`/нагрузки; отдельно определить допустимую свежесть и способ повторного синка исторических дней. До этого допустимы только локальные исправления синка и тесты без записи в общую базу.

## После восстановления Poster: разрешённое расширение окна

Предыдущее ограничение записи было изменено прямым указанием владельца «делай записи в супабейз и продолжай». Poster снова ответил на read-only запрос 16.09; после одной проверенной записи по магазину выполнен синк 16→10.09, **по одной дате за раз**. Каждая дата прошла 26/26 построчных сверок и отдельную сверку сетевого ответа Poster с SQL БД. Подробности и значения — `docs/FOOD_COST_SYNC_AUDIT_2026-09-24.md`.

Текущий readback 037 за 10–23.09: **364/364** пар дата×магазин, **31 324/31 324** строк `run`↔факты, 0 пропусков, 0 несовпадений, 0 `running`/`failed`, 0 NULL в netto. Сетевые суммы в minor: выручка 963 333 951; `product_profit` 576 635 967; `product_profit_netto` 580 044 742. `supabase/037_foodcost_sales_data_readback.sql` обновлён до 14-дневного окна и успешно выполнен. HTTP 500 больше не блокирует этот конкретный период, но его причина остаётся неизвестной.

**Gate 2 всё ещё частичный:** нет отдельного staging, измеренной нагрузки/`EXPLAIN`, защиты от конкурентного повтора и политики обновления исторических дней. 30 дней не синхронизированы. Gate 3–6 и E2E не объявлять выполненными; включение KPI/UI пока не разрешается одной только полнотой 14-дневного снимка.

В том же этапе устранён **последовательный** лишний повтор: синк сверяет все 15 полей строк как мультимножество с последней завершённой версией и при полном совпадении возвращает `unchanged=true` без INSERT. Проверка 10.09 × магазин 1 на рабочей базе: до повтора 1 run, после повтора 1 run, тот же `run_id`; `unchanged=true`. Локально после правки: 6 профильных файлов, 46/46 тестов, typecheck, ESLint изменённых файлов и production build прошли (в build остались прежние warning в разделах отсутствий/графиков). Это **не** устраняет гонку двух одновременных процессов; для неё нужен отдельный DB-инвариант/транзакционная координация, который нельзя объявить проверенным по этому тесту.
