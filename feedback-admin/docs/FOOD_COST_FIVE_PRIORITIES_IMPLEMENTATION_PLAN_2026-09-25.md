## 0. Цель, границы и фактическая база

Руководитель за 15–30 секунд видит: полноту данных; состояние сети по двум методикам; сравнение с равным предыдущим периодом; где проверять категории и товары; как изменились цены поставок. Подробности доступны одним кликом. Нельзя называть оценочный эффект доказанной прибылью, а закупочную цену — фактическим фудкостом продаж.

На дату плана в нашей админке уже есть `/admin/technologist/food-cost` с вкладками `Огляд`, `Категорії`, `Позиції`, а в карточке товара — `Фудкост`. Есть фильтры 7/14/30/60 завершённых суток Europe/Kyiv, `Уся мережа`/магазин, два фактических показателя Poster и строгая проверка полного набора дата × магазин. Основные файлы: `food-cost/page.tsx`, `food-cost-workspace.tsx`, `food-cost-command-center.tsx`, `src/lib/admin/{foodcostPeriod,foodcostRecentNetwork,foodcostSalesRead,foodcostSalesReadModel,foodcostBands}.ts`. Миграции 036–038 уже существуют; **применённые миграции не редактировать**.

Последняя зафиксированная read-only сверка 25.09 показала 26 завершённых магазинных снимков на каждый день 10–24.09.2026 включительно. Этого достаточно для текущих 7 и 14 дней, но не для 30/60; каждый факт нужно перепроверить на момент выполнения. Для сравнения с прошлым *равным* периодом потребуется до 120 календарных дат истории при выборе 60 дней. Наличие 15 дней сегодня не обещает полноту любого будущего окна.

Источники: продажи — `feedbackgb.foodcost_sales_runs/facts` из `dash.getProductsSales`; постачання — `feedbackgb.poster_supply_cost_runs/documents/averages` из Poster `storage.getSupplies` и `storage.getSupplyIngredients`; текущий каталог и названия — Poster с явной пометкой, когда название не историческое. Все маршруты — только `super_admin`, server-side `service_role`, `no-store`, без сырых фактов и секретов в ответе. Сохраняем AntD 5, `AdminPageContainer`, Inter, токены светлой/тёмной темы и существующую боковую навигацию.

### Инварианты расчёта

- `paid = Σ payed_sum_minor` для ровно тех же `run_id`, товаров, магазинов и дат.
- `FC₁ = (paid − Σ product_profit_minor) / paid × 100`; `FC₂ = (paid − Σ product_profit_netto_minor) / paid × 100`. `FC₂ = Н/Д`, если netto не покрывает весь выбранный набор. При `paid <= 0` оба значения `Н/Д`.
- Сеть, категория, товар и магазин пересчитываются из денежных сумм, **не** из среднего процентов. Разность двух FC — процентные пункты.
- Цвета для каждой методики отдельно: `<35%` зелёный, `35–45%` включительно жёлтый, `>45%` красный. Классифицировать по неокруглённому числу; цвет дублировать текстом. Неполнота/NULL не зеленеют.
- Одинаковый состав текущих Poster-магазинов применяется к обоим сравниваемым окнам. Этот фиксированный набор нельзя подписывать «исторический состав сети»: история членства пока не подтверждена.
- Заказанная ранее закупочная методика 30-дневной средневзвешенной для **карточки рецепта** остаётся независимой. Новая вкладка цен может получать 7/14/30/60-дневные окна, но её числа не заменяют 30-дневную стоимость рецепта и не смешиваются с FC продаж.

## 1. Маршруты и композиция

Сохраняем три существующие вкладки и добавляем `Теплова карта`, отдельную вкладку **`Ціни`**, `Матриця`. Приоритеты 1 и 2 — блоки текущего `Огляд`, а не две лишние вкладки. `Ціни` — каталог закупочных цен сырья и ингредиентов, не таблица готовых продуктов и не их продажных цен. Общий `days=7|14|30|60` и `spot_id=all|ID` сохраняются в URL, где соответствующий срез существует. В `Ціни` выбранный `days` означает **окно накладных**, а не смену рецептурной 30-дневной методики; сравнение — с предыдущим равным окном, когда оно полно. Все глубокие ссылки сохраняют фильтры и дают возврат через Back.

### P2. Очередь проверки на `Огляд`

1. Источник тот же `run_id`-snapshot, что KPI; не делать отдельный live Poster-запрос для карточек очереди.

### P5. Вкладка `Матриця`

1. Из того же полного snapshot получить товарные `paid`, `profit` и обе FC; координата X — выбранный FC%, Y — выбранная прибыль Poster в грн за **тот же период**, размер точки — оплаченная сумма. По умолчанию методика FC₁; переключение FC₂ меняет данные и границы без смены знаменателя.

Если нужен 2×2/3×2 квадрант по «высокой марже», отдельно утвердить порог/правило; до этого показывать scatter и таблицу.
3. Учитывать отрицательную прибыль и FC>100%; оси не обрезают реальные данные молча. Очень малые продажи можно фильтровать пользовательским контролом `Мін. оплачено` с видимым значением и количеством исключений; по умолчанию показывать всё.

## 3. Контракты API и данных для исполнителя

Перед созданием нового маршрута проверить существующие `GET /api/admin/technologist/food-cost/{categories,products}/recent-network` и `GET /api/admin/technologist/products/[id]/food-cost`. Новые маршруты разрешены только для реально нового среза: `/comparison`, `/attention`, `/heatmap`, `/supply-prices`, `/matrix` — имена **предложены, не существуют**. Предпочесть один серверный read model и лёгкие агрегаты поверх выбранных `run_id`; не запускать 5 одинаковых чтений всех фактов на один экран.

Каждый ответ: `status=complete|incomplete|unavailable`, `period.from/to`, `comparison.from/to` (где применимо), `scope.spotIds`, `coverage.current/previous`, `methodologyVersion`, `sourceFetchedAt`, `data` либо `null`, `reasonCode` без внутренних сообщений/SQL. Для закупок отдельные `source=poster_supplies`, `unit`, `supplyWindow`, `documentCoverage`. Валидация `days`, `spot_id`, `category_id`, сортировки, пагинации и количества ID до запроса. `Cache-Control: no-store`; `401/403` до чтения данных; `503 schema_missing` при отсутствии нужной миграции. Браузер не получает service key, raw `lines` или PIN.

При выборе метода и фильтров сохранять `days`, `spot_id`, `method`, `category_id` в URL только как несекретные значения; не сохранять персональные данные. Чтение предыдущего периода не меняет текущие цвета: статус FC относится к текущему периоду, дельта имеет отдельный знак и текст. Синк дневных продаж по-прежнему обновляет короткое скользящее окно; исторический backfill — отдельный согласованный процесс с чекпоинтами, идемпотентностью и лимитами.

## 6. Передача Luna 6 и правила приёмки

Luna 6 выполняет **один gate за раз**: G0 → P1 → P2 → P3 → P4 → P5. После каждого этапа — diff-review, typecheck, адресные и полные тесты, локальный браузер, фактический readback. Следующий этап не начинается при проваленном критическом gate. В отчёте отдельные строки `код`, `тесты`, `реальная БД`, `Poster`, `локальный E2E`, `Preview`; отсутствие проверки — `blocked/not started`, не «готово».

Обязательные ограничения для исполнителя: не редактировать другие репозитории, применённые миграции или `public`; не менять рабочую БД без отдельного разрешения; не коммитить чужие изменения; не пушить/деплоить без запроса владельца; не выводить секреты. Если стадий нет, тесты конкурентной записи и backfill не переносить на общую рабочую БД автоматически. Любая новая миграция — forward-only SQL + readback + права + план отката, переданная владельцу для ручного применения. Финальная сдача — список реально работающих вкладок, ссылки/скриншоты, статусы всех тестов и открытые ограничения по покрытию 30/60 и предыдущим периодам.
