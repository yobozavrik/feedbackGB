# Фудкост в админ-панели: план внедрения и макеты

Статус: **план, не реализация**. Дата: 24.09.2026. Область: `feedback-admin`, раздел **Технолог → Фудкост**, существующий каталог **Технолог → Продукти**. Язык интерфейса — украинский. Числа в макетах ниже иллюстративны, не являются данными Poster.

## 1. Цель и границы

Администратор должен видеть **две отдельные методики** фактического фудкоста продаж по сети, магазину, категории и продукту; отдельно — плановый фудкост по текущей цене и себестоимости Poster; отдельно — норматив техкарты и средневзвешенную стоимость её компонентов по накладным за последние 30 календарных дат. Переход с общей страницы на категорию и продукт должен сохранять период, магазин и обе методики.

**Не смешивать четыре величины:**

| Название в UI | Источник | Что означает | Частота |
|---|---|---|---|
| `Фудкост за прибутком товарів` | `dash.getProductsSales.product_profit` | `(Σ payed_sum − Σ product_profit) / Σ payed_sum × 100`; не равен колонке `Прибуток` отчёта Poster | Снимок завершённых продаж |
| `Фудкост за прибутком без ПДВ Poster` | `dash.getProductsSales.product_profit_netto` | `(Σ payed_sum − Σ product_profit_netto) / Σ payed_sum × 100`; за 23.09.2026 сеть расходится с чековым отчётом на 0,01 ₴ | Снимок завершённых продаж |
| `Плановий фудкост за прайсом` | Текущие `menu.getProduct`/цены по точкам | Текущая себестоимость Poster / текущая цена меню | Poster live при открытии продукта |
| `За техкартою Poster` | `menu.getProduct`/`menu.getPrepack` | Сумма стоимости ингредиентов рецепта, не фактический фудкост | Poster live при открытии продукта |
| `За накладними · 30 днів` | Существующий полный снимок накладных в `feedbackgb` | Средневзвешенная закупочная цена ингредиента, умноженная на расход по рецепту | После полного синка; не стоимость остатка |

Фудкост ≠ себестоимость. `product_profit_netto` означает прибыль без НДС в терминологии Poster, **не** чистую прибыль бизнеса. Две методики используют один знаменатель `payed_sum`, но разные поля прибыли; расхождение должно быть показано числом и объяснено в UI на каждой из трёх ступеней. Отсутствующий компонент ≠ нулевая цена. Прогнозный эффект изменения цены ≠ обещанная прибыль. Никаких новых объектов в `public`.

## 2. Навигация и экранный контракт

Сохраняем пункт сайдбара **Технолог → Фудкост**. Внутри раздела:

1. **Огляд** — единственная главная страница: период, магазин, дата обновления; обе карточки фактического фудкоста рядом с одним знаменателем/выручкой и объяснением разницы; линия обеих методик по дням/неделям; вклад категорий в выручку и маржу; таблица проблемных категорий/продуктов. Никаких автоматических AI-утверждений о причинах.
2. **Категорії** — карточки/таблица категорий с двумя фактами, их разницей, изменением к сопоставимому периоду, покрытием данных; клик ведёт на страницу категории.
3. **Позиції** — поиск и сортировка всех продуктов, пагинация на сервере; обе методики в каждой строке, текущие/предыдущие данные, в том числе позиции только одного периода.
4. **Матриця** — интерактивный scatter: X = фактический фудкост %, Y = валовая маржа за период, размер точки = выручка. Пороговые линии стоят в реальных значениях шкал, не в центре рисунка. Пороги задаются утверждённой политикой.
5. **Теплова карта** — строки = категории (режим «магазины» при выборе категории), столбцы = дни или недели; цвет = фактический фудкост относительно утверждённой цели. `Н/Д` отдельным нейтральным состоянием; в tooltip числитель, знаменатель, охват и дата снимка. Без продаж — не `0%`.
6. **Цілі та сценарії** — утверждённые цели, сравнение факта с целью, сценарный пересчёт цены/объёма. Кнопка «Сохранить решение» только после отдельного согласования бизнес-процесса и аудита; цен в Poster автоматически не меняем.

Страница категории: хлебные крошки → заголовок и оба агрегата → объяснение разницы → линия динамики → таблица продуктов с обеими колонками → карта дней/магазинов. Карточка продукта: существующая карточка каталога, добавить вкладку **«Фудкост»**; там оба факта за период/магазин рядом, их разница и объяснение; план по прайсу, себестоимость Poster, техкарта и накладные в раздельных блоках, динамика и таблица по магазинам. Ссылка из таблиц раздела ведёт именно в эту карточку и сохраняет фильтры в URL.

### Общие правила интерфейса

- Период (`7 / 14 / 30 дней / выбранный диапазон`) и магазин (`Вся мережа` по умолчанию) находятся в верхней панели; дата, часовой пояс `Europe/Kyiv` и полнота снимка видны рядом.
- Один набор фильтров для всех вкладок; значения в URL. При переключении вкладок они не теряются. Смена методики не скрывается под тем же названием KPI.
- Светлая и тёмная темы используют токены AntD. Цвет не единственный носитель смысла: рядом с цветом — знак, значение или `Н/Д`. Таблицы доступны с клавиатуры и не теряют читаемости на 1280/1024/390 px.
- Если источник не обновился, блок показывает **время последнего успешного снимка и статус**; старые данные не маркируются как live. Ошибка одного источника не обнуляет остальные блоки.
- Рядом с обеими цифрами на общей странице, странице категории и карточке продукта показывать одно объяснение: «Виторг і період однакові. Перший показник віднімає `product_profit`, другий — `product_profit_netto`; Poster описує netto як прибуток без ПДВ. Тому відсотки різні. Це не два різні обсяги продажів і не бухгалтерськи підтверджена собівартість». В tooltip раскрыть суммы выручки и обоих полей прибыли; не приписывать разницу только НДС без проверки налоговых настроек аккаунта.
- Категории и продукты без продаж остаются видимыми в соответствующих списках как «Без продаж», а не исчезают. Удалённые/архивные объекты с историческими продажами сохраняются в историческом разрезе.

## 3. Контракт показателей — обязательный gate до разработки UI

| Метрика | Предлагаемая формула | Проверка/открытый вопрос |
|---|---|---|
| Выручка фактическая | `Σ payed_sum / 100` | Сопоставить с отчётом Poster по тем же точкам/датам; отдельно проверить скидки, бонусы, сертификаты, возвраты |
| Прибыль товарного API | `Σ product_profit / 100` | За 23.09.2026 совпала с `Σ total_profit` чеков, но **не** с колонкой `Прибуток` UI. Не выдавать за прибыль отчёта Poster. |
| `Прибуток` отчёта Poster | `Σ total_profit_netto / 100` на уровне чеков; товарный кандидат `Σ product_profit_netto / 100` | За 23.09.2026 чеки совпали с Excel точно (`449 621,80 ₴`); товары ниже на 0,01 ₴. Название `netto` в API — без НДС, а не обязательно чистая прибыль бизнеса. |
| Себестоимость продаж — кандидат | `выручка − выбранная прибыль` | Выбор gross/netto должен быть явным; разность с `total_profit_netto` нельзя автоматически называть бухгалтерской себестоимостью. Отрицательные значения не скрывать. |
| Фудкост за прибутком товарів | `(Σ payed_sum − Σ product_profit) / Σ payed_sum × 100`, если знаменатель > 0 | На 23.09.2026 сеть: `39,17%`; не маркировать как совпадающий с колонкой `Прибуток` UI |
| Фудкост за прибутком без ПДВ Poster | `(Σ payed_sum − Σ product_profit_netto) / Σ payed_sum × 100`, если знаменатель > 0 и netto присутствует во всех строках | На 23.09.2026 сеть: `38,80%`; сеть товарных строк против отчёта чеков отличается на 0,01 ₴. Не подставлять нуль вместо отсутствующего netto |
| Изменение | `текущий % − предыдущий %` в процентных пунктах | Для сопоставимых полных периодов, одинаковых точек и определений |
| Цена фактической реализации | `Σ payed_sum / Σ count` при совместимых единицах | Отдельно от цены прайса, особенно для весового продукта |
| План по прайсу | `product.cost / menu.price × 100` после проверки единицы веса и точки | Поле `cost` продукта может быть общесетевым, цена — по магазину |
| Цена ингредиента по накладным | `Σ сумма строк / Σ количество` внутри `ingredient_id + unit` | Только полный 30-дневный снимок; не усреднять средние по документам |

**Решение владельца 24.09.2026:** использовать и показывать **обе методики** на главной странице, по категории и по продукту с объяснением их различия. Ни одна не подменяет другую; один общий знаменатель. Фактическая сверка 23.09.2026: выручка `734 622,99 ₴`, `Σ product_profit=446 839,43 ₴`, UI `Прибуток=Σ total_profit_netto=449 621,80 ₴`, `Σ product_profit_netto=449 621,79 ₴`. Экспортная скидка `425,40 ₴` арифметически равна `Σ discount` товарного API `423,34 ₴` минус `Σ round_sum` чеков `-2,06 ₴`; внутреннее правило Poster не подтверждено. **Ещё не утверждены:** целевые проценты/цветовые пороги, трактовка бонусов/сертификатов, возвратов и применение выведенной разности как бухгалтерской себестоимости. До этих решений UI показывает проверенные фактические значения без оценочного красного/зелёного статуса.

## 4. Источники, хранение и производительность

1. Продажи: `dash.getProductsSales` c `date_from/date_to` и `spot_id`. Проверить реальный ответ на одном дне/магазине, модификаторах, возвратах и закрытии дня. Если API агрегирует не на нужном зерне — не строить дневную карту из недельного агрегата.
2. Справочники: действующие `v_products`/категории плюс Poster ID; сопоставление по `product_id`, не по названию. Snapshot имени/категории в историческом факте для переименований. Не терять удалённые продукты.
3. Прайс/рецепт: существующие серверные функции Poster live; для широких таблиц не делать вызов `menu.getProduct` на каждый ряд при загрузке главной. Детали — по открытию карточки.
4. Накладные: переиспользовать `poster_supply_cost_runs/documents/averages`; доля покрытия и «нет цены» по компонентам. Не копировать top-40-метод из внешнего проекта.
5. Для сети по дням и магазинам исследовать квоты и стоимость API: потенциально `магазины × дни` вызовов. Синхронизация — фоновая, порционная, с checkpoint, retry/backoff и явным `completed` только при полной сверке. UI не ждёт сотни вызовов Poster.
6. Новая **forward-only** миграция после проверки текущего номера (на 24.09.2026 следующая свободная — `037`), только `feedbackgb`: `foodcost_sales_runs` (период, список точек, статус, counts, checksum/версия методики, timestamps, ошибка без токена), `foodcost_sales_facts` (run, дата по Киеву, точка, продукт, модификация, сырые суммы в minor units, count/unit, category snapshot). Уникальный ключ и индексы — после проверки реального grain API; не придумывать `UNIQUE(product_id,date)` до проб.
7. Уникальность и идемпотентность: повтор того же завершённого окна не удваивает факт; неполный run не виден как полный; исправление прошлого периода оформляется новой версией снимка или атомарной заменой с audit trail. Индексы по `(business_date, spot_id)`, `(product_id, business_date)`, `(category_id, business_date)` — уточнить `EXPLAIN` на staging.
8. RLS и ACL как у 036: `service_role` только для таблиц синка, никакого `anon/authenticated`, никакого `public`. Новые API только для разрешённых админских ролей, проверка на сервере на **каждом** маршруте, включая Excel; токен Poster никогда не выходит в клиент/логи.
9. Server response — компактные агрегаты и страницы списка, не тысячи сырых Poster-строк в RSC. Экспорт строится с сервера на зафиксированном snapshot/периоде и содержит методику, источник и дату актуальности.

3. **Gate 0:** базовые unit/typecheck/build и существующий пилот проходят; baseline и доказательства записаны. При падении — сначала разобрать его, не маскировать новой функцией.

### Этап 1. Семантика продаж и API-пробы

4. Сверить 1 полный день, 1 магазин, 1 весовой и 1 штучный продукт с интерфейсом Poster; записать raw-поля (без токена), единицы и итог. Отдельно — бонусы/скидки/возвраты.
5. Проверить повторяющиеся `product_id` с разными `modification_id`; сформулировать ключ агрегирования. Проверить продукт только в предыдущем периоде и только в текущем.
6. Утвердить определение KPI, сравнимого периода и гранулярности; оформить ADR/таблицу решений. **Gate 1:** независимый ручной расчёт сходится с Poster на выбранных случаях или расхождение объяснено, показано владельцу и KPI не запускается до решения.

### Этап 2. БД и синк продаж

7. Создать отдельную forward-only миграцию в `feedbackgb`; schema-only staging readback: таблицы, индексы, RLS, ACL, отсутствие `public`. Ничего не менять в применённых 031–036.

### Этап 5. Аналитические представления

17. Матрица с реальными осями и пороговыми линиями, легендой и таблицей как доступной альтернативой. Не строить оценочный квадрант до утверждения порогов.

20. **Gate 5:** пороги и цвета соответствуют данным, `Н/Д` отдельно, нет ложных причин изменений, дублирующих/противоречивых KPI.

### Этап 6. Excel, наблюдаемость, выкладка

21. Экспортировать только проверенные данные активного snapshot: отдельные листы `Огляд`, `Категорії`, `Позиції`, `Магазини`, `Методика`; UTF-8/украинские заголовки, minor→UAH один раз, период/фильтр/источник/время в файле. Тестировать readback `.xlsx` и суммы.
22. Логировать `request_id`, endpoint, snapshot/run, длительность, количество Poster-вызовов, класс ошибки и покрытие без PIN/токена/персональных полей. Метрики: длительность sync/API, completeness, staleness, Poster 429/5xx, расхождения сверки.
23. Staging: миграция → синк малого окна → полный период → E2E → нагрузка на фильтры/экспорт → readback → только потом Production. Preview со общей рабочей базой **не использовать для записи/синка**.
24. Публикация под feature flag; сначала супер-админ и один период. Мониторить снимки, API и браузерные ошибки; затем расширять доступ только после решения владельца. Откат кода — вернуть пилот; таблицы оставить для расследования, не `DROP` в панике.
25. **Gate 6:** отчёт с версиями кода/миграции, командами, выводом, E2E-видео/скриншотами, сверкой Poster↔БД↔UI, нагрузкой и известными ограничениями. Без этого «готово» не писать.

## 6. Тест-матрица (минимум перед выпуском)

`U` — unit, `I` — интеграционный/контрактный, `E` — браузерный E2E, `D` — БД/readback.

| ID | Проверка | Уровень | Ожидаемо |
|---|---|---|---|
| T01 | Minor units → грн только один раз | U | Точный пример 12345→123,45 ₴ |
| T02 | Сеть = сумма магазинов по одному snapshot | D/I | Суммы равны |
| T03 | Взвешенный FC из сумм, не среднее процентов | U | Формула совпадает вручную |
| T04 | Несколько `modification_id` одного продукта | U/I | Все строки учтены один раз |
| T05 | Продукт только в прошлом периоде | U/I | Видим в сравнении, не пропал |
| T06 | Продукт только в текущем периоде | U/I | `prev = Н/Д`, не ложные −100% |
| T07 | Пустой/нулевой знаменатель | U/E | FC = `Н/Д`, не `0%`/Infinity |
| T08 | Отрицательная маржа/возврат | U/I | Данные сохранены, знак виден |
| T09 | Скидка, бонус, сертификат | I | Результат сверён с Poster по ADR |
| T10 | Весовой товар и штучный товар | U/E | Единицы и цена за 100 г/1 кг/шт корректны |
| T11 | 30-дневная средневзвешенная накладных | U/D | Пересчёт по всем строкам совпал |
| T12 | Отсутствует 1 ингредиент в закупках | U/E | Общий закупочный итог `Н/Д`, не частичная сумма |
| T13 | Неполный/устаревший снимок | I/E | Явное предупреждение, нет метки live |
| T14 | Повторный sync того же окна | D | Нет дублей/двойной суммы |
| T15 | Падение посередине sync + retry | D/I | Не опубликован `completed` до полной сверки |
| T16 | Граница суток Europe/Kyiv/летнее время | U/D | Нет сдвига на день |
| T17 | Разный состав магазинов двух периодов | I/E | Сопоставимость обозначена |
| T18 | Категория переименована/продукт архивирован | I/E | История не потеряна |
| T19 | Матрица: линии порогов в значениях осей | E | Цвет/квадрант и точка согласованы |
| T20 | Heatmap: ячейка без продаж | E | Нейтральное `Н/Д`, не зелёное/0 |
| T21 | Tooltip heatmap и drill-down | E | Значение, магазин, дата, источник совпадают |
| T22 | Фильтры в URL и переход в категорию/продукт | E | Период/магазин сохранены |
| T23 | Существующие вкладки продукта | E | Фото, остатки и техкарта без регрессий |
| T24 | Доступ без сессии / обычной роли | I/E | 401/redirect или 403 без данных |
| T25 | Все новые API, включая Excel | I | Одинаковая проверка роли |
| T26 | Неисправный параметр даты/ID, слишком длинный диапазон | I | 400, без дорогих Poster-вызовов |
| T27 | Токен Poster в HTTP/log/Excel | I | Не обнаружен |
| T28 | Excel readback, листы/итоги/время | I | Совпадает с UI/snapshot |
| T29 | 390/1024/1440 px, обе темы | E | Нет обрезки, оси и цифры читаемы |
| T30 | Клавиатура/фокус/описание цветов | E | Основные сценарии доступны без мыши |
| T31 | Poster 429/5xx и частичный отказ | I/E | Retry ограничен, понятная ошибка, без подмены |
