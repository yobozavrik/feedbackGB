# План исправлений: чтобы всё работало штатно

**Дата:** 2026-09-15
**Принцип:** просто и надёжно. Не трогаем то, что работает. Ничего не улучшаем «на будущее».

---

## Коротко

1. **Сегодня** — вернуть смену PIN в админке и запретить трогать рабочую базу без разрешения.
2. **Вход по PIN не меняем.** Новый вход откладываем, из релиза его убираем.
3. **Фотоотчёт** выпускаем в том виде, в каком он уже сделан: включаем после проверки на нескольких телефонах.
4. **Первую неделю** раз в день смотрим одну цифру: всё ли фото на месте.

## Этап 1. Сегодня: убрать поломку

### Шаг 1. Вернуть смену PIN в админке

**Что сломано.** В админке не получается сменить PIN сотруднику или создать сотрудника с PIN.

**Почему.** Сегодня в рабочей базе «выключили» старый способ смены PIN, а сайт умеет менять PIN только им.

**Что сделать.** Вернуть старый способ одной командой в базе — ровно в том виде, в каком он работал утром. Вход эта команда не затрагивает.

<details>
<summary>Для разработчика: команда</summary>

Выполнить в рабочей базе **только после письменного «да» владельца**:

```sql
create or replace function feedbackgb.set_user_pin(p_user_id uuid, p_pin text)
returns void
language plpgsql
security definer
set search_path = feedbackgb, extensions, household_chemicals, public, pg_catalog
as $$
declare
  collision_user uuid;
begin
  if p_pin !~ '^\d{6}$' then
    raise exception 'PIN must be exactly 6 digits';
  end if;

  select id into collision_user
    from feedbackgb.users
   where is_active
     and pin_hash is not null
     and id <> p_user_id
     and pin_hash = crypt(p_pin, pin_hash)
   limit 1;

  if collision_user is not null then
    raise exception 'PIN collision: this PIN is already used by user %', collision_user
      using errcode = 'unique_violation';
  end if;

  update feedbackgb.users
     set pin_hash = crypt(p_pin, gen_salt('bf', 10)),
         failed_attempts = 0,
         locked_until = null
   where id = p_user_id;

  if not found then
    raise exception 'user % not found', p_user_id;
  end if;
end $$;
```

Это тело функции из `017_fix_pgcrypto_search_path.sql`, одно в одно. Закрепить то же самое в репозитории файлом `027_restore_set_user_pin.sql`, чтобы код и база не расходились.

Остальное, что добавили сегодня (колонка `pin_lookup`, новые функции), **не удалять**: старый сайт ими не пользуется, они ничему не мешают.

</details>

**Готово, если:**
- в админке сменили PIN тестовому сотруднику — ошибки нет;
- тестовый сотрудник вошёл с новым PIN;
- продавец с прежним PIN входит как раньше.

### Шаг 2. Отключить тестовые сайты от рабочей базы

**Что не так.** Каждый раз, когда команда отправляет код, Vercel сам собирает тестовую версию сайта, и она подключена к **настоящей** базе. Поэтому тестовые действия попадают в рабочие данные — так появились 4 фотоотчёта.

**Что сделать.** В настройках Vercel у обоих проектов убрать тестовые версии (Preview) из доступа к базе. Тестовые сайты перестанут работать с данными — так и нужно.

<details>
<summary>Для ответственного за сервера</summary>

В проектах `app.feedback.gb` и `admin.feedback-gb`: Settings → Environment Variables. У переменных `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SESSION_SECRET` снять галочку **Preview**, оставить только **Production**.

</details>

**Готово, если:** в списке переменных обоих проектов напротив этих четырёх стоит только Production.

---

### Шаг 3. Закрыть доступ к рабочей базе

**Что не так.** За сегодня в рабочую базу трижды внесли изменения, хотя в отчётах было написано, что её не трогали.

**Что сделать.** Доступ на изменение рабочей базы оставить одному ответственному. Остальным — только просмотр или вообще без доступа.

**Готово, если:** владелец знает поимённо, у кого есть право менять рабочую базу, и таких людей не больше двух.

## Этап 2. Вход по PIN не трогаем

### Шаг 4. Убрать из релиза изменения входа

**Решение.** Вход работает, и 53 продавца им пользуются. Новый вход откладываем. В релиз идёт **только фотоотчёт**.

**Почему так можно.** Старый вход медленный: одна попытка нагружает базу примерно на 4 секунды. Но продавцы входят редко — сессия живёт долго. Для 26 магазинов этого хватает. К новому входу вернёмся, если магазинов станет заметно больше.

<details>
<summary>Для разработчика</summary>

В ветке `codex/photo-report` вернуть файлы входа к состоянию до переделки (коммит `892e0e2`):

```bash
git checkout 892e0e2 -- \
  feedback-app/src/app/api/auth/login/route.ts \
  feedback-admin/src/app/api/auth/login/route.ts \
  feedback-admin/src/app/api/admin/users/route.ts \
  "feedback-admin/src/app/api/admin/users/[id]/pin/route.ts" \
  shared/lib/rateLimit.ts \
  feedback-app/src/lib/__tests__/login-route.test.ts \
  feedback-admin/src/lib/__tests__/login-route.test.ts \
  feedback-admin/src/lib/__tests__/users-rbac.test.ts
git rm shared/lib/pinLookup.ts
```

Убрать `PIN_PEPPER` и `PIN_LOOKUP_LEGACY_FALLBACK` из обоих `.env.example`. Миграции `025` и `026` не применять ни к одной среде повторно и пометить в шапке файлов: «отложено, не применять».

Проверка:

```bash
git diff 892e0e2 -- feedback-app/src/app/api/auth feedback-admin/src/app/api/auth \
  feedback-admin/src/app/api/admin/users shared/lib/rateLimit.ts
# вывод должен быть пустым
```

Затем `npm test` и `npx tsc --noEmit` в обоих приложениях — без ошибок.

</details>

**Готово, если:** разработчик прислал пустой вывод проверки и зелёные тесты.

## Этап 3. Фотоотчёт

Всё нужное уже сделано:
- отчёт сохраняется целиком или не сохраняется совсем — половинчатых не бывает;
- если что-то сорвалось, лишние файлы удаляются;
- не-фото (подделки под картинку) не принимаются;
- в админке видно по дням: какой магазин отправил, сколько фото, кто и когда, и сами фото.

Функция закрыта выключателем: пока его не включили, продавцы её не видят.

**Что сделать.** Выложить новую версию сайта и админки. Фотоотчёт при этом **выключен**. Для людей ничего не меняется.

### Шаг 6. Проверить фотоотчёт на живых телефонах

**Что сделать.** В нерабочее время включить фотоотчёт и отправить 4–5 отчётов по 15 фото с разных телефонов. Нужны минимум iPhone и Android, оба через Telegram.

**Что проверить глазами:**

| Проверка | Нормально, если |
| --- | --- |
| Выбрать 15 фото | телефон не зависает, видно «15/15» |
| Отправить | за время до 30 секунд пришло «спасибо» |
| Выбрать 16-е фото | не даёт, пишет про лимит |
| Отправить без фото | не даёт, просит добавить фото |
| Выключить интернет и отправить | пишет, что сохранено и отправится позже |
| Админка → Фото звіт → сегодня | магазин «Надіслав», число фото совпадает |
| Открыть фото в админке | все фото открываются |

<details>
<summary>Для разработчика: проверка, что ни одно фото не потерялось</summary>

Выполнить после проверки (запрос только читает):

```sql
with refs as (
  select 'sb:' || o.name as storage_ref from storage.objects o
   where o.bucket_id = 'feedback-photos'
), db_refs as (
  select jsonb_array_elements_text(f.fields->'photo_urls') as ref
    from feedbackgb.feedback f where jsonb_typeof(f.fields->'photo_urls') = 'array'
  union
  select f.photo_url from feedbackgb.feedback f where f.photo_url is not null
)
select
 (select count(*) from refs r
   where not exists (select 1 from db_refs d where d.ref = r.storage_ref)) as lishnie_faily,
 (select count(*) from db_refs d where d.ref like 'sb:%'
     and not exists (select 1 from refs r where r.storage_ref = d.ref))  as poteryannye_foto;
```

Сегодня утром было `lishnie_faily = 2` (старые файлы от 1 мая), `poteryannye_foto = 0`. После проверки `lishnie_faily` должно остаться 2, `poteryannye_foto` — 0.

Как включить и выключить: в Vercel у `app.feedback.gb` добавить `PHOTO_REPORT_ENABLED=true` (Production) и сделать Redeploy. Выключить — удалить переменную и снова Redeploy.

</details>

**Готово, если** все строки таблицы в норме, а разработчик прислал результат запроса: потерянных фото 0.

После проверки владелец решает: удалить тестовые отчёты (разработчик присылает список, удаляет после «да») или оставить.

## Этап 4. Первая неделя

Раз в день — одна минута:

1. Админка → «Фото звіт» → сегодня: сколько магазинов отправили.
2. Разработчик раз в день запускает запрос из шага 6 и пишет в чат две цифры.

**Когда срочно разбираться:**
- `poteryannye_foto` больше 0;
- продавцы жалуются, что не могут войти;
- магазин отправлял, а в админке его нет.

Если что-то из этого случилось — выключить фотоотчёт (удалить переменную, Redeploy) и разбираться. Вход и остальные заявки при этом продолжают работать.

| Что | Почему можно подождать | Когда вернуться |

| Новый быстрый вход по PIN | 26 магазинов старый вход выдерживает | если магазинов станет больше 60 или начнутся жалобы на вход |
