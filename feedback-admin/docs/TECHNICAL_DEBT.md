# Технический долг feedback-admin

Документ фиксирует подтверждённые ограничения, которые сознательно не устраняются в текущей итерации. Это не список идей: у каждого пункта должны быть фактическое основание, риск и критерий закрытия.

## TD-001 — Ночной импорт чеков обрабатывает не более одного пропущенного дня

- **Дата фиксации:** 30.09.2026.
- **Область:** `GET /api/cron/poster-receipts`, `posterReceiptNightlyWorker`.
- **Статус:** открыто; отложено владельцем проекта.
- **Факт:** worker проверяет семь завершённых киевских дней от старого к новому, но после первого `claimed` прекращает поиск и импортирует только один день за один запуск.
- **Текущее состояние данных на момент фиксации:** 28.09.2026 прошёл `audit_poster_receipt_day` (`2188` чеков, `4624` строки, `618` клиентов, ошибок целостности `0`); 29.09.2026 имеет статус `missing`.
- **Расписание:** `20 3 * * *` — 03:20 UTC; 06:20 по Киеву при UTC+3 и 05:20 при UTC+2.
- **Риск:** если перед первым запуском существует отставание, ежедневный импорт одного дня не догоняет источник, потому что каждый день появляется ещё один новый завершённый день. Аналитика чеков сохраняет постоянный лаг.
- **Временное правило:** UI и API обязаны показывать фактическую coverage и не строить итог по неполному периоду. `missing` нельзя превращать в ноль.
- **Варианты закрытия:**
  1. разово дозагрузить накопившиеся дни отдельным bounded backfill;
  2. разрешить cron обрабатывать до двух дней за запуск при сохранении lease, deadline и пост-аудита;
  3. временно добавить второй ночной запуск до ликвидации backlog.
- **Критерий закрытия:** два последовательных завершённых дня после ночного окна имеют `verified`; повторный запуск идемпотентен; параллельный запуск не создаёт второй accepted run; тесты timeout/lease/audit проходят; Production-логи не содержат raw чеков, клиентов или секретов.

## TD-002 — Настроить и проверить Telegram-доставку коммунальных показаний

- **Дата фиксации:** 07.10.2026.
- **Область:** `GET /api/cron/utility-dispatch`, переменная `TELEGRAM_UTILITY_CHAT_ID`.
- **Статус:** открыто; владелец отложил Telegram до завершения приложения и админки. 08.10.2026 владелец указал рабочую группу Telegram с ID `-5364085383` как адресат показаний. Принадлежность ID нужной группе и доступ бота ещё не проверены; server env не настроен.
- **Факт:** worker нового модуля требует отдельный `TELEGRAM_UTILITY_CHAT_ID`. Без него возвращает `503 utility_telegram_not_configured`; fallback на чат обычного фотозвіту отсутствует. Флаг `UTILITY_READINGS_ENABLED` не включён. Приложение и админка могут работать с Supabase отдельно; cleanup использует флаг админки. В админке вкладка доставки скрыта до настройки worker и chat ID.
- **Риск:** сохранённые в Supabase пакеты не будут пересланы бухгалтеру, пока адресат не настроен и не проверен. Задачи `pending` накопятся; перед включением worker нужно решить, отправлять ли старые версии и как избежать неожиданной массовой рассылки. Указывать произвольный или старый чат нельзя.
- **Критерий закрытия:** бот добавлен в указанную группу с нужными правами; ID задан как server env `TELEGRAM_UTILITY_CHAT_ID` в нужном деплое; принято решение по накопленной очереди `pending`; тестовый пакет доставлен именно в эту группу со всеми фото; `message_ids` и статус `sent` прочитаны из БД. ID не прописывать константой в коде, токен не записывать в репозиторий.

## TD-003 — Не завершена эксплуатационная наблюдаемость «Надати показники»

- **Дата фиксации:** 07.10.2026.
- **Область:** seller/admin API нового модуля, загрузка фото, Telegram worker и cleanup.
- **Статус:** частично реализовано локально; staging и алерты открыты. Контракт описан в `docs/UTILITY_PHOTO_REPORT_TECHNICAL_DOCUMENTATION_2026-10-07.md`, раздел 7.
- **Факт:** seller/admin API и cron возвращают `x-request-id` и пишут безопасные JSON-события; upload связывается с подачей по `client_submission_id`; cleanup считает `failed`. `utility_events` фиксирует бизнес-факты, Telegram job хранит состояние и message IDs. Клиентское сжатие, зависший `sending`, `uncertain` и возраст очереди ещё не имеют проверенного мониторинга.
- **Риск:** без корреляции по маршруту трудно отличить отказ загрузки, сбой RPC, потерянный ответ Telegram и сиротский Storage-объект. `sending` с истёкшим lease не восстанавливается автоматически; необдуманный повтор может создать дубль в чате.
- **Критерий закрытия:** безопасные события на ошибках upload/RPC/review/claim/send/ledger/cleanup проверены в staging; секреты, фото, комментарии и signed URL не попадают в лог; по job ID можно восстановить путь от подачи до подтверждённой или неопределённой доставки. Алерт по `uncertain`, зависшему `sending`, `ok:false` и ошибкам cleanup назначен ответственному.

## TD-004 — Аудит безопасности репозитория не завершён

- **Дата фиксации:** 07.10.2026.
- **Область:** репозиторий FeedbackGB, маршруты приложения и админки, cron, доступ к Supabase и локальные материалы, которые можно случайно добавить в Git.
- **Статус:** открыто; выполнены чтение исходников и сканирование Gitleaks, но независимая проверка находок и безопасные изолированные тесты ещё не выполнены.
- **Факт:** в ходе этого аудита production и Supabase не затрагивались; тесты приложения не запускались. Сам аудит до этой записи не менял репозиторий, не создавал коммит и не выполнял push. Это не отменяет отдельную ранее выполненную владельцем установку миграций 056/057 в production и последующий read-only readback.
- **Кандидаты для проверки:** роль из 14-дневного cookie может оставаться действительной после деактивации или понижения администратора. На момент исходного аудита `shared/lib/cronAuth.ts` при отсутствии `CRON_SECRET` в production принимал заголовок `x-vercel-cron: 1`; позже этот проход убран в исходном коде, а локальные тесты обоих приложений проверили отказ. Деплой и фактическая конфигурация production не проверены. Охват всех маршрутов и последствия устаревшей роли требуют независимой проверки; их нельзя считать окончательно доказанными находками.
- **Дополнительные факты:** `.env`-файлы игнорируются Git, но `poster_knowledge_base/`, `docs/architecture/` и `feedback-admin/.playwright-cli/` не игнорируются. Сканирование истории обнаружило совпадения по внутренним названиям схем и адресам инфраструктуры; совпадений по ключам или паролям сканер в истории не выдал. Это не доказывает, что секретов в репозитории нет.
- **Риск:** можно ошибочно объявить репозиторий безопасным, пропустить обход контроля доступа или случайно добавить локальные материалы в коммит.
- **Критерий закрытия:** для каждого кандидата есть независимая проверка исходного пути и результата, безопасный локальный тест в изоляции либо явно зафиксированная внешняя причина невозможности проверки; проверены фактические условия production без раскрытия значений секретов; завершены обзор маршрутов и зависимостей, проверка неотслеживаемых материалов и повторное сканирование Git. Итоговый отчёт отделяет подтверждённые находки от гипотез и непроверенных областей.
