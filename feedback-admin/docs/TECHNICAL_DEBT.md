# Технический долг feedback-admin

Документ фиксирует подтверждённые ограничения, которые сознательно не устраняются в текущей итерации. Это не список идей: у каждого пункта должны быть фактическое основание, риск и критерий закрытия.

## TD-001 — Ночной импорт чеков обрабатывает не более одного пропущенного дня

- **Дата фиксации:** 30.09.2026.
- **Область:** `GET /api/cron/poster-receipts`, `posterReceiptNightlyWorker`.
- **Статус:** открыто; отложено владельцем проекта.
- **Факт:** worker проверяет семь завершённых киевских дней от старого к новому, но после первого `claimed` прекращает поиск и импортирует только один день за один запуск.
- **Текущее состояние данных на момент фиксации:** 28.09.2026 прошёл `audit_poster_receipt_day` (`2188` чеков, `4624` строки, `618` клиентов, ошибок целостности `0`); 29.09.2026 имеет статус `missing`.
- **Расписание:** `20 3 * * *` — 03:20 UTC; 06:20 по Киеву при UTC+3 и 05:20 при UTC+2.
- **Риск:** если перед первым запуском существует отставание, ежедневный импорт одного дня не догоняет источник, потому что каждый день появляется ещё один новый завершённый день. Аналитика чеков сохраняет постоянный лаг.
- **Временное правило:** UI и API обязаны показывать фактическую coverage и не строить итог по неполному периоду. `missing` нельзя превращать в ноль.
- **Варианты закрытия:**
  1. разово дозагрузить накопившиеся дни отдельным bounded backfill;
  2. разрешить cron обрабатывать до двух дней за запуск при сохранении lease, deadline и пост-аудита;
  3. временно добавить второй ночной запуск до ликвидации backlog.
- **Критерий закрытия:** два последовательных завершённых дня после ночного окна имеют `verified`; повторный запуск идемпотентен; параллельный запуск не создаёт второй accepted run; тесты timeout/lease/audit проходят; Production-логи не содержат raw чеков, клиентов или секретов.
