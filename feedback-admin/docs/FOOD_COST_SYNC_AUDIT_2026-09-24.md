# Фудкост: синк и проверка Poster → `feedbackgb`

Дата проверки: 24.09.2026. Контур: общая рабочая база Preview/Production, **не staging**. Период данных: 17–23.09.2026, календарные даты Poster/Киева, 26 магазинов из `access.getSpots`. Запись ограничена двумя таблицами миграции 037 в схеме `feedbackgb`: `foodcost_sales_runs`, `foodcost_sales_facts`. UI, API и cron не изменены и не включены.

## Как выполняли

Для каждой пары дата × магазин запускали `scripts/sync-poster-foodcost-sales-day.mjs YYYY-MM-DD SPOT_ID --write`. Скрипт проверяет существование магазина и завершённую дату, получает `dash.getProductsSales`, валидирует все строки, записывает versioned run и факты, сверяет число строк и три суммы из БД и лишь потом помечает run `completed`. Вызовы шли порциями до 4 параллельно, дата за датой; после каждой даты сравнивали сеть с новым прямым ответом Poster. `--verify` заново читает Poster и БД и сравнивает полный набор полей каждой товарной строки как мультимножество, независимо от порядка строк.

Проверка на каждом шаге: сначала 23.09 × магазин «Кварц», затем все 26 магазинов 23.09, затем по одной дате 22→17. Не запускали массовый 30-дневный backfill.

## Обнаружена изменчивость исторической прибыли Poster

Первый синк 17.09 прошёл локальный readback, но следующий Poster-read показал +0,14 ₴ к `product_profit` и +0,12 ₴ к `product_profit_netto` при неизменной выручке. Построчный контроль локализовал изменения в магазинах 1, 5, 6, 7 и 10. Только эти пять точек были повторно синхронизированы новой версией run; старые версии не удаляли. После повторной записи 26/26 точек и сетевые суммы снова совпали.

Позже, после успешной семидневной сверки, один свежий Poster-read диапазона 17–23.09 показал ту же выручку, но прибыль **на 0,12 ₴ и 0,13 ₴ ниже** выбранных снимков. Повторные дневные запросы объяснили разницу изменениями в нескольких исторических датах; это не ошибка сложения БД. Текущие snapshot-значения верны **на зафиксированное время чтения**, но не являются гарантией неизменности Poster. Причина перерасчётов Poster не установлена; не называем её доказанным округлением или налоговым правилом. Для будущего UI обязательно показывать `source_fetched_at` и методику, а для актуальности — согласовать повторный синк закрытых дат.

Дополнительный контроль 23.09: при последнем чтении `dash.getTransactions` дал 2 391 чек, оплаченная сумма совпала с товарным API; `Σ total_profit_netto` был на 0,01 ₴ выше `Σ product_profit_netto`. Это отличие между зерном чеков и товарных строк уже наблюдалось раньше. Старый Excel-экспорт Poster — другой момент времени и не может служить неизменным эталоном текущей прибыли.

## Что **не** проверено / не включено

- На момент первого этапа не были проверены 14/30-дневный backfill, текущий день, возвраты в отдельных граничных сценариях и будущая ежедневная свежесть. Первая попытка расширить окно до 14 дней остановилась **до записи 16.09**: Poster вернул HTTP 500 на `access.getSpots`. Причина не установлена — не называем её доказанным rate limit. Продолжение после восстановления источника описано ниже.
- Нагрузочный тест или `EXPLAIN` на отдельном staging; такого контура пока нет.
- Многодневный read API и UI категорий/продуктов. Нынешний `/admin/technologist/food-cost` по-прежнему показывает пилот одного продукта, а не эти синхронизированные продажи.
- Cron/автоматическое обновление. Выполнен **разовый**, проверенный семидневный синк, не постоянно работающая интеграция.

Следующий технический этап: SQL-агрегация последних `completed`-версий в `feedbackgb` с индексами и `EXPLAIN`, затем защищённый read API/UI. Перед включением реального KPI согласовать политику повторного синка изменяющихся исторических дней и допустимую задержку данных.

Разрешение на этот bounded backfill не означает, что фудкост в админке готов к публикации.

Гонка двух одновременных процессов этим не закрыта; новые SQL-объекты не применялись.
