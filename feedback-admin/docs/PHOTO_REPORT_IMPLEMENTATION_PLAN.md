# План реалізації та приймання: «Фото звіт»

## 0. Мета і межі

Продавчиня надсилає окремий фото-звіт магазину до чотирьох разів на день. Один звіт містить від 1 до 15 фото. Адмінка за обрану дату повинна показувати кожен активний магазин: чи надіслав звіт, кількість звітів, кількість фото, хто надіслав і час останньої відправки.

У межах цієї задачі не змінюються інші категорії фідбеку, Poster, ролі користувачів або правила призначення відповідальних.

## 1. Контракт даних

| Поле | Значення |
| --- | --- |
| `feedback.category` | `photo_report` |
| Один рядок `feedback` | Один натиск «Відправити» у фото-звіті |
| `photo_url` | Перше фото у форматі `sb:<private-storage-path>` для сумісності зі старими екранами |
| `fields.photo_urls` | Повний упорядкований список шляхів усіх фото |
| `store_id` | Серверне значення із сесії продавчині; клієнт не може підмінити магазин |
| `user_id` | Поточна авторизована продавчиня |
| День звіту | День `created_at` у часовому поясі `Europe/Kyiv` |

Фото не є публічними URL. Вони зберігаються у приватному bucket `feedback-photos`; підписані URL створюються лише на сервері для відповідних адміністративних екранів.

## 2. Етап 1 — підготувати БД

### Дії

1. Перевірити, що staging і production використовують схему `feedbackgb` та таблицю `feedbackgb.categories`.
2. Застосувати [023_photo_report_category.sql](../supabase/023_photo_report_category.sql) спочатку у staging.
3. Перевірити, що в `feedbackgb.categories` існує рівно один рядок `photo_report` з українськими назвою та описом.
4. Переконатися, що `feedbackgb.feedback_feed` уже повертає `photo_urls` із `fields`; окрема зміна view не потрібна.

### SQL-перевірки

```sql
select id, emoji, title, short, sort_order
from feedbackgb.categories
where id = 'photo_report';

select column_name
from information_schema.columns
where table_schema = 'feedbackgb'
  and table_name = 'feedback';
```

### Gate приймання

- Категорія є FK-ціллю до будь-якого deploy UI.
- Якщо SQL-міграцію не застосовано, deploy заборонений: вставка фото-звіту завершиться FK-помилкою.

## 3. Етап 2 — форма у застосунку продавчині

### Реалізація

1. Додати `photo_report` до `shared/lib/categories.ts`. Це єдине джерело категорій для `feedback-app` і `feedback-admin`.
2. Показати окрему картку «📸 Фото звіт» на головному екрані продавчині.
3. Відкрити стандартний маршрут `/feedback/photo_report`.
4. У формі вимагати щонайменше одне фото й обмежити вибір п'ятнадцятьма.
5. Для звіту стискати JPEG до 280 KiB/фото і максимальної сторони 1280 px.
6. Декодувати/стискати не більш як два фото паралельно, щоб не перевантажити RAM iOS Telegram WebView та Android WebView.
7. Передавати `photo_urls`, `client_submission_id` та `client_created_at` у існуючий `POST /api/feedback`.

### Тести форми

| ID | Сценарій | Очікування |
| --- | --- | --- |
| APP-01 | Android Chrome/Telegram: 1 фото з камери | Прев'ю з'являється, звіт відправляється |
| APP-02 | iPhone Safari/Telegram: 15 фото з камери | Інтерфейс не зависає; показано `15/15` |
| APP-03 | Вибрати 16 фото | Прийнято лише 15, користувач бачить ліміт |
| APP-04 | Натиснути «Відправити» без фото | Відправка не відбувається, є зрозуміла помилка |
| APP-05 | Видалити одне з вибраних фото | Лічильник і payload зменшуються на одне |
| APP-06 | Вимкнути інтернет перед відправкою | Зберігається offline-чернетка за поточним контрактом застосунку |
| APP-07 | Відкрити іншу категорію | Її старий ліміт залишається 5 фото |

## 4. Етап 3 — API та Storage

### Реалізація

1. У `feedbackValidation.ts` дозволити лише `photo_report` до 15 фото; інші категорії залишити на ліміті 5.
2. Для `photo_report` вимагати хоча б одне фото також на сервері.
3. Відхилити HTTP body понад 8 MiB до JSON-парсингу.
4. Приймати лише `data:image/jpeg|png|webp;base64,...`; зовнішні URL, інші MIME та порожні буфери відхиляти.
5. Для `photo_report` обмежити декодований файл 280 KiB; для старих категорій зберегти 5 MiB.
6. Завантажувати максимум три файли одного звіту паралельно.
7. Якщо хоча б одне фото не завантажено, видалити вже створені файли цього запиту та не вставляти рядок `feedback`.
8. Лише після повної успішної загрузки вставити `feedback` з `photo_url` і `fields.photo_urls`.

### API-тести

| ID | Запит | Очікування |
| --- | --- | --- |
| API-01 | 15 валідних small JPEG | `200`, один рядок feedback, 15 шляхів у `fields.photo_urls` |
| API-02 | 16 валідних JPEG | `400 Too many photos: max 15`, без Storage/DB записів |
| API-03 | Нуль фото | `400 Photo report requires at least one photo` |
| API-04 | Фото понад 280 KiB | `503`, без рядка feedback, без orphan-файлів |
| API-05 | Одне з 15 фото не проходить Storage | `503`, без рядка feedback, уже завантажені шляхи видалені |
| API-06 | Повторний `client_submission_id` тією самою продавчинею | `200 duplicate:true`, не з'являється другий рядок |
| API-07 | Підмінений `store_id` у payload продавчині | Записаний `store_id` із сесії, не з payload |
| API-08 | Зовнішній URL або SVG замість фото | Не записується як фото |

## 6. Етап 5 — навантаження: 100 продавчинь одночасно

### Розрахунок межі

- Максимум одного звіту: `15 × 280 KiB = 4.10 MiB` JPEG.
- З base64 JSON це приблизно `5.47 MiB`, що нижче API-ліміту 8 MiB.
- 100 одночасних повних звітів: приблизно `547 MiB` inbound JSON.
- 3–4 повні хвилі на день: 4 500–6 000 фото, приблизно 1.6–2.2 GiB JSON-входу на добу.

Ці цифри доводять лише відповідність локальним лімітам. Вони не є доказом достатньої квоти Vercel або Supabase.

### Підготовка staging

1. Використати окремий Supabase staging project або окремий bucket; production не використовувати.
2. Створити 100 тестових користувачів і 100 активних тестових магазинів.
3. Підготувати 15 JPEG не більше 280 KiB на звіт.
4. Встановити окремий test-run marker у `client_submission_id`/тестових облікових записах, щоб очистка була точною.
5. Зафіксувати початкові Storage usage, Vercel function logs і DB row counts.

### Прогін

1. Запустити 100 одночасних авторизованих POST з 15 фото.
2. Не перезапускати впалі запити автоматично, поки не зафіксована первинна причина.
3. Зібрати: HTTP-коди, p50/p95/p99 latency, Vercel duration/memory, Storage errors, кількість рядків `feedback`, кількість object-ів у bucket.
4. Відкрити адмінку на цій даті та звірити всі 100 магазинів.

### Критерії успішності

- 100/100 запитів завершились `2xx`.
- Рівно 100 записів `feedback` категорії `photo_report`.
- Рівно 1 500 private Storage object-ів тестового запуску.
- У кожному рядку рівно 15 елементів `fields.photo_urls`.
- Немає рядків із 1–14 фото та немає orphan-файлів.
- Адмінка показує `100/100` магазинів, що надіслали, та `1 500` фото.
- Якщо хоча б один критерій не виконано, production gate = **BLOCKED**; не маскувати помилку повторним запуском.

## 7. Етап 6 — регресія, безпека та спостережуваність

1. Прогнати `npm.cmd run build` і `npm.cmd test` у `feedback-app` та `feedback-admin`.
2. Перевірити, що попередні категорії все ще приймають не більше 5 фото.
3. Перевірити, що buyer/seller не має доступу до `/admin/photo-report` і до необроблених Storage URL.
4. Перевірити, що в логах немає base64 фото, cookies, PIN або service-role key.
5. Перевірити retry/duplicate поведінку з однаковим `client_submission_id`.
6. Перевірити підписані URL: вони короткоживучі та не записуються в БД замість `sb:` шляху.

## 8. Етап 7 — release у production

1. Підтвердити успішний staging gate з розділу 6.
2. Застосувати SQL-міграцію у production через затверджений адміністративний канал.
3. Прочитати назад рядок `feedbackgb.categories.photo_report`.
4. Розгорнути seller app і admin panel з однаковим комітом.
5. Провести один контрольований production smoke-test авторизованою тестовою продавчинею з 1 фото.
6. Перевірити приватний object у Storage, рядок `feedback`, `feedback_feed` та одну строку в адмінці.
7. Лише після readback оголосити функцію доступною продавчиням.

## 9. Відкат

1. Якщо проблема лише у UI, повернути deploy обох застосунків на попередній перевірений commit.
2. Не видаляти `photo_report` категорію або historical feedback rows без окремого погодження: це знищує аудит.
3. Якщо потрібно тимчасово зупинити нові звіти, прибрати картку з seller app у наступному deploy; дані та адмінський read-only перегляд зберегти.
4. Зафіксувати точний час, commit, число зачеплених звітів та Storage paths до будь-яких виправлень.
