## Вывод: BLOCKED — выпускать нельзя

Заявленный сценарий «100 продавцов одновременно» упирается **не в загрузку фото, а во вход в систему**. Одна попытка входа стоит **3 772 мс процессорного времени БД** — это измерено на рабочей базе, а не рассчитано. Сто входов в одном окне дают около 377 секунд чистой нагрузки на ту же базу, которая обслуживает и загрузку фото, и счётчик лимитов.

Второе: правило «не трогать production без согласования» уже нарушено — миграция применена, и в базе лежат четыре реальных фотоотчёта за сегодня, хотя документ ветки утверждает обратное.

Третье, важное для планирования: сам механизм загрузки фото менять не требуется — реальные замеры оказались лучше расчётных. Подробности в разделе «Решение архитектуры».

## 1. Измеренные факты

Всё ниже получено запросами только на чтение к базе, к которой подключён MCP и в которой лежат живые данные (118 заявок, 53 активных продавца). Единственная операция с вычислительной нагрузкой — один расчёт bcrypt, эквивалентный одному обычному входу пользователя.

| Показатель | Значение | Что это меняет |
| --- | ---: | --- |
| Стоимость одного входа | **3 772 мс** | 60 хешей bcrypt (cost 10) на каждую попытку — успешную и неуспешную одинаково |
| Активных пользователей с PIN | 60 | Стоимость входа растёт линейно: при 100 пользователях ≈ 6,3 с |
| Активных продавцов / магазинов | 53 / 26 | Цель «100 одновременно» — двукратный запас к текущему масштабу |
| Реальный размер фото (среднее) | 172 KiB | Клиентское сжатие работает: максимум 214 KiB при потолке 280 KiB |
| Реальная волна 100 × 15 фото | ≈ 337 MiB | Против 547 MiB в расчёте ветки — оценка была консервативной |
| Прирост Storage при 3–4 волнах | 0,74–0,99 GiB/сут | 22–30 GiB в месяц при полном отсутствии политики хранения |
| Фотоотчётов уже в базе | 4 | Созданы сегодня, 6/5/10/10 фото — функция уже работала на этой базе |
| Потерянных ссылок (missing) | 0 | Из 31 реального фото ни одно не потеряно — целостность на этой выборке держится |
| Файлов-сирот в бакете | 2 | Оба от 2026-05-01, то есть старше функции: процесса очистки не существует вовсе |

Запрос, которым измерена стоимость входа (воспроизводим):

```sql
with t0 as materialized (select clock_timestamp() as a),
 work as materialized (
   select max(length(household_chemicals.crypt('000000', u.pin_hash))) as c,
          count(*) as n
     from feedbackgb.users u, t0
    where u.is_active and u.pin_hash is not null
      and (u.locked_until is null or u.locked_until <= now()))
select w.n as hashes_computed,
       round(extract(epoch from (clock_timestamp() - t.a)) * 1000) as elapsed_ms
  from t0 t, work w;
-- hashes_computed = 60, elapsed_ms = 3772
```

Запрос, которым посчитаны сироты и потерянные ссылки (пригодится как постпроверка нагрузочного теста):

```sql
with refs as (
  select 'sb:' || o.name as storage_ref
    from storage.objects o where o.bucket_id = 'feedback-photos'
), db_refs as (
  select jsonb_array_elements_text(f.fields->'photo_urls') as ref
    from feedbackgb.feedback f where jsonb_typeof(f.fields->'photo_urls') = 'array'
  union
  select f.photo_url from feedbackgb.feedback f where f.photo_url is not null
)
select
 (select count(*) from storage.objects where bucket_id = 'feedback-photos') as storage_objects,
 (select count(*) from db_refs where ref like 'sb:%')                        as db_referenced_paths,
 (select count(*) from refs r
   where not exists (select 1 from db_refs d where d.ref = r.storage_ref))   as orphan_objects,
 (select count(*) from db_refs d
   where d.ref like 'sb:%'
     and not exists (select 1 from refs r where r.storage_ref = d.ref))      as missing_objects;
-- 48 / 46 / 2 / 0
```

## 2. Критические находки

### CRIT-1. Вход — одновременно узкое место нагрузки и вектор отказа в обслуживании

**Источник:** не из этой ветки · ТЗ §6
**Где:** `feedback-admin/supabase/017_fix_pgcrypto_search_path.sql:62-108`, `shared/lib/rateLimit.ts`

`verify_pin_global` перебирает **всех** активных пользователей и для каждого считает bcrypt. Раннего выхода при совпадении нет — цикл всегда идёт до конца, чтобы поймать дубликаты PIN. Значит цена не зависит от того, верный PIN или нет.

```
Замер на рабочей БД:
  60 хешей · 3 772 мс CPU на один запрос входа

Ограничение: 10 попыток / 10 мин с одного IP
  → один IP законно расходует 37,7 с CPU БД каждые 10 минут
  → ~20 IP непрерывно держат целое ядро БД занятым

Утренняя волна 100 продавцов ≈ 377 с чистого bcrypt
  на той же БД, где живёт check_rate_limit и вставка отчётов
```

Отдельно: лимитер «фейлится закрыто» в production — когда БД перегружена, `rateLimit()` бросает исключение и login отвечает 503. То есть перегрузка от входов сама блокирует входы.

**Исправить:** ввести короткий идентификатор пользователя рядом с PIN либо индексируемый префикс хеша, чтобы проверять один хеш вместо шестидесяти. До этого нагрузочный тест входа запускать бессмысленно — он положит базу.

### CRIT-2. Блокировка учётной записи после миграции 009 не работает

**Источник:** не из этой ветки · ТЗ §6
**Где:** `schema.sql:206`, `002_security_hardening.sql:135` (старый путь) против `017_fix_pgcrypto_search_path.sql:95` (текущий путь)

Счётчики `failed_attempts` / `locked_until` увеличиваются только в старой функции `verify_pin(user_id, pin)`. Действующий вход через `verify_pin_global` их **только обнуляет при успехе** и никогда не увеличивает при неудаче.

```
schema.sql:206 — failed_attempts + 1 >= 10 → блокировка на час   (старый путь)
017_fix_pgcrypto_search_path.sql:95 — if match_count = 0 then return null;  (текущий путь)
                                      ↑ ни одного инкремента

Единственная защита от перебора — IP-лимит,
а clientIp() берёт первый элемент X-Forwarded-For (shared/lib/rateLimit.ts)
→ на self-hosted прокси значение подставляется клиентом
```

PIN шестизначный и опознаёт пользователя сам, без логина. При 60 активных PIN вероятность попадания — примерно 1 на 16 тысяч попыток, то есть вход под чужой учётной записью достижим перебором, если лимит обходится подменой заголовка.

**Исправить:** считать неудачи по ключу «IP + окно» в БД с экспоненциальной задержкой; брать клиентский IP из доверенного заголовка прокси, а не из первого элемента цепочки. Кнопка «Розблокувати» в админке сейчас управляет мёртвым счётчиком — оживить или убрать.

### BLOCKER-3. Документ ветки расходится с реальным состоянием базы

**Источник:** процесс · ТЗ §2, §9
**Где:** `feedback-admin/docs/PHOTO_REPORT_IMPLEMENTATION_PLAN.md:191`

План в ветке утверждает: миграция «не застосовано», staging «не виконано», production deploy «не виконано». Фактически:

```
categories: photo_report присутствует        → миграция 023 ПРИМЕНЕНА
feedback:   4 строки photo_report за 2026-09-15, 31 фото в приватном бакете
audit_log:  индекс action_occurred_at_idx отсутствует → миграция 024 НЕ применена
```

Пока статус-таблица не соответствует базе, ни один пункт приёмки нельзя считать подтверждённым — и требование «запрещено запускать тест на production» уже де-факто нарушено ручными прогонами.

**Исправить:** зафиксировать реальное состояние каждой миграции по всем средам отдельным readback-запросом, а не текстом в документе. Решить, что делать с четырьмя боевыми отчётами: оставить как рабочие данные или удалить как тестовые.

## 3. Высокий приоритет

### HIGH-1. Ошибка записи в БД оставляет все фото в Storage навсегда

**Источник:** эта ветка · ТЗ §3
**Где:** `feedback-app/src/app/api/feedback/route.ts:145,278,310`

ТЗ прямо требует сценарий очистки или журналирования при ошибке БД после загрузки файлов. В коде единственный вызов `storage.remove` — в ветке частичной загрузки. Путь ошибки вставки возвращает 500 и не трогает уже загруженные файлы.

```
route.ts:145  storage.remove(...)   ← единственный, только для partial upload
route.ts:278  console.error("supabase insert error", { code })
route.ts:310  return 500            ← 15 файлов остаются, пути нигде не записаны

Подтверждение, что чистки не существует вовсе:
  2 файла-сироты от 2026-05-01 живы спустя 4,5 месяца
```

**Исправить:** в ветке ошибки вставки либо удалять загруженное, либо логировать полные пути отдельным событием, и завести фоновую задачу, сверяющую бакет с базой (SQL выше).

### HIGH-2. Лог неудавшегося отката не содержит того, ради чего его добавляли

**Источник:** эта ветка · коммит `6b01277`
**Где:** `feedback-app/src/app/api/feedback/route.ts:151`

Комментарий в коде объясняет цель: без этого лога «осиротевшие объекты нельзя отследить и удалить». Но в событие пишется только **количество** файлов, а не их пути — отслеживать по-прежнему нечего.

```js
logPhotoReport("photo_report.cleanup_failure", {
  request_id, user_id, store_id,
  uploaded_photo_count: photoUrls.length,   // ← только счётчик
  duration_ms,
});
```

**Исправить:** добавить массив путей в событие. Пути — случайные UUID, персональных данных в них нет, требование «не логировать PII» не нарушается.

### HIGH-3. Админ-страница выгружает в браузер 31 день данных ради одного дня на экране

**Источник:** эта ветка · ТЗ §5
**Где:** `feedback-admin/src/app/(admin)/admin/photo-report/page.tsx:25`

Серверный компонент тянет до 15 000 строк вместе с массивами `photo_urls` и отдаёт их клиенту целиком; выбор даты и агрегация происходят уже в браузере. Сегодня это 4 строки, поэтому дефект не виден.

```
.limit(15000) за 31 день, все photo_urls

При целевом объёме (100 магазинов × 3–4 отчёта × 15 фото):
  ≈ 9 300–12 400 строк → 7–9 MB в payload на каждое открытие страницы

Сверх 15 000 строк тихо отсекаются САМЫЕ СТАРЫЕ дни —
календарь покажет «никто не отправил» вместо «данных нет»
```

**Исправить:** перенести фильтр по дате и агрегацию на сервер — запрашивать один выбранный день и возвращать уже посчитанные строки.

### HIGH-4. Галерея подписывает каждую ссылку отдельным запросом

**Источник:** эта ветка · ТЗ §4
**Где:** `feedback-admin/src/app/api/admin/photo-report/gallery/route.ts:67`

На открытие модального окна выполняется `createSignedUrl` для каждого фото через `Promise.all` без ограничения параллелизма — при потолке в 100 отчётов это до 1 500 обращений к Storage внутри одного HTTP-запроса. В supabase-js есть пакетный `createSignedUrls(paths[], ttl)` — одна операция на весь набор.

Там же: TTL подписи 10 минут без продления. Открытая вкладка через десять минут начинает отдавать 403, а у `<Image>` не задан обработчик ошибки — админ увидит молча сломанные картинки.

**Исправить:** пакетное подписание, ограничение окна выборки, повторный запрос ссылок при истечении срока.

## 4. Средний приоритет

### MED-1. Содержимое изображения не проверяется — доказано собственным тестом ветки

**Где:** `feedback-app/scripts/load-photo-report.mjs:44`, `feedback-app/src/app/api/feedback/route.ts:356`

Сервер доверяет только строке MIME в data-URL: сигнатура файла не проверяется. Нагрузочный скрипт из этой же ветки формирует фикстуру из 280 KiB одинакового байта и объявляет её как `image/jpeg` — и она штатно попадает в приватный бакет. Ограничение бакета `allowed_mime_types` проверяет только объявленный тип.

**Исправить:** проверять сигнатуру первых байтов (JPEG `FF D8 FF`, PNG, WebP) перед выгрузкой. Заодно это сделает фикстуру нагрузочного теста честной.

### MED-2. Телеметрия открыта без аутентификации в обоих приложениях

**Где:** `feedback-app/src/middleware.ts:41`, `feedback-admin/src/middleware.ts:41`, `*/api/telemetry/client-error/route.ts:23`

Middleware добавил `/api/telemetry/` в список путей, пропускаемых мимо сессии. Эндпоинт пишет строки в `audit_log`, а его единственная защита — тот же лимит по подставляемому IP. Ограничение размера тела читается только из заголовка `content-length`, которого клиент может не прислать (обходится chunked-запросом; повторной проверки после чтения нет — в `/api/feedback` она есть).

**Исправить:** проверять фактическую длину после чтения тела; записи от анонимных клиентов складывать в отдельную таблицу с TTL, а не в журнал аудита.

### MED-3. Нет политики хранения при приросте около гигабайта в сутки

По измеренному среднему размеру фото целевой режим даёт 0,74–0,99 GiB в сутки → 22–30 GiB в месяц → 270–360 GiB в год. Ни срока хранения, ни архивации, ни удаления в коде и миграциях нет.

**Исправить:** согласовать срок хранения (например, 90 дней), реализовать удаление по расписанию вместе с очисткой сирот, заложить стоимость в бюджет до запуска.

### MED-4. Нагрузочный скрипт не измеряет то, что требует ТЗ

**Где:** `feedback-app/scripts/load-photo-report.mjs`

Защита от запуска по production сделана хорошо: явное подтверждение `LOAD_TEST_CONFIRM_STAGING=YES`, сверка хоста, требование ста разных сессий. Как измерительный инструмент он при этом непригоден:

1. **Вход не участвует** — используются готовые cookie, поэтому главное узкое место (3,77 с на логин) тест не увидит.
2. **Фикстура не JPEG** — искажает и поведение, и результат.
3. **`Promise.all` на 100 × ~5,5 MB в одном процессе Node** — пул соединений undici станет очередью, и p95/p99 измерят клиента, а не сервер.
4. **Проверяются только коды и задержки** — критерии целостности ТЗ (1 500 объектов, 0 частичных отчётов, 0 сирот) не проверяются вовсе.

**Исправить:** разнести нагрузку по нескольким процессам или машинам, включить в сценарий вход, использовать настоящие JPEG, добавить постпроверку целостности SQL-запросом (готов, см. раздел 1).

### MED-5. Схема базы разошлась с репозиторием

В рабочей базе есть объекты, которых нет в репозитории ни в одной миграции: таблицы `facilities`, `user_app_access`, `user_facility_memberships`, `photo_mirror` и категория `raw_material_defect`. Расширение pgcrypto установлено в схему `household_chemicals`.

```
raw_material_defect: sort_order = 11
photo_report:        sort_order = 11   ← конфликт порядка сортировки
```

Следствие для staging: среда, собранная из миграций репозитория, **не воспроизведёт рабочую** — включая схему pgcrypto, от которой зависит вход. Тест на такой среде будет недостоверен.

**Исправить:** снять актуальный дамп схемы с рабочей базы и привести миграции в соответствие **до** разворачивания staging.

## 5. Низкий приоритет

- **Календарь без границ.** У `DatePicker` не задан `disabledDate`: дата вне окна в 31 день или дата в будущем покажет «никто не отправил» вместо честного «данных нет».
- **Нет составного индекса.** Запросы идут по `category + created_at` и `store_id + category + created_at`, а в базе эти столбцы проиндексированы по отдельности. При 150 тыс. строк в год станет заметно.
- **`user_interactions` без RLS.** Единственная таблица схемы с выключенным RLS, при этом у роли `authenticated` есть на неё INSERT. На остальных таблицах модель выстроена верно.
- **Бакет `telegram-user-photos` публичный** и без ограничений по типу и размеру. К фотоотчётам отношения не имеет, но рядом.

## 6. Подтверждено как исправное

Эти пункты ТЗ проверены и нареканий не вызвали — перепроверять на staging не нужно.

- **Бакет приватный.** `public: false`, потолок 5 MiB, типы ограничены jpeg/png/webp на уровне самого бакета.
- **Доступ к API закрыт по роли.** `requireAdminSession` проверяет уровень роли, middleware закрывает все админские маршруты; ссылки выдаются только подписанные, с коротким сроком.
- **RLS включён на всех таблицах** без политик (по умолчанию запрещено); у `anon` остался только SELECT на справочник категорий.
- **Магазин берётся из серверной сессии** продавца и не может быть подменён полем запроса.
- **Ключевое допущение плана верно:** `feedback_feed` действительно отдаёт `photo_urls` (jsonb), а `v_stores.id` совпадает по типу со `store_id` — сводка по магазинам не развалится.
- **Клиентское сжатие работает на реальных телефонах:** 31 фото, все JPEG, максимум 214 KiB при лимите 280 KiB.
- **Целостность на реальной выборке:** ни одной битой ссылки, ни одного сироты, порождённого новым потоком.
- **Галерея закрывает прежний разрыв:** отчёты за день разделены, у каждого свой номер, автор, время и свой набор фото.

## 7. Что не проверено и почему

Правило ТЗ соблюдено буквально: ничего не изменено, нагрузочный тест не запускался. Ниже — то, что **нельзя** закрывать этим отчётом.

- **Нагрузка 100 × 15.** Нет staging, нет ста отдельных сессий, нет разрешения на запись. Запуск по рабочей базе запрещён самим ТЗ — и, учитывая цену входа, положил бы её.
- **Реальные устройства.** iPhone и Android, Telegram WebView, поворот экрана, уход в фон, медленная сеть — проверяются только руками на технике.
- **Поведение при сбоях Storage.** Сценарии «упала одна загрузка из пятнадцати» и «упало удаление при откате» требуют управляемой среды с внесением отказов.
- **HEIC с iPhone.** Ни в коде, ни в тестах формат не упоминается: нужно проверить на устройстве, конвертирует ли камера в JPEG до отправки.
- **Квоты и лимиты платформы.** Ограничения функций и Storage под нагрузкой — только замером, не чтением кода.

## 9. Решение архитектуры: менять ли механизм загрузки

По измеренным данным — **механизм менять не требуется**. Реальная волна даёт около 337 MiB вместо расчётных 547 MiB, отдельный отчёт укладывается в 3,4 MiB при лимите 8 MiB, и целостность на боевой выборке держится. Переход на прямую загрузку в Storage по временным ссылкам усложнил бы проверку содержимого и правило «всё или ничего» ради выигрыша, который сегодня не нужен.

Пересматривать это решение следует:

- при росте примерно вдвое — к 200 одновременным продавцам;
- если после исправления входа замеры покажут, что узким местом стала именно передача тела запроса;
- обязательно — если потребуется поднять потолок в 15 фото или отказаться от сжатия до 280 KiB.

## 10. Порядок работ до повторной проверки

1. **Починить вход.** Пока одна попытка стоит 3,77 с, ни нагрузочный тест, ни релиз смысла не имеют. Это единственное, что блокирует всё остальное.
2. **Вернуть защиту от перебора:** счётчик неудач с задержкой и доверенный источник IP.
3. **Закрыть потерю файлов:** очистка или журналирование путей при ошибке вставки, пути в событии неудавшегося отката, фоновая сверка бакета с базой.
4. **Свести схему репозитория с рабочей базой** и зафиксировать реальный статус каждой миграции по средам.
5. **Развернуть staging из выверенных миграций** — отдельный проект, отдельные ключи, сто тестовых сессий.
6. **Доработать тестовый скрипт:** вход в сценарии, настоящие JPEG, распределённая нагрузка, постпроверка целостности.
7. **Прогнать нагрузку и мобильные проверки**, после чего вернуться к вопросу о релизе.

---

*Проверка выполнена без изменений в коде и данных: только чтение файлов ветки и read-only запросы. Единственная операция с вычислительной нагрузкой — один расчёт bcrypt, равный по стоимости одному входу пользователя. Все числа воспроизводимы запросами к той же базе.*
