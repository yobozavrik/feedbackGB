# План ускорения админ-панели

Статус: план. Код, настройки Vercel, базу и миграции этот документ не меняет.

## Цель

Ускорить открытие и переключение ключевых страниц админки без потери данных, нарушения авторизации или изменения бизнес-правил.

Приоритетные маршруты: `/admin`, `/admin/stores`, `/admin/technologist/products`, `/admin/photo-report` и drawer магазина.

## Подтверждённые факты

- `/admin` передаёт до 5 000 строк `feedback_feed` в client-компоненты KPI, сигналов и heatmap.
- `/admin/stores` получает до 10 000 строк `feedback_feed` даже на вкладке карточек магазинов.
- `/admin/technologist/products` получает до 5 000 строк `v_products` для подсчёта категорий.
- Главная лента может создавать до 200 Storage signed URL при загрузке.
- Графики AntV и части pro-components импортируются статически; `next/dynamic` в коде не используется.
- `pin_hash` выбирается серверной страницей магазинов только для `has_pin`; в браузер не передаётся, но запрос можно сузить.
- `/admin` dynamic из-за layout, который проверяет cookies. Удаление `force-dynamic` со страниц не создаст ISR само по себе.
- Карточки вкладки `Магазини` используют только `v_stores` (название, адрес, активность, ID); `feedback_feed` нужен вкладке `Звіти`.
- Dashboard heatmap сейчас использует `Date.getDay()`/`getHours()` в локальной таймзоне браузера, а KPI/signals — скользящие интервалы от `Date.now()`. Таймзона `Europe/Kyiv` для этой heatmap в коде не закреплена.
- Realtime на главной странице вызывает `router.refresh()` и отдельно получает краткие данные для уведомления через защищённый `/api/admin/feedback/[id]`; прямой вставки новой строки в client state нет.

## Правила

1. Работать в отдельной ветке производительности.
2. Не менять применённые миграции и не выполнять DDL/DML в production ради замеров.
3. Сначала baseline, затем одно изменение, затем повторный замер.
4. Каждый этап требует preview и авторизованный E2E; локальная сборка недостаточна.
5. Не записывать PIN hashes, service-role key, Poster token, cookies или signed URL в Git и доказательства.
6. При отсутствии улучшения или функциональном регрессе откатывать только текущий этап.

## P-00. Baseline — обязательный gate

1. Зафиксировать SHA и Preview URL.
2. Выполнить `npm.cmd run build` в изолированной среде; сохранить First Load JS.
3. Под авторизованным супер-админом открыть `/admin`, `/admin/stores`, `/admin/technologist/products` по 5 раз с disabled cache; записать сеть, устройство, viewport и режим cold/warm.
4. Для каждого маршрута сохранить TTFB document и RSC, размер document/RSC response (переданный и распакованный, если доступен), First Load JS и главные JS chunks. HAR или Network-скриншоты очистить от cookies, токенов, signed URL и персональных данных.
5. Зафиксировать число строк в payload, число Storage signed-url вызовов и распределение времени по пяти прогонам (медиана и диапазон), не смешивая cold и warm.

Gate P-00 пройден только при наличии измерений до изменений. Без него все последующие сравнения блокируются.

## Этапы реализации

### P-07. Оптимизация импортов — выполнить первой после P-00

1. Добавить `experimental.optimizePackageImports` для `@ant-design/pro-components` и `@ant-design/plots`.
2. `antd` и `@ant-design/icons` добавлять только если build-анализ покажет отсутствие встроенной оптимизации Next.
3. Не обновлять Next/React/Ant Design в рамках этого плана.
4. Сравнить First Load JS, состав chunks, TTFB и размеры document/RSC с P-00. Если эффекта нет, так и записать; выигрыш не считать установленным заранее.

Проверки: typecheck, полный `vitest run`, production build, Preview Ready и отсутствие manifest errors на затронутых маршрутах и вкладках. P-05 измерять относительно принятого результата P-07, сохраняя P-00 как исходный baseline.

Откат: удалить только добавленную конфигурацию.

### P-01. Ленивая загрузка вкладки `Звіти` магазинов

Проблема: вкладка `Магазини` не использует фидбек, но сервер уже загружает каталог, продавцов и до 10 000 строк фидбека. Проверено по `StoreCards`: её поля берутся только из `StoreRow` (`v_stores`), поэтому P-01 может идти до P-03 без потери счётчиков карточек.

Действия:

1. Оставить server page только с лёгким справочником магазинов.
2. Создать защищённый admin API отчётов с периодом, лимитом и пагинацией.
3. Загружать API только после первого открытия `Звіти`.
4. Отменять запрос при смене вкладки или периода через `AbortController`.
5. До P-03 сохранить текущие расчёты StoreDrawer без изменения формул.

Проверки:

- Открытие `/admin/stores` на `Магазини` не вызывает reports API.
- Первое открытие `Звіти` вызывает один запрос; повторное не дублирует его без смены фильтра.
- Ошибка API отображается в существующем дизайне без фиктивных KPI.
- Все 26 карточек магазинов остаются доступны.
- Название, адрес, бейдж активности и ID каждой карточки совпадают с состоянием до P-01; вкладка `Звіти` сохраняет прежние цифры до перехода на P-03.

Откат: вернуть единый server fetch; БД не изменяется.

### P-02. Агрегация dashboard в БД

Проблема: `/admin` сериализует до 5 000 строк ради трёх клиентских агрегатов.

Действия:

1. Зафиксировать контракты KPI, signals и heatmap: скользящие окна от одного `as_of`, статусы, исключение `photo_report`, порядок выбора топ-категории и таймзону heatmap. Для точного паритета прогонять старый JS и SQL в одной явно заданной таймзоне браузера: SQL-группировка дня/часа должна соответствовать `getDay()`/`getHours()` (например, `created_at AT TIME ZONE p_timezone`). Отдельное решение закрепить `Europe/Kyiv` для всех админов считать изменением бизнес-семантики и проверять отдельно.
2. Сделать новую forward-only миграцию с read-only view или RPC; применённые миграции не редактировать.
3. Вернуть компактные отдельные DTO для KPI, сигналов и heatmap.
4. Оставить ленту 200 последних записей отдельным read-path, но не использовать её для агрегатов.
5. Переписать client-компоненты на DTO.
6. Для T-03 зафиксировать `as_of` один раз, использовать интервал `created_at >= as_of - interval '30 days' AND created_at < as_of` и одинаковые границы 24ч/3/7/14 дней для обоих путей. В staging подготовить неизменяемый набор строк со всеми полями, включая `status`, `store_name`, `category_title` и `product_name`; сравнить SQL с прежними JS-функциями на том же наборе. Один `as_of` без фиксирования строк недостаточен: статусы и справочники могут измениться между чтениями.
7. На staging выполнить `EXPLAIN (ANALYZE, BUFFERS)` для новых read-view/RPC на репрезентативном объёме и периоде; сохранить план, время, прочитанные блоки и решение об индексах. Сначала проверить существующие индексы и фактический план, затем добавлять индекс только при доказанной необходимости.

Проверки:

- SQL и старые JavaScript-расчёты совпадают на зафиксированном snapshot.
- Отдельные граничные примеры около полуночи и перехода летнего/зимнего времени совпадают при заданной таймзоне; `as_of` одинаков для SQL и JS.
- Проверены пустой период, магазин без фидбека, неизвестная категория, `new`, `in_progress`, `resolved`, `rejected`.
- `photo_report` не входит в KPI.
- Network перестаёт передавать тысячи сырых строк ради dashboard.

Откат: вернуть прежний read-path отдельным коммитом; новую view/RPC не удалять из применённой миграции.

### P-03. Агрегация отчётов магазинов в БД

Проблема: отчёты и детали 26 магазинов рассчитываются из до 10 000 строк в JavaScript.

Действия:

1. Зафиксировать контракт `StoreSummary` и `StoreDetail`: 30/90-дневные окна, топ-категория, продавцы, статусы и единый `as_of` для SQL и старого JS.
2. Добавить отдельную read-view/RPC по магазинам; не смешивать её с фотоотчётами.
3. API `Звіти` возвращает агрегаты и пагинированную детализацию, не исходный `feedback_feed` целиком.
4. Сформировать безопасный seller read-model: ID, ФИО, магазин, active, last_login, `has_pin`; без `pin_hash`.
5. Загружать историю конкретного магазина только при открытии drawer.
6. T-04 выполнять на одном неизменяемом staging-наборе строк и продавцов; фильтр `created_at < as_of` и границы окон должны совпадать в обоих путях. На staging выполнить `EXPLAIN (ANALYZE, BUFFERS)` для сводки и детализации, включая фильтр магазина; проверить существующие индексы и добавлять составной индекс только по результату плана.

Проверки:

- Для каждого из 26 магазинов новый 30-дневный итог совпадает со старым на одном snapshot.
- Магазин без фидбека показывает нули.
- `pin_hash` отсутствует в RSC payload, API response и client props.
- 20 параллельных GET отчётов не дают 5xx; среда и результаты замера зафиксированы.

Откат: вернуть старый API/read-path одним коммитом.

### P-04. Агрегация категорий товаров

Проблема: страница категорий читает до 5 000 товаров и считает группы в коде; при большем каталоге счётчики станут неверными.

Действия:

1. Добавить read-view/RPC, группирующую `feedbackgb.v_products` по `category_id`, `category_name`, `category_sort` в PostgreSQL.
2. Явно обрабатывать `NULL category_id` как одну карточку `Без категорії`.
3. Сортировать по `category_sort`, затем по украинскому названию.
4. Заменить `limit(5000)` компактным чтением агрегированных категорий.
5. На staging сравнить агрегат и исходный каталог на одном неизменяемом наборе, затем выполнить `EXPLAIN (ANALYZE, BUFFERS)` новой view/RPC; проверить стоимость чтения `v_products` и план соединений.

Проверки:

- Сумма `product_count` равна числу строк `v_products` на snapshot.
- Каталог более 5 000 позиций не обрезает счётчики.
- Скрытые POS-категории не появляются, так как источник — `v_products`.
- Авторизованный Preview smoke не содержит Server Component manifest error.

Откат: вернуть локальную группировку; новая read-view/RPC остаётся безопасной.

### P-05. Ленивая загрузка тяжёлого UI

1. После P-07 сравнить bundle и Network chunks с принятым результатом P-07 и с исходным P-00.
2. Перевести `StoreDrawer` на `next/dynamic` с controlled loading state; графики drawer не входят в initial JS `/admin/stores`.
3. Отдельно рассмотреть charts фотоотчёта и funnel: загружать только при выборе их вкладки.
4. Не обещать эффект от lazy `ProTable`, пока bundle analysis не докажет его: `ProLayout` уже глобален.
5. Проверить light/dark, узкий viewport и hydration.

Проверки: Drawer открывается, после loading показывает прежние данные; до открытия нет chart chunks; First Load JS, TTFB и размер document/RSC сравнены с P-07 и P-00; вручную просмотрены light/dark скриншоты.

Откат: вернуть статический import конкретного модуля.

### P-06. Signed URL только по запросу

1. Убрать pre-generation signed URL из server fetch главной ленты.
2. Передавать только безопасный признак фото и feedback ID.
3. При клике получать ссылку через защищённый `/api/admin/feedback/[id]/photos`.
4. После истечения URL запрашивать endpoint повторно.
5. Проверить путь realtime: после INSERT `router.refresh()` подгружает строку без заранее созданной signed URL; при открытии её фото используется тот же защищённый endpoint. Краткий GET для уведомления не должен подписывать фото.

Проверки: открытие `/admin` не создаёт пакетные Storage signed-url запросы; админ открывает фото старой и пришедшей через realtime записи; неавторизованный доступ закрыт; `sb:` путь и запись без фото не создают утечку.

Откат: временно вернуть resolver; объекты Storage не меняются.

### P-08. Точечное сужение `select('*')`

1. Инвентаризировать каждое вхождение отдельно.
2. Зафиксировать минимальный response contract.
3. Менять запросы по одному вместе с API/UI-тестом.
4. Не менять запрос, где все поля действительно нужны, без доказательства.

## Критерии готовности

1. Есть baseline P-00 и evidence до/после для каждого завершённого этапа.
2. P-01—P-08 завершены либо честно имеют `blocked` с причиной.
3. Нет регрессий авторизации, PIN-индикатора, магазинов, KPI, фото и графиков.
4. Production обновляется только после отдельного разрешения и Preview E2E.

## Не входит в план

- Редизайн.
- Изменение ролей технолога.
- Изменение бизнес-формул фудкоста, графиков, absence workflow или фотоотчётов.
- Превращение админки в ISR простым удалением `force-dynamic`.
- Обновление Next, React, Ant Design и Supabase SDK.
