## Обязательные действия перед staging

1. Сгенерировать один секрет: `openssl rand -hex 32`.
2. Задать **одно и то же** значение `PIN_PEPPER` в server-side env админки и приложения. Не добавлять его в `NEXT_PUBLIC_*`, SQL или git.
3. Применить `feedback-admin/supabase/025_pin_lookup_auth.sql` через согласованный канал.
4. Развернуть оба приложения с одним коммитом, включив временно `PIN_LOOKUP_LEGACY_FALLBACK=true`.
5. После успешных входов выполнить readback:

```sql
select count(*) filter (where pin_lookup is null) as not_migrated,
       count(*) as total
from feedbackgb.users
where is_active and pin_hash is not null;
```

6. Только когда `not_migrated = 0`, установить `PIN_LOOKUP_LEGACY_FALLBACK=false` и повторить проверку входа. До этого старый путь существует и R-05 не закрыт.

## Риски пути B

- При одновременной утечке базы и `PIN_PEPPER` шестизначные PIN подбираются быстро. Pepper хранится только в переменных окружения.
- Нет честной блокировки конкретного пользователя при неверном PIN: неверный PIN не идентифицирует аккаунт. Компенсация — IP и глобальные ограничения.
- Пока включён `PIN_LOOKUP_LEGACY_FALLBACK`, неверный PIN может запустить старый дорогой поиск. Окно перехода нужно ограничить и закрыть по readback.
