# План внедрения: магазины для замены у продавцов

## 1. Цель

Разрешить продавцу отправлять **«Фото звіт»** за фактический магазин, где он работает в день замены, не меняя его основной магазин и не позволяя подменить магазин запросом из браузера.

Пример результата:

- в карточке сотрудника: `Основной магазин: Шкільна`;
- ему выдан доступ на замену в `Роша`;
- в приложении он выбирает `Работаю сейчас: Роша`;
- отчёт сохраняется за Рошей;
- админка показывает: `отправила Пашник Яна; основной магазин — Шкільна; отчёт — Роша; основание — замена`.

## 2. Границы первой версии

### Входит в объём

1. Сделать основной магазин необязательным при создании и редактировании продавца.
2. Добавить в карточку продавца мультивыбор `Магазины для замены`.
3. Давать продавцу возможность выбрать фактический магазин только для категории `photo_report`.
4. Проверять доступ к выбранному магазину на сервере и в БД, а не доверять браузеру.
5. Сохранять неизменяемый контекст отчёта для аналитики и аудита.
6. Показывать в админке автора, основной магазин автора и фактический магазин отчёта.

### Не входит в первую версию

1. График смен, время начала/окончания смены и табель рабочего времени.
2. Геолокация, QR-код или доказательство физического присутствия в магазине.
3. Автоматическое назначение по расписанию.
4. Перевод на выбранный магазин других категорий заявок: HR, склад, техпроблемы и т. д.

Это сознательное ограничение: первая версия решает ошибочную атрибуцию фотоотчёта, но не должна незаметно изменить весь контур заявок.

## 3. Зафиксированные правила продукта

1. У продавца может быть ноль или один основной магазин.
2. Продавец может иметь доступ к нулю, одному или многим магазинам для замены.
3. Основной магазин сам по себе разрешён для отправки `Фото звіту`.
4. Магазин для замены разрешён только при активной записи доступа.
5. Если у продавца нет ни основного магазина, ни активного магазина для замены, отправка фотоотчёта запрещена с понятным сообщением.
6. При нескольких доступных магазинах продавец обязан выбрать фактический магазин перед отправкой.
7. Выбор магазина в интерфейсе — это только UX. Решение о праве принимает сервер по данным БД.
8. Уже созданные отчёты не переписываются и не переносятся.
9. Доступ «для замены» не означает подтверждённую смену. В аналитике его нельзя называть фактическим присутствием на смене.

## 4. Целевая модель данных

### 4.1. Существующая таблица сотрудников

`feedbackgb.users`

- `store_id` сохраняется как **основной магазин**;
- для роли `seller` допускается `NULL`;
- `store_id` больше не должен быть обязательным правилом API или формы;
- для `admin` и `super_admin` остаётся `NULL`, как и сейчас.

### 4.2. Новая таблица доступов

Создать `feedbackgb.seller_store_permissions`.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID PK | идентификатор записи доступа |
| `seller_id` | UUID FK → `feedbackgb.users(id)` | продавец |
| `store_id` | integer FK → `categories.spots(spot_id)` | магазин для замены |
| `granted_at` | timestamptz | когда выдан доступ |
| `granted_by` | UUID FK → `feedbackgb.users(id)` nullable | кто выдал доступ |
| `revoked_at` | timestamptz nullable | когда доступ отозван |
| `revoked_by` | UUID FK → `feedbackgb.users(id)` nullable | кто отозвал доступ |
| `note` | text nullable | короткая служебная причина, если потребуется |

Ограничения и индексы:

1. Один активный доступ для пары `(seller_id, store_id)`:
   уникальный частичный индекс `where revoked_at is null`.
2. Проверка, что доступ выдаётся только пользователю с ролью `seller` — серверная проверка плюс DB-trigger либо защищённая RPC-функция.
3. Индексы для серверной проверки: активные доступы по `seller_id` и по `(seller_id, store_id)`.
4. Включить RLS; отозвать доступы у `anon`/`authenticated`; выдать прямой доступ только `service_role`.
5. Не удалять доступ физически: отзыв через `revoked_at` нужен для аудита.

### 4.3. Неизменяемый контекст фотоотчёта

`feedback.store_id` уже остаётся фактическим магазином отчёта. Для исторически верной аналитики создать отдельную таблицу `feedbackgb.photo_report_attribution`:

| Поле | Тип | Назначение |
|---|---|---|
| `feedback_id` | UUID PK FK → `feedbackgb.feedback(id)` | конкретный фотоотчёт |
| `seller_id` | UUID FK → `feedbackgb.users(id)` | автор отчёта |
| `report_store_id` | integer | фактический магазин отчёта |
| `home_store_id` | integer nullable | основной магазин автора на момент отправки |
| `permission_id` | UUID nullable FK → `seller_store_permissions(id)` | использованный доступ для замены |
| `source` | text | `home_store` или `replacement_permission` |
| `created_at` | timestamptz | момент фиксации контекста |

Это обязательно для честной истории: последующее изменение карточки продавца или отзыв доступа не должны менять смысл старого отчёта.

## 5. Целевой поток

```text
Админ создаёт сотрудника
        ↓
Основной магазин (опционально) + магазины для замены (0..N)
        ↓
Продавец входит по PIN
        ↓
Приложение получает разрешённые магазины фотоотчёта
        ↓
Продавец выбирает фактический магазин из разрешённого списка
        ↓
POST /api/feedback { category: photo_report, store_id: ... }
        ↓
Сервер заново проверяет доступ в БД
        ↓
Сохраняются feedback + неизменяемая attribution
        ↓
Админка/аналитика показывают фактический магазин и автора
```

## 6. Пошаговое выполнение

Нельзя переходить к следующему шагу, пока критерий предыдущего не пройден.

### Шаг R-01. Инвентаризация текущего контура

**Что сделать**

1. Зафиксировать SHA обеих приложений, миграций и текущую схему `feedbackgb.users`.
2. Read-only запросами проверить: nullable ли `users.store_id`, число активных продавцов, число продавцов без `store_id`, число фотоотчётов.
3. Зафиксировать текущую логику: `users.store_id` → PIN-сессия → `FeedbackForm` → `/api/feedback`.

**Проверка**

- Отчёт содержит результаты read-only запросов и точные SHA.
- Нет изменений в Production.

**Готово, когда**

- Команда может доказать текущую точку принудительной подстановки магазина на сервере.

### Шаг R-02. Утверждение контракта первой версии

**Что сделать**

Подтвердить правила раздела 3, включая два принципиальных решения:

1. Основной магазин всегда является разрешённым магазином для фотоотчёта.
2. «Магазины для замены» дают право отправить отчёт, но не являются табелем смен.

**Проверка**

- Утверждённый документ или комментарий владельца продукта.

**Готово, когда**

- Нет противоречия между UI, API, аналитикой и термином «смена».

### Шаг R-03. Написать миграцию без применения

**Что сделать**

1. Создать новую forward-only миграцию после последней применённой миграции.
2. Создать `seller_store_permissions` и `photo_report_attribution`.
3. Добавить FK, partial unique index, RLS, revoke/grant, индексы и комментарии.
4. Добавить безопасный rollback-блок в комментарии: он допустим только до появления записей в новых таблицах.
5. Не изменять существующие `feedback_feed`, `feedback`, `users` и отчёты без необходимости.

**Проверка**

1. SQL выполняется на пустой тестовой базе.
2. Повторный запуск либо безопасно завершается, либо явно запрещён и описан.
3. Попытка добавить второй активный доступ одной пары завершается ошибкой уникальности.
4. Отзыв доступа и повторная выдача той же пары проходят.
5. У `anon` и `authenticated` нет прямого доступа к новым таблицам.

**Готово, когда**

- Есть SQL-файл, readback-запросы и результаты тестовой БД.

### Шаг R-04. Проверить миграцию независимым readback

**Что сделать**

В staging выполнить миграцию вручную через SQL Editor и запустить readback.

**Readback должен подтвердить**

1. Обе таблицы существуют в `feedbackgb`.
2. RLS включён.
3. FK, partial unique index и индексы существуют.
4. Существующие продавцы и фотоотчёты не изменились.
5. В новых таблицах нет строк до начала функциональных тестов.

**Готово, когда**

- Результаты readback приложены к отчёту.

### Шаг R-05. Изменить API создания и редактирования сотрудника

**Что сделать**

1. Убрать требование `store_id` для роли `seller` из POST/PATCH API.
2. Сохранить проверку существования магазина, если `store_id` передан.
3. Добавить POST/GET/PATCH API только для управления магазинами для замены.
4. Все write-операции должны требовать admin/super_admin, логироваться в audit log и сохранять `granted_by`/`revoked_by`.
5. Обновить контракт TypeScript и тесты.

**Проверка API**

| Сценарий | Ожидаемый результат |
|---|---|
| создать продавца без основного магазина | 200, `store_id = null` |
| создать продавца с существующим магазином | 200 |
| создать продавца с несуществующим магазином | 400 |
| выдать доступ продавцу к Роше | 200 и audit event |
| выдать тот же активный доступ повторно | 409/предсказуемая ошибка |
| выдать доступ админу | 400/403 |
| отозвать доступ | 200, запись не удалена |
| неавторизованный запрос | 403 |

**Готово, когда**

- Все сценарии покрыты автоматическими route-тестами.

### Шаг R-06. Изменить карточку сотрудника в админке

**Что сделать**

1. В форме создания заменить обязательное поле `Магазин` на необязательное `Основной магазин`.
2. В форме редактирования добавить мультивыбор `Магазины для замены`.
3. Для каждого доступного магазина показать понятный статус: активен / отозван, дату и автора изменения.
4. Не показывать PIN после создания и не включать его в аудит/логи браузера.
5. В списке сотрудников разделить отображение: `Основной магазин` и `Магазины для замены`.

**Проверка UI**

1. Можно создать продавца без основного магазина.
2. Можно добавить 0, 1 и несколько магазинов для замены.
3. Повтор одного магазина не появляется.
4. Отзыв доступа подтверждается и отображается после обновления страницы.
5. Пользователь с ролью admin не может выдать права за пределами своего разрешённого RBAC.

**Готово, когда**

- UI не создаёт возможность выбирать произвольный ID магазина.

### Шаг R-07. Добавить read-маршрут разрешённых магазинов в приложении

**Что сделать**

Создать защищённый маршрут, например `GET /api/auth/photo-report-stores`, возвращающий только:

- основной магазин, если он есть;
- активные магазины для замены;
- понятные метки происхождения (`home_store`, `replacement`).

Маршрут не должен возвращать PIN, хеши, все магазины сети или чужие разрешения.

**Проверка**

1. Продавец Школьной с доступом к Роше получает только Школьную и Рошу.
2. Продавец без доступов получает пустой список.
3. Админ/суперадмин получают контракт, определённый в ТЗ, либо не используют этот маршрут.
4. Отозванный магазин исчезает из ответа.

**Готово, когда**

- Route-тесты подтверждают отсутствие лишних магазинов.

### Шаг R-08. Изменить форму «Фото звіт» в приложении

**Что сделать**

1. Только для `photo_report` заменить заблокированный магазин на контрол `Де працюю зараз`.
2. Если доступен один магазин — подставить его автоматически и показать название.
3. Если доступны несколько — требовать явный выбор.
4. Если магазинов нет — скрыть загрузку фото и показать: `Для вас не призначено магазин для фото звіту. Зверніться до адміністратора.`
5. Нельзя использовать локальный предыдущий выбор без сверки с серверным списком.
6. В offline-черновик сохранять выбранный фактический магазин; при отправке после восстановления сети сервер обязан проверить право заново.

**Проверка UI**

1. У продавца только Школьная → выбор отсутствует, отчёт идёт в Школьную.
2. У продавца Школьная + Роша → можно выбрать Рошу.
3. У продавца без магазинов → отправка недоступна.
4. После отзыва Роши открытая форма не может отправить отчёт за Рошу.
5. Не-фото формы сохраняют прежнее поведение и основной магазин.

**Готово, когда**

- Ни один путь интерфейса не отправляет магазин вне полученного разрешённого списка.

### Шаг R-09. Сделать серверную проверку при создании фотоотчёта

**Что сделать**

Изменить только ветку `category === "photo_report"` в `POST /api/feedback`:

1. Принять выбранный `store_id` как кандидат.
2. На сервере загрузить текущий основной магазин и активные доступы автора.
3. Разрешить магазин только при совпадении с основным или активным доступом.
4. При отказе вернуть 403 с нейтральным сообщением; не загружать фото в Storage до проверки.
5. После успешной записи фотоотчёта создать неизменяемую `photo_report_attribution`.
6. Логировать только `user_id`, `requested_store_id`, `resolved_store_id`, результат и request ID. Не логировать фото, PIN, cookie или текст полей.

**Критические тесты API**

| Сценарий | Ожидаемый результат |
|---|---|
| основной магазин Шкільна | отчёт принят за Школьную |
| разрешённая замена Роша | отчёт принят за Рошу |
| чужой магазин | 403, без записи и без файлов Storage |
| отозванная Роша | 403 |
| `store_id` отсутствует при двух доступных магазинах | 400 |
| подмена `store_id` в HTTP-клиенте | 403 |
| повтор `client_submission_id` | прежняя идемпотентность сохраняется |
| offline-очередь после отзыва доступа | 403, файлы не становятся сиротами |

**Готово, когда**

- Тесты доказывают, что сервер, а не UI, является точкой контроля.

### Шаг R-10. Обновить аналитику и админский просмотр

**Что сделать**

1. В daily-таблице и галерее сохранить группировку по `feedback.store_id` — это фактический магазин отчёта.
2. Добавить автору подпись: `Основной: Шкільна` только если он отличался от фактического магазина.
3. Добавить метку `Заміна` для `source = replacement_permission`.
4. В тепловой карте показывать автора отчёта; не называть его «был на смене» без будущего отдельного учёта смен.
5. Использовать `photo_report_attribution`, а не текущую карточку пользователя, для исторических данных.

**Проверка**

1. Отчёт Яны за Рошу входит в счётчики Роши, а не Школьной.
2. При изменении её основного магазина старая запись не меняет подпись.
3. Галерея Роши содержит её фотографии.
4. Строка Школьной не получает ложный отчёт.

**Готово, когда**

- Сквозной тест подтверждает одинаковую атрибуцию в API, таблице, галерее и тепловой карте.

### Шаг R-11. Сквозное тестирование на изолированных тестовых сотрудниках

**Что сделать**

В staging создать два тестовых продавца и два тестовых магазина/разрешения, не используя Production.

**Обязательный сценарий**

1. Создать Яну с основным магазином Шкільна.
2. Выдать ей Рошу в «Магазины для замены».
3. Войти её PIN в приложении.
4. Выбрать Рошу, отправить один фотоотчёт с 1–2 тестовыми изображениями.
5. Открыть admin → Фото звіт → Контроль дня/Магазины.
6. Подтвердить, что отчёт, фото, автор и метка замены находятся у Роши.
7. Отозвать Рошу, повторить попытку и подтвердить 403 без Storage-мусора.

**Готово, когда**

- В отчёте приложены ID созданных тестовых строк, API-ответы, скриншоты и readback SQL.

## 7. SQL readback: обязательный минимум

После миграции команда должна приложить результаты запросов, подтверждающих:

1. Существование новых таблиц, PK, FK, индексов и RLS.
2. Нет повторяющихся активных доступов `(seller_id, store_id)`.
3. Все `photo_report_attribution.report_store_id` совпадают с `feedback.store_id`.
4. Все `photo_report_attribution.seller_id` совпадают с `feedback.user_id`.
5. Нет attribution без соответствующего `feedback`.
6. Нет фотоотчётов, принятых за магазин без основного магазина или активного разрешения на момент записи.
7. Старые фотоотчёты остались неизменны; отсутствие attribution у старых строк обозначено как `legacy`, а не как ошибка.

## 8. Критерии приёмки

Функция принимается, только если одновременно выполнены все пункты:

1. Продавца можно создать без основного магазина.
2. Админ может выдать и отозвать несколько магазинов для замены с аудитом.
3. Продавец видит и выбирает только разрешённые магазины для `Фото звіту`.
4. Подмена `store_id` вне разрешений отвергается сервером до загрузки файлов.
5. Фотоотчёт замещающего продавца учитывается у фактического магазина.
6. Исторический основной магазин и основание доступа сохраняются рядом с отчётом.
7. Старые отчёты и другие категории заявок не изменили поведение.
8. Пройдены unit, integration, staging и production smoke tests.
9. Нет неподтверждённых утверждений о фактическом присутствии продавца на смене.

## 9. Откат

1. До появления production-записей: откатить deploy обеих приложений и удалить новые таблицы только после подтверждения их пустоты.
2. После появления записей: не удалять таблицы и историю; отключить UI выбора замены feature flag/серверной конфигурацией, вернуть прежний основной-магазинный путь и сохранить данные для расследования.
3. Никогда не переносить существующие фотоотчёты между магазинами массовым обновлением без отдельного письменного решения.

## 10. Открытые решения до начала разработки

1. Разрешается ли обычному admin выдавать доступы ко всем магазинам или только super_admin?
2. Нужно ли ограничивать число магазинов для замены у одного продавца?
3. Нужна ли причина выдачи/отзыва доступа в первой версии?
4. Можно ли отправить фотоотчёт за основной магазин без явного выбора, когда есть также магазины для замены?
5. Кто является единственным допустимым тестовым продавцом для production smoke test?
