## Как читать этот документ

Каждый шаг содержит пять обязательных блоков:

- **Что не так** — дефект и его место в коде.
- **Что сделать** — конкретное изменение, а не направление мысли.
- **Критерий проверки** — команда, запрос или тест, который даёт однозначный ответ «да/нет». Если критерий нельзя выполнить, шаг не считается закрытым.
- **Готово, когда** — определение завершённости.
- **Откат** — как вернуть, если стало хуже.

Шаг закрывается только после того, как критерий выполнен **и** результат внесён в журнал (раздел 12). Шаги без отметки в журнале при приёмке считаются невыполненными.

## Этап 0. Зафиксировать факты и остановить неконтролируемые изменения

Цель этапа — получить достоверную картину сред. Сейчас документ ветки и реальная база противоречат друг другу, поэтому ни один вывод о готовности проверить нельзя.

### R-01. Зафиксировать реальное состояние миграций по всем средам

**Приоритет:** BLOCKER · **Роль:** DevOps · **Источник:** BLOCKER-3

**Что не так.** `PHOTO_REPORT_IMPLEMENTATION_PLAN.md:191` утверждает, что миграция 023 не применена. Фактически она применена, а 024 — нет. Статус-таблица в документе недостоверна.

**Что сделать.** Заменить текстовую таблицу статусов на выводимый readback. Для каждой среды (dev / staging / production) выполнить проверочный запрос и приложить его вывод к отчёту.

```sql
-- Фактическое состояние миграций функции
select
  (select count(*) from feedbackgb.categories where id = 'photo_report')            as m023_category,
  (select count(*) from pg_indexes
     where schemaname = 'feedbackgb' and indexname = 'audit_log_action_occurred_at_idx') as m024_index,
  (select count(*) from information_schema.columns
     where table_schema = 'feedbackgb' and table_name = 'feedback_feed'
       and column_name = 'photo_urls')                                              as feed_photo_urls,

```

**Критерий проверки.** В отчёте есть три вывода запроса — по одному на среду — с датой и именем базы. Ожидаемое для готовой среды: `m023_category = 1`, `m024_index = 1`, `feed_photo_urls = 1`.

**Готово, когда.** Таблица статусов в `PHOTO_REPORT_IMPLEMENTATION_PLAN.md` заменена ссылкой на этот запрос и на журнал выполнения; текстовых утверждений о статусе миграций в документах не осталось.

**Откат.** Не требуется — изменения только в документации.

## Этап 1. Вход в систему — блокирующий этап

Это единственный этап, который блокирует нагрузочный тест. Пока одна попытка входа стоит 3 772 мс процессорного времени базы, любой замер под нагрузкой измеряет bcrypt, а не функцию.

### R-04. Продуктовое решение: остаётся ли вход только по PIN

**Приоритет:** CRITICAL · **Роль:** владелец системы + архитектор · **Источник:** CRIT-1, CRIT-2

**Что не так.** Оба критических дефекта аутентификации вытекают из одного свойства: PIN опознаёт пользователя сам, без идентификатора. Из этого следует и перебор всех хешей, и невозможность блокировки конкретной учётной записи — неверный PIN не указывает ни на кого, поэтому увеличивать счётчик неудач не у кого.

**Что сделать.** Выбрать один из двух путей и зафиксировать выбор.

| | **Путь A — идентификатор + PIN** | **Путь B — детерминированный ключ поиска** |
| --- | --- | --- |
| UX | продавец вводит табельный номер и PIN | без изменений, только PIN |
| Хешей на попытку | 1 | 1 |
| Блокировка учётной записи | работает штатно | невозможна, только по IP и глобальная |
| Риск при утечке БД | прежний | при утечке **и** БД, и секрета pepper 6 цифр перебираются мгновенно |
| Объём работ | средний, меняется экран входа | средний, экран входа не меняется |

Рекомендация: **путь B** как основной — он не меняет привычный сценарий для 53 продавцов и решает проблему производительности полностью. Путь A следует выбрать, если блокировка конкретной учётной записи является требованием безопасности, от которого нельзя отказаться.

**Критерий проверки.** Решение зафиксировано письменно с указанием принявшего, даты и обоснования. Дальнейшие шаги R-05…R-07 написаны под путь B; при выборе пути A они переписываются до начала работ.

**Готово, когда.** Решение принято.

### R-05. Убрать перебор всех хешей при входе

**Приоритет:** CRITICAL · **Роль:** разработка + архитектор · **Источник:** CRIT-1
**Где:** `feedback-admin/supabase/017_fix_pgcrypto_search_path.sql:62-108`, `*/src/app/api/auth/login/route.ts`

**Что не так.** `verify_pin_global` в цикле сравнивает введённый PIN с хешем каждого активного пользователя и не выходит из цикла при совпадении. Стоимость — 60 операций bcrypt на каждую попытку, измерено 3 772 мс.

**Что сделать.**

1. Добавить в `feedbackgb.users` колонку `pin_lookup bytea` и уникальный частичный индекс по ней. Уникальность заодно закрывает сценарий «два продавца с одинаковым PIN», который сейчас отлавливается только в рантайме.
2. Значение `pin_lookup` считать **в приложении**, а не в базе: `HMAC-SHA256(pin, PIN_PEPPER)`, где `PIN_PEPPER` живёт в переменных окружения и в базу не попадает. Это важно: если секрет хранить в БД, он утечёт вместе с ней.
3. Новая функция входа принимает готовый `pin_lookup`, делает поиск по индексу и проверяет bcrypt **одной** операцией для найденной строки.
4. На время перехода оставить запасной медленный путь: если поиск по индексу ничего не дал, один раз выполнить прежний перебор и при успехе записать `pin_lookup` для этого пользователя. Так колонка заполняется сама по мере входов, без перевыпуска PIN-кодов.
5. Для пользователей, не заходивших за период перехода, — принудительный перевыпуск PIN через существующий механизм `set_user_pin` (он должен заполнять `pin_lookup`).
6. **Отдельным шагом удалить запасной путь** — пока он существует, вектор нагрузки открыт.

**Критерий проверки.**

1. Стоимость попытки входа после заполнения `pin_lookup`:

```sql
-- Повторить замер из аудита: должен упасть с 3772 мс
with t0 as materialized (select clock_timestamp() as a),
 work as materialized (
   select max(length(household_chemicals.crypt('000000', u.pin_hash))) as c, count(*) as n
     from feedbackgb.users u, t0
    where u.is_active and u.pin_hash is not null
      and (u.locked_until is null or u.locked_until <= now()))
select w.n as hashes_computed,
       round(extract(epoch from (clock_timestamp() - t.a)) * 1000) as elapsed_ms
  from t0 t, work w;
```

Этот запрос показывает стоимость **старого** пути. Новый критерий — измерить сам эндпоинт: 50 последовательных неуспешных входов на staging, **p95 < 150 мс** (одна операция bcrypt плюс сеть).

2. Полнота заполнения колонки:

```sql
select count(*) filter (where pin_lookup is null) as not_migrated,
       count(*)                                    as total
  from feedbackgb.users
 where is_active and pin_hash is not null;
-- критерий: not_migrated = 0
```

3. Запасной путь удалён из кода: поиск по репозиторию не находит цикла по всем пользователям в функции входа.

**Готово, когда.** `not_migrated = 0`, p95 неуспешного входа на staging < 150 мс, запасной путь удалён, секрет `PIN_PEPPER` задан во всех средах и отсутствует в репозитории и логах.

**Откат.** Прежняя функция сохраняется под другим именем до окончания этапа 6; переключение — одной заменой вызова в маршруте входа. Колонка `pin_lookup` при откате не мешает.

### R-06. Восстановить защиту от перебора

**Приоритет:** CRITICAL · **Роль:** разработка + безопасность · **Источник:** CRIT-2
**Где:** `shared/lib/rateLimit.ts`, `*/src/app/api/auth/login/route.ts`

**Что не так.** Счётчик `failed_attempts` после миграции 009 не увеличивается никогда — блокировка учётной записи мертва. Единственная защита, IP-лимит, берёт адрес из первого элемента `X-Forwarded-For`, который на self-hosted прокси подставляется клиентом.

**Что сделать.**

1. Брать IP из доверенного источника: либо последний элемент цепочки `X-Forwarded-For` (добавленный вашим прокси), либо выделенный заголовок, который прокси перезаписывает. Одновременно настроить прокси так, чтобы входящий `X-Forwarded-For` от клиента отбрасывался.
2. Ввести экспоненциальную задержку по ключу «IP + окно»: после 5 неудач — задержка ответа, после 10 — отказ на нарастающий срок.
3. Добавить глобальный предохранитель: если доля неуспешных входов по системе превышает порог за минуту, включать дополнительное трение и поднимать алерт. Это защита именно от сценария «подобрать хоть чей-нибудь PIN».
4. Честно задокументировать в `SECURITY`-разделе, что блокировка конкретной учётной записи при входе только по PIN невозможна, и указать, чем она заменена.
5. Привести в порядок админскую кнопку «Розблокувати»: она управляет счётчиком, который больше не растёт. Либо связать её с новым механизмом, либо убрать.
6. Необязательное усиление: увеличить длину PIN с 6 до 8 цифр. При 60 активных PIN это снижает вероятность попадания со случайной попытки примерно с 1 к 17 тысячам до 1 к 1,25 миллиона.

**Критерий проверки.**

1. Подмена заголовка не влияет на лимит. На staging выполнить 15 запросов входа с разными значениями `X-Forwarded-For`:

```bash
for i in $(seq 1 15); do
  curl -s -o /dev/null -w "%{http_code}\n" \
    -X POST "$STAGING/api/auth/login" \
    -H "content-type: application/json" \
    -H "x-forwarded-for: 10.0.0.$i" \
    -d '{"pin":"000000"}'
done
```

Критерий: начиная с 11-го запроса возвращается `429`. Если все 15 отвечают `401`, защита обходится и шаг не закрыт.

2. Счётчик неудач по IP фиксируется в БД:

```sql
select key, count(*) from feedbackgb.rate_limits
 where key like 'login:ip:%' group by key order by 2 desc limit 5;
```

3. В `audit_log` присутствуют события неуспешного входа с IP; PIN в них отсутствует:

```sql
select count(*) as pin_leaks
  from feedbackgb.audit_log
 where action like 'auth.%'
   and (meta::text ~ '\d{6}' or meta::text ilike '%pin%');
-- критерий: 0
```

**Готово, когда.** Все три критерия выполнены, решение по длине PIN принято и зафиксировано.

**Откат.** Пороговые значения вынести в переменные окружения — при ложных срабатываниях ослабляются без развёртывания.

### R-07. Проверить, что перегрузка входа больше не блокирует вход

**Приоритет:** HIGH · **Роль:** QA + DevOps · **Источник:** CRIT-1

**Что не так.** Лимитер в production «фейлится закрыто»: при недоступной или перегруженной базе `rateLimit()` бросает исключение, и маршрут входа отвечает 503. Перегрузка, вызванная самими входами, блокировала входы.

**Что сделать.** После R-05 повторить сценарий и убедиться, что каскад исчез. Отдельно предусмотреть, что при недоступности базы сообщение пользователю остаётся понятным, а событие попадает в лог с `request_id`.

**Критерий проверки.** На staging — 100 одновременных входов реальных тестовых сессий. Критерий: **100 % ответов 2xx**, p95 < 1 с, в логах нет `telemetry.rate_limit.failed` и нет ответов 503 от маршрута входа.

**Готово, когда.** Критерий выполнен и вывод приложен к отчёту этапа.

## Этап 2. Целостность данных и файлов

### R-08. Не терять файлы при ошибке записи в базу

**Приоритет:** HIGH · **Роль:** разработка · **Источник:** HIGH-1
**Где:** `feedback-app/src/app/api/feedback/route.ts:278-310`

**Что не так.** Единственный вызов `storage.remove` относится к частичной загрузке. Если все 15 фото загрузились, а вставка строки упала, файлы остаются в приватном бакете навсегда, и их пути нигде не записаны. ТЗ §3 требует либо очистку, либо журналирование задачи на очистку.

**Что сделать.** В ветке ошибки вставки удалить загруженные объекты тем же способом, что и при частичной загрузке. Если удаление не удалось — записать событие `photo_report.orphan_pending` с **полным списком путей**, чтобы фоновая задача могла их убрать.

**Критерий проверки.** Интеграционный тест: замокать ошибку вставки при 15 успешно загруженных фото. Критерий: ответ 500, в бакете не осталось ни одного из 15 объектов **либо** в логе присутствует событие со всеми 15 путями. Проверка на данных — запрос `orphan_objects` из R-10 возвращает 0 после прогона.

**Готово, когда.** Тест в наборе и проходит; ручной прогон подтверждает отсутствие сирот.

**Откат.** Изменение локальное, откатывается коммитом.

### R-09. Записывать пути в событии неудавшегося отката

**Приоритет:** HIGH · **Роль:** разработка · **Источник:** HIGH-2
**Где:** `feedback-app/src/app/api/feedback/route.ts:151`

**Что не так.** Событие `photo_report.cleanup_failure` содержит только количество файлов. Комментарий в коде объясняет, что лог нужен, чтобы «отследить и удалить» осиротевшие объекты, — но по количеству отследить нечего.

**Что сделать.** Добавить в событие массив путей. Пути состоят из даты и случайного UUID, персональных данных не содержат, поэтому требование «не логировать PII» не нарушается.

**Критерий проверки.** Тест с подставленной ошибкой удаления: в выводе события присутствует массив из N путей, где N равно числу загруженных файлов. Проверка на отсутствие утечек — в событии нет base64, cookie и PIN.

**Готово, когда.** Тест проходит, образец события приложен к отчёту.

### R-10. Фоновая сверка бакета с базой

**Приоритет:** HIGH · **Роль:** разработка + DevOps · **Источник:** HIGH-1
**Основание:** в бакете лежат 2 файла-сироты от 2026-05-01 — процесса очистки не существует вовсе.

**Что сделать.** Задание по расписанию (раз в сутки), которое выполняет сверку и удаляет объекты старше 24 часов, на которые не ссылается ни одна строка. Порог в 24 часа защищает от гонки с только что загруженными файлами.

```sql
-- Основа задания: те же множества, что и в аудите
with refs as (
  select 'sb:' || o.name as storage_ref, o.name, o.created_at
    from storage.objects o where o.bucket_id = 'feedback-photos'
), db_refs as (
  select jsonb_array_elements_text(f.fields->'photo_urls') as ref
    from feedbackgb.feedback f where jsonb_typeof(f.fields->'photo_urls') = 'array'
  union
  select f.photo_url from feedbackgb.feedback f where f.photo_url is not null
)
```

## 13. Правила, действующие на всё время работ

1. **Не запускать нагрузочный тест по рабочей среде** — ни целиком, ни частично, ни «одним пользователем для проверки».
2. **Не закрывать шаг без выполненного критерия.** Формулировка «сделано, выглядит нормально» не принимается — в журнал вносится фактический вывод команды.
3. **Не повторять упавший нагрузочный прогон до разбора причины.** Повторный запуск маскирует дефект.
4. **Не расширять область.** Найденное попутно вносится в журнал отдельной строкой и приоритизируется отдельно, а не чинится внутри текущего шага.
5. **Не писать в логи** PIN, cookie, токены, base64 фотографий, содержимое личных комментариев и персональные данные сверх служебного идентификатора.
6. **Изменения в рабочей среде** — только после прохождения приёмки и только через согласованный канал.
