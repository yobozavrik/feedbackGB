## 1. Зачем этот документ

Отчёт о выполнении плана утверждает, что код готов и проверен локально. Независимая проверка подтвердила тесты (162/162 и 221/221), но нашла две критические ошибки во входе, которые тесты не покрывают, и расхождение отчёта с рабочей базой.

Цель ТЗ — получить от команды **проверяемые доказательства** по каждому пункту ниже. Проверяющий не принимает формулировки «проверено», «работает», «всё ок». Принимается только фактический вывод команды, запроса или теста, по которому можно повторить проверку.

После получения отчёта проверяющий выборочно повторит часть пунктов сам — чтением кода и read-only запросами. Расхождение отчёта с повторной проверкой отклоняет весь блок, а не только пункт.

## 3. Обязательные правила на время проверок

1. **Никаких записей в рабочую базу.** Сюда относится и Preview: по факту F-8 он пишет в боевую базу. Все проверки с записью — только на staging с отдельной базой.
2. **Не задавать `PIN_PEPPER` и `PIN_LOOKUP_LEGACY_FALLBACK` в Preview**, пока у Preview общая с Production база. Backfill с pepper Preview испортит ключи боевых пользователей.
3. **Не отключать Deployment Protection** на Preview.
4. **Не вызывать** на рабочей базе `set_user_pin`, `backfill_pin_lookup` и любые функции, меняющие `users`.
5. **Не выдавать моки за интеграционную проверку.** Если пункт требует реального Storage или реальной базы, юнит-тест с моками его не закрывает — это нужно указать явно.
6. Пункт, который нельзя выполнить без staging, получает статус `blocked` с причиной. **Подменять staging рабочей средой запрещено.**
7. В логах, отчётах и скриншотах не должно быть PIN, значения `PIN_PEPPER`, cookie, токенов и base64 фотографий.

## 4. Порядок работ

```
Блок A (среды и происхождение) ──┐
                                 ├─→ Блок B (исправления входа) ─→ Блок C (переход на ключи)
                                 │
                                 ├─→ Блок D (целостность фотоотчётов)
                                 ├─→ Блок E (админка)
                                 └─→ Блок F (безопасность)
                                                  │
                           Блок G (staging, нагрузка, устройства) ← только после A-1…A-4 и B
```

Блоки A и B — первые и обязательные. Блоки D, E, F можно вести параллельно с B. Блок G начинается только после того, как есть staging с отдельной базой (A-4) и закрыты критические пункты блока B.

## 6. Блок B. Критические исправления входа

Пункты B-1 и B-2 — **блокирующие**. Пока они не закрыты, вход по новой схеме нельзя включать ни в одной среде, где есть реальные пользователи.

### B-1. Лимит неудач проверяется до проверки PIN

**Что не так (факт F-12).** В `feedback-app/src/app/api/auth/login/route.ts` и `feedback-admin/src/app/api/auth/login/route.ts` лимиты `login:failure:ip:*` и `login:failure:global` проверяются только внутри `failedLogin()`, после вызова верификатора. Отсюда два следствия:
- верный PIN с заблокированного IP выдаёт сессию — ограничение не мешает перебору;
- при `PIN_LOOKUP_LEGACY_FALLBACK=true` каждый заблокированный запрос всё равно запускает `verify_pin_global` (замер: 3 772 мс CPU базы).

**Что должно быть после исправления.** Состояние лимитов читается **до** вызова любого верификатора. Если IP или глобальный лимит исчерпан, ответ 429 **даже при верном PIN**, cookie не выставляется, RPC верификации не вызывается.

**Как проверить — обязательные автотесты в обоих приложениях:**

| Тест | Ожидаемый результат |
| --- | --- |
| IP-лимит исчерпан, PIN **верный** | 429, заголовка `Set-Cookie` нет, `verify_pin_lookup` не вызван |
| IP-лимит исчерпан, PIN неверный | 429, верификатор не вызван |
| Глобальный лимит исчерпан, PIN верный | 429, cookie нет |
| Fallback включён, IP-лимит исчерпан | `verify_pin_global` **не вызван** |
| Лимит не исчерпан, PIN верный | 200, cookie выставлен |
| База лимитов недоступна | 503, верификатор не вызван |

**Как проверить на staging.** 11 неуспешных попыток с одного IP, затем 12-я — с верным PIN тестового пользователя:

```bash
for i in $(seq 1 11); do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST "$STAGING_APP/api/auth/login" \
    -H "content-type: application/json" -d '{"pin":"000000"}'
done
curl -s -D - -o /dev/null -X POST "$STAGING_APP/api/auth/login" \
  -H "content-type: application/json" -d "{\"pin\":\"$TEST_PIN\"}"
```

**Ожидаемый результат.** Последний ответ — `429`, в заголовках нет `set-cookie`.

**Приложить.** Имена тестов и вывод прогона; вывод staging-сценария (PIN замаскировать).

### B-2. Запрет совпадения PIN на период перехода

**Что не так (факт F-13).** Новая `set_user_pin(uuid,text,text)` полагается на уникальный индекс `users_pin_lookup_unique_active_idx`, а он не видит пользователей с пустым `pin_lookup` — сейчас это все 60. Сценарий:
1. у продавца A (legacy, `pin_lookup is null`) PIN `X`;
2. админ создаёт или сбрасывает пользователя B с тем же PIN `X` — операция проходит;
3. A входит со своим PIN → `verify_pin_lookup` находит строку B → **A получает сессию B**. Если B — админ, продавец получает права админа.

**Что должно быть после исправления.** `set_user_pin` отклоняет PIN, совпадающий с PIN **любого** другого активного пользователя: по `pin_lookup` (индекс) и по bcrypt для строк, где `pin_lookup is null`. Ошибка — `unique_violation`, как в старой версии.

**Как проверить на staging:**

| Шаг | Ожидаемый результат |
| --- | --- |
| Создать legacy-пользователя A с PIN `X` старой функцией, `pin_lookup` пустой | успех |
| Создать пользователя B с PIN `X` через `POST /api/admin/users` | ошибка, пользователь без PIN не активирован |
| Сбросить PIN существующему пользователю C на `X` через `POST /api/admin/users/{id}/pin` | ошибка |
| Войти с PIN `X` | сессия A, не B и не C |
| Повторить при заполненном `pin_lookup` у A | ошибка на шагах 2–3 |

Контрольный запрос после сценария:

```sql
-- ни у одного PIN не должно быть двух активных владельцев
select pin_lookup, count(*) from feedbackgb.users
 where is_active and pin_lookup is not null
 group by pin_lookup having count(*) > 1;
-- ожидается: пусто
```

**Приложить.** Вывод каждого шага (коды ответов, текст ошибки без PIN), `uid` сессии на шаге 4, вывод контрольного запроса. Плюс автотест на уровне SQL или маршрута, воспроизводящий сценарий.

### B-3. Старая `set_user_pin(uuid,text)` не может испортить ключ

**Что не так (факт F-4).** Двухаргументная версия осталась в базе, а комментарии в миграциях `002`, `009` и `schema.sql` советуют операторам вызывать именно её. Она меняет `pin_hash` и не трогает `pin_lookup` — ключ остаётся от старого PIN. Дальше:
- fallback выключен → пользователь не может войти;
- fallback включён → старый верификатор пропускает, `backfill_pin_lookup` возвращает `false`, маршрут отвечает 500 на каждую попытку.

**Что должно быть после исправления.** Двухаргументная версия удалена, либо выбрасывает исключение с понятным текстом. Комментарии в миграциях и runbook обновлены.

**Как проверить на staging:**

```sql
select pg_get_function_identity_arguments(p.oid)
  from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'feedbackgb' and p.proname = 'set_user_pin';
-- ожидается: одна строка с тремя аргументами
-- либо вызов двухаргументной версии завершается исключением
```

**Приложить.** Вывод запроса, текст исключения (если выбран этот вариант), список обновлённых комментариев и runbook с путями.

### B-4. Выключенный fallback не отключает вход незаметно

**Что не так.** По умолчанию `PIN_LOOKUP_LEGACY_FALLBACK` выключен. Если развернуть код при `not_migrated > 0` и забыть флаг, все пользователи с пустым ключом (сейчас 60 из 60) не смогут войти, а в логах будут выглядеть как обычные неверные PIN.

**Что должно быть.** Когда верификатор по ключу не нашёл пользователя, fallback выключен, а в базе есть активные пользователи без ключа, пишется отдельное событие уровня `error` (например `auth.pin_lookup.unmigrated_users_without_fallback`) с числом таких пользователей, без PIN. Проверка кэшируется и не выполняется на каждый запрос.

**Как проверить.** Автотест: fallback выключен, пустые ключи есть, неверный вход → событие записано. Staging: развернуть без флага при `not_migrated > 0` и найти событие в логах по `request_id`.

**Приложить.** Имя теста, строку лога со staging.

**Проверить:**
1. PIN, выданный в админке, принимается при входе в приложение продавца. Это доказывает равенство pepper в обоих проектах.
2. Значения нет в клиентском бандле, логах и репозитории.

**Ожидаемый результат.** `clean` для обоих бандлов, `gitleaks` без находок, вход на staging успешен.

**Приложить.** Вывод команд, код ответа входа.

### B-6. Защита от перебора описана честно

## 8. Блок D. Целостность фотоотчётов

Всё — на staging с реальным Storage. Юнит-тесты с моками прикладываются дополнительно, но пункты не закрывают (правило 5).

Подсчёт для постпроверки каждого сценария:

```sql
with refs as (
  select 'sb:' || o.name as storage_ref from storage.objects o
   where o.bucket_id = 'feedback-photos'
), db_refs as (
  select jsonb_array_elements_text(f.fields->'photo_urls') as ref
    from feedbackgb.feedback f where jsonb_typeof(f.fields->'photo_urls') = 'array'
  union
  select f.photo_url from feedbackgb.feedback f where f.photo_url is not null
)
select
 (select count(*) from storage.objects where bucket_id = 'feedback-photos') as storage_objects,
 (select count(*) from refs r where not exists (select 1 from db_refs d where d.ref = r.storage_ref)) as orphan_objects,
 (select count(*) from db_refs d where d.ref like 'sb:%'
     and not exists (select 1 from refs r where r.storage_ref = d.ref)) as missing_objects;
```

Для каждого сценария — вывод **до и после**.
