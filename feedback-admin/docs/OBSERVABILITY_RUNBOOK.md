# Диагностика FeedbackGB

## Что фиксируется

| Источник | Место | Для чего |
|---|---|---|
| Каждый запрос к seller app и admin panel | Vercel Runtime Logs | `request_id`, метод, путь, решение middleware (`allow`, `unauthenticated`, `forbidden`) |
| Ошибка браузера / необработанное Promise | `feedbackgb.audit_log`, действие `client.error` | Приложение, маршрут, сообщение и stack (обрезаны и очищены от PIN/токенов) |
| Вход, выход, фидбек, изменение статуса, PIN, управление пользователями | `feedbackgb.audit_log` | Кто, когда, что изменил |
| Фотоотчёт | `feedback`, Storage и `audit_log` | Создание записи, фото, магазин, отправитель |

Не сохраняются: PIN, cookie, Authorization-заголовки, тела запросов, тексты форм и сами фото.

## Как найти проблему

1. Попросить пользователя прислать время, экран и `x-request-id` из ответа API, если он доступен.
2. Открыть Vercel → проект → Logs и отфильтровать по `request_id` или маршруту.
3. В админ-панели открыть «Журнал дій», отфильтровать действие `Помилка застосунку` и развернуть строку: в `meta` будут `route`, `message`, `stack`, `request_id`.
4. Для данных фотоотчёта сопоставить время, магазин, автора и `feedback_id` в журнале.

## Ограничения

- `/admin/audit` показывает последние 500 записей. Полный поток HTTP-запросов хранится в Vercel Runtime Logs, а не в Supabase.
- Для отображения `client.error` как «Помилка застосунку» необходимо применить миграцию `024_observability_client_errors.sql`.
- Сквозной E2E-тест авторизованных сценариев требует PIN двух тестовых продавцов и отдельного тестового администратора. Не использовать реальные аккаунты и не отправлять PIN в общий чат.
