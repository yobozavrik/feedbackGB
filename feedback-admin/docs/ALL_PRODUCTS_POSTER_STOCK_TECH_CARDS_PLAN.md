# План: залишки та технологічні карти для всіх карток продуктів

Дата базової перевірки: 2026-09-23, близько 09:02 UTC. Статус: **базові вкладки вже реалізовані; кроки цього плану ще не виконувалися**.

## 1. Мета і межі

Кожна картка у `Мережа → Технолог → Продукти → категорія → продукт` повинна відкривати вкладки `Залишки` і `Технологічна карта`. Дані беруться безпосередньо з Poster на запит, із часом фактичного отримання. Відсутність даних у Poster не перетворюється на нуль і не заповнюється припущеннями.

**Важливе уточнення:** самі вкладки й серверні маршрути вже універсальні за `product_id` (коміти `887bf72` і `6937fc9`). Завдання не в тому, щоб скопіювати реалізацію 372 рази. Потрібно довести покриття всього каталогу, правильно класифікувати непокриті типи, прибрати оманливі загальні помилки й перевірити навантаження.

У межах цього етапу: лише читання Poster, відображення та діагностика. Не змінювати рецептури, залишки чи налаштування Poster; не записувати живі залишки в Supabase; не міняти міграції без окремої потреби та погодження.

## 2. Перевірений стан на дату плану

Джерела перевірки: `feedbackgb.v_products` у Supabase (тільки каталог карток), прямі read-only `menu.getProducts`, `menu.getPrepacks`, `menu.getProduct` і `storage.getStorageLeftovers` у Poster. Підрахунки є знімком, не постійними нормативами.

| Група карток | Кількість | Залишки готового продукту | Техкарта |
| --- | ---: | --- | --- |
| Страви Poster з `ingredient_id` | 325 | Є рядок в усіх 26 складах | Є склад рецепта |
| Страви Poster без `ingredient_id` | 18 | Немає складського ID, не можна показувати залишок готового продукту | Є склад рецепта |
| Товари Poster зі складським ID і рядками на 26 складах | 8 | Є | Рецепта немає (для цього типу нормально) |
| Товари Poster зі складським ID, але без рядків на всіх 26 складах | 8 | **Немає даних**, не нуль | Рецепта немає |
| Картки `v_products`, яких поточний Poster не повертає навіть через `menu.getProduct` | 13 | Немає поточного джерела | Немає поточного джерела |
| **Разом у `v_products`** | **372** | | |

Poster `menu.getProducts` повернув 359 продуктів: 343 страви (`type=2`) і 16 товарів (`type=3`). Поточні 26 магазинів мають по одному прив'язаному складу; 26/26 викликів складів пройшли. Серед підтверджених рядків трапляються справжні нулі та від'ємні значення — їх слід залишати як є. Вісім товарів без складських рядків не вважати нульовими. Тринадцять відсутніх у Poster карток не видаляти автоматично: спочатку з'ясувати походження та правила синхронізації `categories.products`.

## 3. Контракт джерел

- ID картки — `feedbackgb.v_products.id` із дзеркала `categories.products`; для живих даних його потрібно зіставити з Poster `product_id`. Зіставлення лише за назвою заборонено.
- `menu.getProduct(product_id)` дає `ingredient_id`, склад страви, `structure_brutto`, `structure_netto`, `structure_unit`, опис технології та `out`.
- Для `structure_type=2` вкладену карту читати через `menu.getPrepack(product_id=<id напівфабрикату>)`; зберегти захист від циклів і ліміти вкладеності. Значення `out` показувати без вигаданої одиниці: API її явно не повертає.
- `access.getSpots` дає зв'язок `spot_id → storage_id`. Не зіставляти магазини та склади за назвою. Якщо складів 0 або більше 1, показувати `потрібне уточнення`, не підсумовувати мовчки.
- `storage.getStorageLeftovers(storage_id, zero_leftovers=true)` дає по складу саме `storage_ingredient_left`. Поле `ingredient_left` — загальний залишок і не підходить для магазину.
- Авторизація: тільки `super_admin`. `POSTER_TOKEN` лише на сервері; не повертати, не логувати й не комітити. Відповіді — `private, no-store`.

## 4. Послідовність реалізації: наступний крок лише після перевірки попереднього

### P-00. Зафіксувати відтворюваний знімок покриття

Зробити read-only аудит із **одним часом запуску**: усі ID `v_products`, `menu.getProducts`, `menu.getPrepacks`, `access.getSpots`, по одному `getStorageLeftovers` на унікальний склад. З'єднати дані за ID та вивести 5 груп із §2, список 13 відсутніх і 8 товарів без складських рядків. Скрипт не повинен друкувати токен або URL з токеном.

**Перевірка:** сума груп дорівнює повній кількості карток; усі 26 складів мають результат або явну помилку; повторний запуск позначає нову дату. Якщо це не виконується — зупинитися й розібрати синхронізацію, не переходити до UI.

### P-01. Уніфікувати безпечний Poster-клієнт

У двох теперішніх модулях (`posterStock.ts`, `posterTechCard.ts`) повторюється HTTP-обгортка. Винести її в спільний серверний модуль: тайм-аут, розбір відповіді, безпечні коди помилок, `no-store`, без витоку токена в логах. Не міняти бізнес-значення полів.

**Перевірка:** існуючі тести залишків і техкарти проходять без зміни результату; тест на помилку Poster доводить, що тіло відповіді/помилка не містить токена.

### P-02. Формалізувати стани залишків для кожного типу картки

Сервер повинен розрізняти: `available` (включно з 0 і мінусом), `product_missing_in_poster`, `product_without_stock_id`, `storage_mapping_missing_or_ambiguous`, `stock_row_missing`, `poster_unavailable`. Замість загального `503` для 18 страв без складського ID віддавати типізований очікуваний стан без вигаданого залишку. Для 8 товарів без рядків — окреме пояснення, що Poster не повернув складський запис.

**Перевірка:** вибрати по одному реальному ID із кожної групи §2; API й вкладка показують відповідний стан. Число `0` відображається лише для фактичного `storage_ingredient_left=0`.

### P-03. Формалізувати стани техкарти

Страви зі складом відображати з брутто/нетто та вкладеними напівфабрикатами. Для товарів `type=3` без рецепта показувати `Техкарту не задано в Poster`, не аварію. Для 13 відсутніх карток — `Продукт відсутній у поточному Poster`. Якщо вкладений напівфабрикат не завантажився, основну карту залишати, але показувати неповноту. Не розраховувати фудкост у цій вкладці.

**Перевірка:** страви, товари, подарункові позиції без складського ID, вкладений напівфабрикат, цикл, порожня карта, помилка вкладеного API — окремі тест-кейси.

### P-04. Покращити UI без нового дизайн-патерну

Зберегти наявні Ant Design `Card`, `Tabs`, `Table`, `Alert`. В обох вкладках показувати джерело, час отримання, стан і кнопку оновлення. Помилки та відсутність джерела називати конкретно. Якщо оновлення не вдалося, старий знімок позначати як попередній, а не актуальний. Не робити 372 запити при відкритті сторінки категорії: дані завантажуються лише після входу у відповідну вкладку конкретного продукту.

**Перевірка:** на світлій і темній темі, широкому та мобільному екрані; усі категорії, пагінація, перехід між різними продуктами без показу старої карти під новою назвою.

### P-05. Навантаження й обмеження Poster

Зараз одна вкладка залишків виконує приблизно 28 запитів до Poster: 1 продукт + 1 список магазинів + 26 складів. Не множити цю схему на весь каталог для фонового аудиту: аудит P-00 читає склади **один раз** і зіставляє багато продуктів у пам'яті. Для звичайного відкриття картки виміряти p50/p95 часу відповіді, частку помилок, час до відображення, кількість запитів і реакцію на 429/тайм-аут при 1, 5 і 10 одночасних адміністраторах. Зберегти ліміт паралелізму; рішення про короткий кеш/дедуплікацію приймати лише після замірів, з явним часом знімка і без підміни «живих» даних старими.

**Перевірка:** Poster не перевантажений, усі часткові помилки видимі, токен не потрапляє до HAR браузера та серверних логів. Якщо p95 або 429 неприйнятні — зупинити реліз і окремо погодити кешування.

### P-06. З'ясувати долю 13 застарілих карток

Перевірити, чому `feedbackgb.v_products` продовжує показувати ID, яких немає в Poster: вік/джерело синхронізації `categories.products`, ознака видалення, використання цих ID в історичних документах. Обрати продуктове правило: залишити архівні картки з відповідною міткою або прибрати їх із активної навігації. **Не видаляти вручну й не міняти view без доказів та окремого рішення.**

**Перевірка:** кожен із 13 ID має задокументований статус; історичні посилання не зламані; новий знімок покриття пояснює всі розбіжності.

### P-07. Реліз і післярелізна перевірка

Після P-00…P-06: `typecheck`, усі unit/API-тести, production build, авторизований E2E у Preview зі справжнім read-only Poster для представників кожної групи, перевірка тем і мобільного виду. Коміт і push окремо після зеленої перевірки. У Production — smoke тих самих сценаріїв, перевірка `POSTER_TOKEN` без його розкриття, серверних помилок і фактичного часу відповіді.

**Готово, коли:** кожна видима картка має зрозумілий результат в обох вкладках — числові дані або правдиву причину їх відсутності; жоден відсутній запис не показано як 0; реалізований workflow не робить записів у Supabase/Poster; Preview і Production перевірені окремо.

## 5. Мінімальна матриця тестів

1. ID картки збігається з `product_id` Poster.
2. Картка відсутня в Poster — явний стан, без підміни за назвою.
3. Блюдо з `ingredient_id` і позитивним залишком.
4. Справжній нуль із `storage_ingredient_left`.
5. Від'ємний залишок без обрізання до нуля.
6. `ingredient_left` (загальний) не використовується замість складського.
7. Блюдо без `ingredient_id` — техкарта є, залишок готового продукту недоступний.
8. Товар зі складським ID, але без рядка на складі — `немає даних`, не `0`.
9. Немає прив'язаного складу.
10. Два склади у магазину — не підсумовувати автоматично.
11. Помилка одного складу не приховує відповіді інших.
12. Тайм-аут/429 Poster — безпечна помилка, без токена.
13. Неавторизований/звичайний admin отримує 403.
14. Некоректний `product_id` відхиляється до запиту Poster.
15. Страва з повною техкартою, брутто/нетто/одиниці без перерахунку.
16. Напівфабрикат розкривається за ID, не за назвою.
17. Вкладена карта недоступна — основна карта не зникає, є попередження.
18. Цикл і ліміт вкладеності зупиняють рекурсію.
19. Товар без рецепта — інформативний порожній стан, не помилка.
20. Порожній опис технології не заповнюється штучним текстом.
21. Вихід `out` показано без вигаданої одиниці.
22. Переходи між двома картками не показують старий продукт під новою назвою.
23. Вкладки не завантажують Poster до їх відкриття.
24. Оновлення дає новий `checkedAt`; збій позначає попередній знімок.
25. Усі 372 картки доступні через категорії/пагінацію або мають пояснений статус після рішення P-06.
26. Світла/темна тема, мобільний екран, клавіатурна навігація.
27. Навантаження 1/5/10 адмінів: зафіксувати p50/p95, 429, помилки і кількість Poster-викликів.
28. Ні браузер, ні логи, ні Git не містять `POSTER_TOKEN`.

## 6. Артефакти приймання

- Знімок покриття з датою, кількостями, ID непокритих груп і причинами; без секретів та без повних відповідей Poster.
- Вивід команд `typecheck`, повного тестового набору, production build.
- E2E-скріншоти/логи для кожної групи §2 у Preview і smoke у Production.
- Замір часу та кількості Poster-запитів при 1/5/10 одночасних адмінах.
- Рішення щодо 13 застарілих карток і будь-якого кешування — окремо зафіксоване до відповідної зміни.
