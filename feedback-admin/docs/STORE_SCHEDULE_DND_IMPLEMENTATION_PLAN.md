# План внедрения drag-and-drop графиков продавцов

**Контур:** `Мережа → Графіки роботи` (`/admin/network/schedules`).  
**Статус:** план реализации. Не является разрешением применять SQL в production.  
**Цель:** администратор перемещает карточку продавца между ячейками «дата × магазин», а система безопасно создаёт или меняет плановую смену, фиксирует замену и оставляет проверяемую историю.

## 1. Неподвижные правила

1. DnD — только жест интерфейса. Единственный источник истины — Supabase.
2. Drop никогда не меняет данные напрямую: он формирует запрос на подтверждение.
3. Плановая смена, фотозвит и фактическая явка — разные факты. Фотозвит не используется для зарплаты.
4. Магазин, отличный от основного, является заменой только при активном `seller_store_permissions`.
5. Нельзя обойти проверку через две вкладки: используется `row_version` и ограничения БД.
6. Заблокированный/архивный месяц не редактируется.
7. Нет «ночных смен» в пользовательском DnD. Смена переносится в пределах того же локального времени Kyiv и одной календарной даты.

## 2. Целевой пользовательский сценарий

1. Администратор берёт карточку продавца мышью, touch-долгим нажатием или клавиатурой.
2. Карточка становится полупрозрачной; допустимая ячейка получает контур, запрещённая не принимает drop.
3. При отпускании система вычисляет новую дату и магазин, но не сохраняет сразу.
4. Если это другой магазин, интерфейс маркирует действие «Заміна».
5. Открывается модальное подтверждение: откуда → куда, продавец, дата, время, признак замены. Для `published` обязательна причина от трёх символов.
6. После подтверждения UI отправляет PATCH с исходной `row_version`.
7. При `200` сетка перезагружается из API. При `409/422/423` карточка остаётся на исходном месте и показывается сообщение сервера.

## 3. Этап A — договор данных и миграции

### A-1. Базовый график

Проверить, что применены миграции `030`, `031`, `032`, `033` в указанном порядке. Readback:

```sql
select to_regclass('feedbackgb.store_work_shifts'),
       to_regclass('feedbackgb.v_store_schedule_calendar'),
       to_regclass('feedbackgb.v_store_schedule_store_month');
```

**Готово:** все три объекта существуют; у `store_work_shifts` есть exclusion constraint пересечений.

### A-2. Фиксация фотозвитов

Подготовить и применить `034_store_schedule_photo_report_control.sql` сначала на staging. Объекты:

- `store_work_shift_photo_reports` — неизменяемая связь отправленного фотозвита с плановой сменой либо статусом `no_scheduled_shift`;
- `capture_store_work_shift_photo_report()` — `AFTER INSERT` trigger на `feedback`;
- `v_store_schedule_shift_photo_report_control` — смены с числом соответствующих фотозвитов;
- `v_store_schedule_unmatched_photo_reports` — отчёты вне плановой смены.

**Проверка:** RLS включён, доступ `anon/authenticated/public` отозван, `service_role` имеет только SELECT на read-model. Исторические фотозвиты не backfill-ятся: старый график нельзя достоверно применить к прошлому событию.

### A-3. Индексы и зависимости

Проверить индексы: поиск отчётов по `shift_id`, по `seller_id + report_store_id + local_date`, отдельно не сопоставленные отчёты. Проверить зависимость: `feedback → store_work_shift_photo_reports → store_work_shifts`; удаления запрещены через `ON DELETE RESTRICT`.

## 4. Этап B — API и серверные проверки

### B-1. Существующий маршрут смен

Использовать только `PATCH /api/admin/network/schedules?id=<shift_id>`. Payload: `store_id`, `starts_at`, `ends_at`, `row_version`, и при необходимости `change_reason`. Не создавать отдельный «DnD write API».

### B-2. Проверки маршрута

До update API обязан проверить: admin-сессию, UUID, актуальность `row_version`, период, допустимость интервала, активность seller, активное разрешение замены и обязательную причину для published периода. База повторно проверяет период, продавца, смену и пересечения.

### B-3. Read API контроля

Добавить `GET /api/admin/network/schedule-photo-control?month=YYYY-MM`. Ответ: смены из `v_store_schedule_shift_photo_report_control` и несопоставленные отчёты указанного месяца. Ошибка отсутствия `034` — явный `503 schedule_photo_control_schema_missing`, без подмены пустым массивом.

### B-4. Аудит и события

Успешное перемещение пишет `admin.schedule.update` в `audit_log`; DB trigger добавляет `updated` в `store_work_shift_events`. Связь фотозвита создаётся trigger-ом автоматически и не изменяется UI/API.

## 5. Этап C — интерфейс DnD

1. Заменить HTML5 drag на `@dnd-kit/core`.
2. Сенсоры: mouse (порог 6px), touch (180ms, tolerance 6px), keyboard.
3. Карточка смены — draggable только для scheduled смены в незакрытом периоде.
4. Ячейка месяца — droppable. Та же ячейка не создаёт запрос.
5. Во время drag: активная карточка полупрозрачна, `over`-ячейка имеет primary outline и фон темы; тёмная тема использует Ant Design tokens.
6. `onDragEnd` только вызывает существующий confirmation modal. Никакого оптимистичного update до подтверждения.
7. Enter/Space открывает редактирование как доступный эквивалент; dnd-kit KeyboardSensor поддерживает перенос без мыши.
8. Для touch не мешать вертикальному scroll: задержка захвата и минимальное отклонение обязательны.

## 6. Этап D — вкладка «Контроль фотозвитів»

Добавить четвёртую вкладку в графике:

- «Є фотозвіт» — плановая смена с совпавшим отчётом;
- «Немає фотозвіту» — смена без совпадения;
- «Звіт поза зміною» — отчёт с `no_scheduled_shift`;
- фильтры: месяц, магазин, продавец, только замены;
- ссылка на галерею фотозвита в существующем `Фотозвіт`.

Не называть статусы «явка», «відпрацював» или «табель».

## 7. Автоматические тесты

1. Некорректный месяц → 400.
2. Не-admin → 403 для read/write графика.
3. Нет `034` → 503, не пустой ответ.
4. DnD в той же ячейке не вызывает PATCH.
5. DnD в draft формирует confirmation, но не update до подтверждения.
6. DnD в published требует причину.
7. Closed/archived период не draggable и API возвращает 423.
8. Перенос в основной магазин сохраняет `is_replacement=false`.
9. Перенос в разрешённый магазин сохраняет `is_replacement=true` и permission id.
10. Перенос без разрешения → 422.
11. Пересечение смен → DB/API отказ; UI остаётся на исходной ячейке.
12. Устаревшая `row_version` → 409; UI делает reload.
13. Отмена смены не может стать источником DnD.
14. Mouse sensor не стартует при движении менее 6px.
15. Touch sensor требует long press.
16. Keyboard Enter/Space открывает доступное редактирование.
17. Тёмная тема: hover/over цель видима, нет hardcoded white background.
18. Trigger создаёт `matched_scheduled_shift` для отчёта в интервале смены.
19. Trigger создаёт `no_scheduled_shift` вне интервала.
20. Два отчёта одной смены дают count=2 в control view.
21. Редактирование смены после отчёта не меняет её immutable report link.
22. RLS/grants `034`: нет прав у anon/authenticated.
23. Проверить индексный план `EXPLAIN` для seller/store/date.
24. `audit_log` и `store_work_shift_events` содержат перенос.
25. Галерея доступна только через существующий admin endpoint.

## 8. E2E сценарии

На staging с отдельными тестовыми продавцами и магазинами:

1. Создать draft месяца, смену основного магазина, перетащить на другую дату, подтвердить, обновить страницу — новая ячейка сохранена.
2. Выдать право замены, перетащить в разрешённый магазин, подтвердить — карточка/журнал показывают «Заміна».
3. Попытаться перенести в неразрешённый магазин — после подтверждения получить 422 и увидеть исходную карточку.
4. Открыть две вкладки; изменить смену в первой, перетащить устаревшую во второй — 409 и reload без потери факта.
5. Опубликовать месяц: перенос требует причину; закрыть месяц: перенос недоступен.
6. Войти продавцом, отправить 6–15 фото внутри запланированной смены; admin control показывает совпадение.
7. Отправить фотозвит вне плановой смены; control показывает «Звіт поза зміною».
8. Повторить DnD на touch-устройстве/эмуляции и клавиатурой.

## 9. Порядок выпуска

1. Unit/API/SQL-contract тесты локально.
2. Preview deployment и E2E без production-данных.
3. Применить `034` на staging, выполнить readback A-2/A-3.
4. Staging E2E, включая сохранение/откат и фотозвит.
5. Отдельно утвердить production migration.
6. Применить миграцию, readback, затем production deploy admin-панели.
7. После deploy проверить маршрут, создание/перенос тестовой смены, audit и view. Удалить/отменить тестовую смену только по согласованной процедуре.

## 10. Критерии приёмки

- Перенос не обходит права замен, пересечения, блокировку периода или concurrency.
- Каждое подтверждённое изменение восстанавливается из базы после reload.
- История смены и audit показывают автора и причину там, где она обязательна.
- Новый фотозвит имеет ровно одну immutable запись контроля.
- Отчёт вне смены виден отдельно и не подменяется отсутствием отчёта.
- Все 25 автоматических проверок и 8 E2E сценариев имеют приложенный результат.
