# План: HR-заявки в «Мережа → Графік відсутностей»

> **Рішення 22.09.2026:** затверджено варіант A — операційна Kanban-дошка. Це цільовий інтерфейс вкладки «Заявки».

**Статус:** код и миграция подготовлены локально; миграция `035` ещё не применена к staging/production.
**Контур:** `feedback-app` → `feedbackgb.feedback` → `feedback-admin /admin/network/absences` → `feedbackgb.employee_absences` → графики смен.
**Цель:** сделать «Графік відсутностей» рабочим местом HR по отпускам, больничным, отгулам и переводам. Общая лента dashboard остаётся источником всех обращений, но HR-обработка ведётся в этом разделе.

## 1. Подтверждённое исходное состояние

1. Приложение создаёт запросы в `feedbackgb.feedback` с `category = 'hr_question'` и `fields.hr_topic`.
2. Рабочие темы: `vacation`, `day-off`, `sick-leave`, `transfer`, `resignation`.
3. Вкладка отсутствий создаёт `employee_absences` вручную; связи с `feedback.id` нет.
4. Смена статуса HR-заявки в dashboard не создаёт отсутствие, перевод и увольнение.
5. Графики смен сейчас не проверяют активные отсутствия.

## 2. Границы первой версии

### Включено

- Канбан заявок в существующем разделе `/admin/network/absences`.
- Темы: отпуск, больничный, отгул, перевод.
- Колонки: `Отримано`, `На розгляді`, `Погоджено`, `Відхилено`.
- Связь согласованного отпуска/больничного/отгула с одной записью `employee_absences`.
- Отображение связанных запросов в календаре и списке отсутствий.
- Предупреждения в уже созданных сменах и запрет создавать/переносить новую смену в активное отсутствие.
- Аудит действий, уведомления продавцу, защита от повторного согласования.

### Не включено без отдельного решения

- Автоматическое увольнение продавца по карточке `resignation`.
- Расчёт зарплаты, табель или фактическая явка.
- Автоматический перевод продавца в новый магазин: перевод требует отдельного подтверждения и отдельного бизнес-процесса.
- Удаление исторических HR-заявок или отсутствий.

**Увольнение:** остаётся в общей ленте до отдельного решения. Его нельзя трактовать как отсутствие.

## 3. Каноническая модель процесса

| Колонка | `feedback.status` | Разрешённые действия |
|---|---|---|
| Отримано | `new` | назначить HR-ответственного, начать рассмотрение, отклонить |
| На розгляді | `in_progress` | запросить уточнение в комментарии, согласовать, отклонить |
| Погоджено | `resolved` | открыть связанное отсутствие; для transfer — открыть карточку перевода |
| Відхилено | `rejected` | показать обязательную причину; вернуть в рассмотрение только с аудитом |

Перетаскивание карточки — только UI-жест. Оно открывает подтверждение, не сохраняет состояние мгновенно.

### Типы

- `vacation` → активное отсутствие `vacation`.
- `day-off` → активное отсутствие `day_off`.
- `sick-leave` → активное отсутствие `sick_leave`; пока нет даты окончания, согласование невозможно без явного ввода даты HR-администратором.
- `transfer` → не создаёт `employee_absences`; после согласования хранится как HR-решение, а перенос основного магазина выполняется отдельным будущим процессом.

### Правило согласования

Для трёх типов отсутствия действие «Погодити» открывает форму проверки: продавец, магазин, период, тип, примечание. Подтверждение создаёт отсутствие и переводит запрос в `resolved` **в одной транзакции**. Если период отсутствия конфликтует с уже созданной сменой, отсутствие всё равно фиксируется, а график получает проблему для устранения; болезнь и согласованный отпуск не должны блокироваться из-за ошибочного старого графика.

## 4. Изменения схемы: только новая миграция `035_hr_absence_request_linking.sql`

Не редактировать **ни одну применённую миграцию**. Все изменения делаются только forward-only миграцией `035`.

1. Добавить `employee_absences.source_feedback_id uuid null unique references feedbackgb.feedback(id) on delete restrict`.
2. Создать индекс на `source_feedback_id` (уникальность одновременно покрывает lookup).
3. Создать закрытую view `feedbackgb.v_hr_absence_requests`:
   - только `feedback.category = 'hr_question'` и `fields.hr_topic in ('vacation', 'day-off', 'sick-leave', 'transfer')`; `resignation` намеренно исключён;
   - извлекает `hr_topic`, даты, комментарий, фото, статус, автора, домашний магазин, назначенного администратора;
   - присоединяет `employee_absences.id/status/period` через `source_feedback_id`;
   - присоединяет информацию о связанных сменах только агрегированно, без подмены отсутствия явкой.
4. Добавить SQL-функцию `feedbackgb.approve_hr_absence_request(...)` с `security definer` и безопасным `search_path = feedbackgb, categories, pg_catalog`:
   - первой операцией блокирует строку заявки `SELECT ... FOR UPDATE`; это сериализует действия из двух вкладок, в том числе `transfer`, для которого absence не создаётся;
   - проверяет, что запись — допустимый HR-топик, автор — активный продавец, текущий статус `new|in_progress`;
   - валидирует даты и отсутствие дубликата;
   - вставляет `employee_absences` с `source_feedback_id`; `store_id` берётся из заблокированной `feedback.store_id` (магазин на момент подачи заявки), а не из payload браузера и не из default-триггера домашнего магазина;
   - обновляет `feedback.status = 'resolved'`, `resolved_at`, `resolved_by`, `assigned_to`;
   - возвращает IDs заявки и отсутствия;
   - при любой ошибке откатывает обе части.
5. Добавить SQL-функцию `feedbackgb.review_hr_absence_request(...)`: блокирует строку `FOR UPDATE`, переводит только `new → in_progress`, назначает HR и сохраняет необязательный комментарий одной транзакцией.
6. Добавить SQL-функцию `feedbackgb.reject_hr_absence_request(...)`, которая блокирует строку заявки `FOR UPDATE`, требует причину 3–500 символов, пишет её в `feedbackgb.feedback_comments` от имени HR-администратора и переводит заявку в `rejected` в одной транзакции. Причина доступна продавцу через существующий `/api/my-feedback/<id>`.
7. Forward-only переопределить `validate_employee_absence()`: отсутствие может быть создано только для активного продавца. Это закрывает ручной путь, который не использует approve-функцию.
8. Расширить `v_store_schedule_issues` строкой `employee_active_absence` для уже существующих смен, пересекающихся с активным отсутствием. Сравнение выполняется **по employee_id, не по store_id**.
9. Расширить серверную валидацию новой/изменяемой смены: пересечение с активным отсутствием возвращает понятный `422 schedule_employee_absent`.
   - Обе стороны переводятся в локальные календарные даты timezone периода: `daterange((starts_at at time zone period.timezone)::date, ((ends_at - interval '1 microsecond') at time zone period.timezone)::date, '[]')` пересекается с `daterange(absence.starts_on, absence.ends_on, '[]')`.
   - Так смена через полночь проверяется на каждый локальный день, а не по UTC и не по магазину.
10. `employee_absences` сохраняет действующий RLS. На новой view и новых `security definer`-функциях отозвать права у `public`, `anon`, `authenticated`; выдать только необходимые права `service_role`. Каждая write-функция сама проверяет активного actor с ролью `admin|super_admin`.

## 5. Серверные маршруты

### Read

`GET /api/admin/network/absence-requests?month=YYYY-MM&topic=&storeId=&sellerId=`

Возвращает карточки только четырёх тем первой версии. Параметры строго валидируются. Отсутствие `035` возвращает явный `503 absence_request_schema_missing`, а не пустой список.

### Write

- `POST /api/admin/network/absence-requests/<feedbackId>/review` — `new → in_progress`, назначение администратора/комментарий.
- `POST /api/admin/network/absence-requests/<feedbackId>/approve` — вызывает атомарную SQL-функцию. Для больничного требует период в payload, если продавец не указал окончание.
- `POST /api/admin/network/absence-requests/<feedbackId>/reject` — требует причину; функция сохраняет её комментарием к заявке.
- `PATCH /api/admin/network/absences/<absenceId>` — отдельное редактирование/отмена уже созданного отсутствия с `row_version`, причиной отмены и аудитом. При отмене один UPDATE атомарно ставит `status = 'cancelled'`, `cancelled_by`, `cancelled_at`, `cancel_reason`, `updated_by`.

Каждый write-маршрут: проверка admin-сессии, UUID, допустимого перехода, версии данных, ограничения длины текста, журнал аудита с `request_id`, уведомление продавцу после успешного решения. Недоступность объектов 035 распознаётся как `42P01` / `42703` / `42883` и возвращает явный `503 absence_request_schema_missing`.

## 6. Интерфейс

В существующем `/admin/network/absences` остаются те же шрифты, `AdminPageContainer`, `Card`, `Tabs`, `Table`, `Tag`, светлая и тёмная темы.

### Вкладки

1. **Заявки** — Kanban по статусам. По умолчанию открывается эта вкладка.
2. **Календар відсутностей** — подтверждённые и ручные отсутствия по месяцам; отметка «З HR-заявки» и переход к карточке.
3. **Список** — таблица всех отсутствий, редактирование/отмена и ссылка на источник.

### Карточка Kanban

- ФИО, магазин на момент запроса, тип и период.
- Статус связанного отсутствия: `не створено`, `активне`, `скасовано`.
- Фото справки — только через существующий защищённый admin endpoint.
- Исполнитель, дата создания, последние комментарии.
- Действия зависят от колонки: взять в работу, согласовать, отклонить, открыть отсутствие.

### Фильтры

- тип (все / отпуск / больничный / отгул / перевод);
- магазин;
- продавец;
- месяц пересечения периода;
- «только без решения»;
- назначенный HR-ответственный.

## 7. Пошаговая реализация с воротами

1. **Контракт.** Утвердить scope и значения переходов. Проверка: нет автоматического увольнения/перевода в первой версии.
2. **SQL 035.** Написать миграцию и rollback до начала записи данных. Проверка: SQL lint, RLS/grants/readback.
3. **Staging readback.** Применить только на staging. Проверить новые колонку, view, функции, ограничения, EXPLAIN для фильтров.
4. **Server read.** Реализовать GET и тесты auth/filters/schema-missing.
5. **Server write.** Реализовать review/approve/reject/absence-edit. Проверка: атомарность и audit.
6. **Kanban.** Реализовать read-only карточки и фильтры. Проверка: темы/колонки/тёмная тема.
7. **Переходы.** Подключить модалки, DnD и перезагрузку из базы после успеха.
8. **Календарь/список.** Показать источник HR и отмену отсутствия.
9. **Связь со сменами.** Добавить предупреждения существующих пересечений и запрет новых назначений.
10. **Staging E2E.** Выполнить только на тестовых продавцах и магазинах.
11. **Preview.** Задеплоить admin отдельно, smoke-test.
12. **Production.** Только после отдельного подтверждения миграции и результата staging.

## 8. Автоматические проверки

1. Не-admin не читает Kanban: 403.
2. Некорректный `month`: 400.
3. Неизвестный topic: 400.
4. Нет `035`: явный 503.
5. Read filter по магазину возвращает только его карточки.
6. Read filter по продавцу возвращает только его карточки.
7. `new → in_progress` создаёт audit и уведомление.
8. `new → rejected` без причины: 400.
9. Причина отказа <3 символов: 400; допустимая причина появляется в `feedback_comments` и доступна автору заявки.
10. Vacation approve создаёт `employee_absences` и `resolved` атомарно.
11. Day-off approve создаёт `day_off`.
12. Sick leave без конечной даты требует её от HR.
13. Transfer approve не создаёт absence.
14. Повторное approve одной заявки и два параллельных approve в разных транзакциях не создают вторую absence; вторая операция получает контролируемую ошибку состояния.
15. Конфликт активных отсутствий: 422 и статус заявки не меняется.
16. Ошибка вставки absence откатывает статус заявки.
17. Отмена absence требует причину и сохраняет `cancelled_by/at`.
18. Отменённое отсутствие не блокирует новую смену.
19. Активное отсутствие блокирует создание новой смены для того же продавца, в том числе replacement в другом магазине: 422.
20. Существующая конфликтующая смена появляется в `v_store_schedule_issues`; смена через полночь и timezone периода проверяются по локальному daterange.
21. Locked график не меняется через HR-действие.
22. Ссылка absence ↔ feedback работает в обе стороны.
23. Отсутствие прямого `source_feedback_id` остаётся допустимым для ручного ввода.
24. `anon/authenticated/public` не имеют доступа к новым DB-объектам.
25. Темная тема не использует жёстко заданный белый фон.
26. `resignation` не попадает в Kanban и read API.
27. Ручной POST absence для неактивного продавца отклоняется БД.
28. При approve `store_id` равен `feedback.store_id` на момент подачи заявки, даже если домашний магазин продавца позже изменился.
29. PATCH cancellation одним запросом заполняет все обязательные cancel-поля и проходит DB CHECK.

## 9. E2E на staging

1. Продавец отправляет отпуск на 7+ дней вперёд; карточка появляется в «Отримано».
2. HR берёт её в работу, добавляет комментарий; продавец видит статус.
3. HR согласует отпуск; после reload есть одна absence и ссылка на исходную заявку.
4. Администратор пытается назначить продавца на дату отпуска; получает запрет.
5. HR создаёт больничный с неизвестной датой окончания; Kanban не позволяет согласовать без уточнения даты.
6. HR отклоняет отгул; причина видна продавцу и в audit.
7. HR согласует перевод; absence не создаётся.
8. HR отменяет уже согласованное отсутствие; оно исчезает из активного календаря и перестаёт блокировать новые смены.
9. Две вкладки пытаются согласовать одну карточку; только одна операция успешна.
10. Проверка desktop, mobile-width и тёмной темы.
11. Две вкладки одновременно согласуют `transfer`; только одна операция успешна, отсутствие не создаётся.
12. Смена, пересекающая полночь в timezone периода, блокируется при активном отсутствии на любом затронутом локальном дне.
13. Продавец сменил домашний магазин после подачи заявки: согласованное отсутствие хранит магазин из исходной заявки.

## 10. Критерии приёмки

- HR-заявка и созданное из неё отсутствие имеют однозначную проверяемую связь.
- Нет дублирования absence при повторных кликах/двух вкладках.
- Согласование не делает перевод или увольнение автоматически.
- Активное подтверждённое отсутствие не позволяет планировать новую смену поверх него.
- Все решения, отмены и уведомления имеют аудит.
- Dashboard не ломается: HR-заявки по-прежнему там видны.
