# План реализации графиков работы магазинов

**Статус:** план, без применения миграций и без изменения рабочих данных.  
**Контур:** `Мережа → Графіки роботи` (`/admin/network/schedules`).  
**Источник текущих графиков:** Google Sheets «Графік роботи».  
**Целевой источник истины после внедрения:** Supabase `feedbackgb`; Google Sheets остаётся архивом и источником одноразового импорта.

## 1. Цель

Перенести ведение графиков продавцов из помесячных Google Sheets в админ-панель. Администратор должен создавать, изменять, публиковать и контролировать смены магазинов, включая замены. Каждая операция должна быть проверяемой: кто, когда и почему изменил смену.

Данные должны быть пригодны для будущего модуля зарплаты, но **эта итерация не рассчитывает зарплату и не хранит ставки**.

## 2. Что подтверждено сейчас

1. В админке уже есть маршрут `/admin/network/schedules`, пока с честной заглушкой без данных.
2. В базе есть `feedbackgb.users` с `full_name`, `store_id`, `role`, `is_active`.
3. Магазины привязаны через `categories.spots(spot_id)`.
4. Есть `feedbackgb.seller_store_permissions`: разрешение работать на заменах. Это разрешение даёт право работать в другом магазине, но **не является фактом назначенной смены**.
5. Есть общий `feedbackgb.audit_log` и серверный `logAudit()`.
6. В текущем Google Sheets один лист содержит один месяц и один контур; строки — даты, колонки — магазины/локации, ячейки — ФИО. Видны цветовые пометки, но их бизнес-смысл не подписан.

## 3. Границы первой версии

В первой версии делаем только график магазинов и продавцов:

- планирование одной или нескольких смен на сотрудника;
- обычные смены, замены, выходные, отпуск и больничный как явные статусы;
- календарный просмотр «по магазинам» и просмотр «по сотруднику»;
- публикацию графика;
- журнал изменений;
- импорт согласованных исторических данных из Google Sheets;
- контроль пересекающихся смен и назначений без активного доступа к магазину.

Не делаем в этой версии:

- расчёт начислений, ставок, премий, удержаний и выплат;
- автоматическое признание смены отработанной по входу в приложение или фотоотчёту;
- двустороннюю синхронизацию с Google Sheets;
- графики кухни и цехов: они используют будущий общий механизм, но идут отдельной реализацией;
- мобильное редактирование графика продавцом.

## 4. Решения, которые нужно утвердить до миграции

Ниже — обязательный gate. Пока на все пункты нет ответа, migration не писать и не применять.

| Вопрос | Почему это критично | Рекомендуемое правило |
|---|---|---|
| Что означают красный и жёлтый цвета в текущем файле? | Цвет нельзя превратить в статус по догадке. | Составить легенду для каждого цвета и подтвердить на трёх датах. |
| Что означает пустая ячейка? | Пустота может быть выходным, отпуском либо незакрытой сменой. | В новой системе пустота не используется как статус. |
| Нужен ли один продавец на магазин в день или несколько? | От этого зависит проверка покрытия. | Модель поддерживает несколько назначений; норматив задаётся отдельно. |
| Какие стандартные интервалы смен? | Без времени нельзя корректно ловить пересечения и готовить данные для зарплаты. | Администратор указывает `starts_at`, `ends_at`, перерыв; шаблон лишь подставляет значения. |
| Когда сотрудник считается реально отработавшим смену? | План нельзя использовать как факт для зарплаты. | До будущего подтверждения все смены имеют только плановый статус. |
| Кто имеет право публиковать и закрывать месяц? | Публикация и закрытие влияют на будущую зарплату. | Обычный admin редактирует; super admin публикует и закрывает. Подтвердить. |
| Какой доступ к Google Sheets допустим для импорта? | Графики содержат данные о персонале; публичная ссылка не должна стать технической зависимостью без решения владельца. | Выделенная service account с read-only доступом к одному файлу. Публичный export использовать только для разового ручного переноса, если это отдельно одобрено. |
| Как долго хранить историю? | История нужна для споров и начислений. | Не удалять события; срок хранения согласовать отдельно. |

**Результат gate:** подписанная таблица правил и импорт-маппинг. Если хотя бы один пункт не утверждён, этапы БД и импорта имеют статус `blocked`.

## 5. Бизнес-логика

### 5.1. Период графика

График создаётся на календарный месяц в часовом поясе `Europe/Kyiv`.

Статусы периода:

| Статус | Значение | Разрешённые действия |
|---|---|---|
| `draft` | План составляется. | Создание, редактирование, удаление черновых смен. |
| `published` | План доступен для операционной работы. | Изменение только с причиной; все изменения журналируются. |
| `locked` | Период передан в будущий расчёт зарплаты. | Только просмотр. Открыть обратно может super admin с причиной. |
| `archived` | Исторический период. | Только просмотр и экспорт. |

### 5.2. Смена

Одна запись смены описывает одного сотрудника на одной локации и одном временном интервале. Это сознательно проще и надёжнее, чем одна «общая» смена с массивом сотрудников.

Обязательные поля:

- сотрудник;
- магазин;
- дата и время начала/окончания;
- перерыв в минутах;
- тип: обычная смена или замена;
- статус;
- автор создания и автор последнего изменения.

Дополнительные поля:

- причина замены;
- причина отмены или изменения опубликованной смены;
- ссылка на разрешение `seller_store_permissions`, если смена является заменой;
- плановые часы, вычисленные из интервала минус перерыв;
- фактические часы — пока `NULL`; добавляются только отдельным будущим модулем факта.

### 5.3. Замена

1. Если выбранный магазин совпадает с `users.store_id`, смена обычная.
2. Если магазин отличается, API ищет активную запись `seller_store_permissions`.
3. Нет активного разрешения — API возвращает `422 replacement_store_not_allowed`; UI не сохраняет форму.
4. Есть разрешение — `is_replacement = true`, `replacement_permission_id` сохраняется вместе со сменой.
5. Разрешение на замену не подтверждает, что сотрудник реально отработал смену. Оно только разрешает назначение.
6. Последующая отмена разрешения не переписывает уже созданные исторические смены.

### 5.4. Пересечения

Для одного сотрудника нельзя сохранить две активные смены с пересекающимся временем. Правило работает на уровне БД, поэтому его нельзя обойти прямым API-вызовом или двумя одновременными вкладками.

Пограничные случаи:

- `09:00–18:00` и `18:00–22:00` допустимы;
- `09:00–18:00` и `17:59–22:00` запрещены;
- отменённая смена не блокирует новую;
- ночная смена, пересекающая полночь, поддерживается, если `ends_at > starts_at`;
- смены хранятся в UTC, а календарная дата и проверки отображаются в `Europe/Kyiv`.

### 5.5. Публикация

Перед публикацией система проверяет:

1. Нет пересечений смен.
2. Нет назначений на неактивного сотрудника.
3. Все замены имеют активное разрешение на момент назначения.
4. Нет незавершённых импортов с ошибочными строками, если период был создан импортом.
5. Если утверждён норматив покрытия — нет незакрытых обязательных слотов.

Публикация не делает план фактическим временем работы. Она только фиксирует операционный план.

### 5.6. Связь с фотоотчётами

Фотоотчёт остаётся независимым событием. В будущем экран контроля может показать рядом:

- была ли у продавца плановая смена в этом магазине;
- был ли фотоотчёт в дату смены;
- был ли магазин выбран как замена.

Но фотоотчёт не создаёт смену, не меняет график и не является основанием для начисления денег.

## 6. Предлагаемая модель данных Supabase

Все новые объекты находятся только в схеме `feedbackgb`. Использовать `public` запрещено.

Номер файла миграции намеренно обозначен как `NNN`: его выбирают **только после** readback последней реально применённой миграции на staging. Например: `feedback-admin/supabase/NNN_store_work_schedules.sql`.

### 6.1. `feedbackgb.work_schedule_periods`

Одна строка на месяц графика магазинов.

| Поле | Тип | Правило |
|---|---|---|
| `id` | `uuid` | PK, `gen_random_uuid()` |
| `scope` | `text` | В MVP только `store`; CHECK подготовлен для `workshop` позднее |
| `period_start` | `date` | Первый день месяца |
| `period_end` | `date` | Последний день того же месяца |
| `timezone` | `text` | `Europe/Kyiv` в MVP |
| `status` | `text` | `draft`, `published`, `locked`, `archived` |
| `published_at`, `published_by` | `timestamptz`, `uuid` | nullable до публикации |
| `locked_at`, `locked_by`, `lock_reason` | | nullable до закрытия |
| `row_version` | `integer` | optimistic concurrency, начинается с `1` |
| `created_at`, `updated_at` | `timestamptz` | audit timestamps |

Ограничения:

- `period_start = date_trunc('month', period_start)::date`;
- `period_end = (period_start + interval '1 month - 1 day')::date`;
- один активный период на `(scope, period_start)`;
- `locked_at` заполнен только для `locked`/`archived`;
- `published_at` заполнен только для `published`/`locked`/`archived`.

### 6.2. `feedbackgb.store_work_shifts`

Одна строка — один сотрудник на одном магазине в одном интервале.

| Поле | Тип | Правило |
|---|---|---|
| `id` | `uuid` | PK |
| `period_id` | `uuid` | FK → `work_schedule_periods(id)` `on delete restrict` |
| `employee_id` | `uuid` | FK → `users(id)` `on delete restrict` |
| `store_id` | `integer` | FK → `categories.spots(spot_id)` `on delete restrict` |
| `starts_at`, `ends_at` | `timestamptz` | `starts_at < ends_at` |
| `break_minutes` | `smallint` | `0..480`, меньше длительности смены |
| `planned_minutes` | `integer generated always` или вычисление в view | разница интервала минус перерыв |
| `status` | `text` | `scheduled`, `cancelled` в MVP |
| `is_replacement` | `boolean` | вычисляется в server workflow, не вводится свободно |
| `replacement_permission_id` | `uuid` | FK → `seller_store_permissions(id)`, nullable только для обычной смены |
| `change_reason` | `text` | обязательна при изменении опубликованной смены/отмене |
| `row_version` | `integer` | optimistic concurrency |
| `created_by`, `updated_by`, `cancelled_by` | `uuid` | FK → `users(id)` |
| `created_at`, `updated_at`, `cancelled_at` | `timestamptz` | timestamps |

Ограничения:

1. Только активный сотрудник может быть создан API; БД-триггер повторяет проверку.
2. В store-контуре сотрудник должен иметь роль `seller`; кухонные и производственные роли не смешиваются с этим MVP.
3. Смена должна полностью лежать в календарных границах своего `period_id` в `Europe/Kyiv`.
4. `replacement_permission_id is null` при `is_replacement = false`.
5. `replacement_permission_id is not null` при `is_replacement = true`.
6. `change_reason` обязателен при отмене и при изменении опубликованного периода.
7. Физическое удаление опубликованной смены запрещено. Используется `status = 'cancelled'`.
8. Уникальное exclusion-ограничение `btree_gist` запрещает пересечение диапазонов одного `employee_id` для статуса `scheduled`:

```sql
exclude using gist (
  employee_id with =,
  tstzrange(starts_at, ends_at, '[)') with &&
)
where (status = 'scheduled');
```

Расширение устанавливается как `create extension if not exists btree_gist with schema extensions;`, а не в открытой API-схеме.

### 6.3. `feedbackgb.store_work_shift_events`

Append-only история доменных событий. Её нельзя заменять только общим `audit_log`, потому что на экране смены нужны полные before/after именно этой записи.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `uuid` | PK |
| `shift_id` | `uuid` | FK → `store_work_shifts(id)` `on delete restrict` |
| `event_type` | `text` | `created`, `updated`, `cancelled`, `published`, `period_locked`, `imported` |
| `actor_user_id` | `uuid` | Кто выполнил действие |
| `occurred_at` | `timestamptz` | Когда произошло |
| `before_state`, `after_state` | `jsonb` | Снимки изменённых полей без секретов |
| `reason` | `text` | Причина изменения/отмены |
| `request_id` | `uuid` | Связь с серверным запросом |

Запретить `UPDATE` и `DELETE` через триггер `raise exception`; вставка разрешена только через database function, вызываемую сервером.

### 6.4. `feedbackgb.work_schedule_import_runs`

Хранит факт импорта из Google Sheets и делает импорт повторяемым.

- `id`, `source_kind` (`google_sheets`), `source_document_id`, `source_sheet_name`;
- `period_id`, `status` (`started`, `validated`, `applied`, `failed`, `rolled_back`);
- `started_by`, `started_at`, `completed_at`;
- `source_revision`, `source_hash`, `rows_seen`, `rows_created`, `rows_skipped`, `rows_failed`;
- `failure_summary`, `request_id`.

### 6.5. `feedbackgb.work_schedule_import_rows`

Построчный результат импорта. Полезен, когда ФИО или магазин не удалось сопоставить.

- `run_id`, `source_row_key`, `raw_payload jsonb`;
- `resolved_employee_id`, `resolved_store_id`;
- `result` (`ready`, `created`, `skipped`, `failed`);
- `error_code`, `error_detail`;
- `created_shift_id`.

Ни одну строку с `failed` нельзя применять автоматически.

### 6.6. Индексы

Минимум:

```text
store_work_shifts(period_id, store_id, starts_at)
store_work_shifts(employee_id, starts_at)
store_work_shifts(store_id, starts_at) where status = 'scheduled'
store_work_shift_events(shift_id, occurred_at desc)
work_schedule_import_runs(period_id, started_at desc)
work_schedule_import_rows(run_id, result)
```

Индексы проверяются через `pg_indexes` после применения migration, а не только чтением SQL-файла.

## 7. Views Supabase

Views предназначены для чтения админским API. Запись через них не допускается.

### 7.1. `feedbackgb.v_store_schedule_calendar`

Строчный безопасный read-model календаря:

- `period_id`, `local_date`, `store_id`, `store_name`;
- `shift_id`, `starts_at`, `ends_at`, `break_minutes`, `planned_minutes`;
- `employee_id`, `employee_full_name`, `employee_role`, `employee_home_store_id`;
- `is_replacement`, `status`, `row_version`;
- `period_status`.

Дата получается через `starts_at at time zone period.timezone`, а не через UTC-день. Это не даст ночной смене попасть в неверный день в Киеве.

### 7.2. `feedbackgb.v_store_schedule_employee_month`

Read-model для карточки сотрудника:

- сотрудник, основной магазин, дата;
- все запланированные смены за месяц;
- число смен, плановые минуты;
- количество замен;
- отменённые смены отдельно.

Никаких ставок и денежных сумм в view нет.

### 7.3. `feedbackgb.v_store_schedule_issues`

Показывает только проверяемые проблемы:

- смена назначена неактивному сотруднику;
- замена не имеет действующей ссылки на permission;
- смена лежит вне периода;
- запись имеет невозможный статус/время.

Не включать «нехватку персонала», пока не согласован норматив покрытия магазина. Иначе view будет выдавать выдуманные проблемы.

### 7.4. `feedbackgb.v_store_schedule_payroll_source`

Заготовка для следующей фазы. Возвращает только подтверждённые будущим модулем факта смены и их минуты. В MVP она должна возвращать **ноль строк** или иметь явный `not_ready` флаг, потому что факт смены ещё не реализован.

Это защищает от ошибочного использования планового графика для зарплаты.

## 8. Безопасность, RLS и аудит

1. На всех новых таблицах включить RLS.
2. Отозвать все права у `public`, `anon`, `authenticated`.
3. Выдать минимальные права только `service_role`.
4. Клиент браузера не обращается к Supabase для графиков напрямую. Только серверные API admin-панели после `requireAdminSession()`.
5. Каждая mutation проходит server validation, DB function и запись двух журналов:
   - доменное событие в `store_work_shift_events`;
   - обзорное событие `admin.schedule.*` в существующий `audit_log` через `logAudit()`.
6. В `audit_log.meta` сохраняются идентификаторы периода/смены/магазина, но не сохраняются PIN, cookie, IP в бизнесовых JSON-снимках или персональные комментарии сверх необходимого.
7. Все запросы получают request ID. Ошибка API содержит код, но не раскрывает лишние данные о сотрудниках.
8. Для изменения используется optimistic concurrency: UI передаёт `row_version`; при устаревшей версии API возвращает `409 schedule_conflict` и текущую безопасную версию записи.

## 9. API-контракт

Все URL работают в Node runtime, используют `requireAdminSession()` до query, Zod-валидацию, ограничение body и понятные коды ошибок.

| Метод | URL | Назначение |
|---|---|---|
| `GET` | `/api/admin/network/schedules?month=YYYY-MM&storeId=&employeeId=` | Календарь и фильтры |
| `POST` | `/api/admin/network/schedules` | Создать одну смену |
| `PATCH` | `/api/admin/network/schedules/:id` | Изменить или отменить смену |
| `POST` | `/api/admin/network/schedule-periods/:id/publish` | Проверить и опубликовать период |
| `POST` | `/api/admin/network/schedule-periods/:id/lock` | Закрыть период, только super admin |
| `POST` | `/api/admin/network/schedules/import/validate` | Сухая проверка импорта Google Sheets |
| `POST` | `/api/admin/network/schedules/import/apply` | Применить ранее валидированный импорт |
| `GET` | `/api/admin/network/schedules/issues?month=YYYY-MM` | Проверяемые проблемы |
| `GET` | `/api/admin/network/users/:id/schedule?month=YYYY-MM` | Вид сотрудника |

`import/apply` принимает только ID предварительно валидированного run; не принимает произвольные ячейки из браузера.

```text
Магазин / дата      01   02   03   04   05 ...
Шкільна             Пет  Пет  —    Пет  Пет
Роша                Яна  Яна  Яна  —    Яна

Петро Порошенко · 09:00–21:00 · Шкільна
```

Правила UX:

1. Ячейка может содержать несколько карточек смен.
2. Нажатие открывает Drawer, а не переносит пользователя на другую страницу.
3. В Drawer показаны магазин, время, сотрудник, замена, история и причина последнего изменения.
4. Пустая ячейка имеет отдельную кнопку «Додати зміну», но не означает автоматически выходной.
5. В режиме «По працівниках» строки — люди, колонки — дни; это помогает видеть двойные назначения.
6. Цвет всегда сопровождается текстовым статусом и иконкой. Цвет не является единственным носителем смысла.
7. Перед публикацией показывается список блокирующих и неблокирующих предупреждений.

## 11. Пошаговая реализация

Нельзя переходить к следующему этапу, пока критерий текущего этапа не выполнен.

### Этап 0. Зафиксировать правила и источник

1. Снять образец минимум трёх дней из листа продавцов и трёх дней из листа кухни.
2. Описать для каждой цветовой метки: значение, влияет ли на оплату, допустима ли пустая ячейка.
3. Согласовать стандартные интервалы, перерывы, правило ночных смен и публикации.
4. Утвердить: после запуска Supabase — источник истины; Google Sheets — архив/одноразовый импорт.
5. Утвердить ролевую матрицу admin/super admin.

**Проверка:** бизнес-владелец подтверждает таблицу правил и импорт-маппинг письменно/в задаче.  
**Стоп:** неясная цветовая легенда или источник истины.

### Этап 1. Read-only обследование реальной базы

1. Выполнить на staging только readback: PostgreSQL version, последняя применённая migration, схема `feedbackgb`.
2. Подтвердить наличие и типы `users`, `categories.spots`, `seller_store_permissions`, `audit_log`, `set_updated_at()`.
3. Проверить, что `btree_gist` доступен и можно установить в `extensions`.
4. Выгрузить активных продавцов и магазины для сопоставления с Google Sheets.
5. Выявить дубли ФИО, неактивных пользователей, магазины без соответствия, пустые `store_id`.

**Проверка:** приложен readback SQL и результат без изменения данных.  
**Готово, когда:** на каждую колонку Sheets есть однозначный `spot_id`, на каждое импортируемое ФИО — `users.id` либо явная строка в списке ошибок.

### Этап 2. Подготовить migration и ревью

1. Выбрать фактический номер `NNN` после readback.
2. Написать одну forward-only migration с таблицами, FK, checks, indexes, RLS, grants, views и triggers.
3. Добавить явные `comment on table/column` для бизнес-смысла замены, планового времени и запрета использования для зарплаты.
4. Добавить в конец migration readback SQL для таблиц, views, constraints, indexes, RLS/grants и rollback-условий.
5. Описать rollback: допустим только пока новые таблицы пусты и приложение не использует migration. После появления рабочих данных — только forward fix migration.
6. Провести SQL-review отдельно: порядок создания объектов, schema-qualified names, `security definer` search path, отсутствие `public`.

**Проверка:** `supabase db lint` либо эквивалент staging SQL parser не выдаёт ошибок.  
**Готово, когда:** migration проходит независимый review и не меняет существующие таблицы `feedback`, `users`, `seller_store_permissions` без отдельного решения.

### Этап 3. Применить на staging и подтвердить БД

1. Применить migration только на staging.
2. Сразу выполнить readback из migration.
3. Проверить RLS у всех пяти таблиц, отсутствие grants для `anon`/`authenticated`.
4. Проверить, что все views в `feedbackgb`, а не `public`.
5. Проверить test insert/update через service-role transaction и негативные запросы через anon/authenticated.
6. Проверить exclusion constraint двумя пересекающимися INSERT в отдельных транзакциях.
7. Проверить, что отменённая смена перестаёт блокировать новый интервал.

**Проверка:** результаты SQL readback сохранены в отчёте staging.  
**Стоп:** любой прямой доступ браузерной роли, неработающий FK/check/exclusion или view не в `feedbackgb`.

### Этап 4. Серверный domain layer и API

1. Добавить типы и Zod-схемы входов/выходов.
2. Реализовать server actions/RPC для создания, изменения, отмены, публикации и закрытия.
3. Проверку замен вынести в один domain service, использующий `seller_store_permissions`.
4. Добавить request ID, `logAudit()` и запись `store_work_shift_events` в одной логической операции.
5. Добавить optimistic concurrency.
6. Добавить лимиты диапазона дат и пагинацию; запрещать выгрузку неограниченного числа месяцев.
7. Написать unit и route tests до UI.

**Проверка:** API tests проверяют и успешные, и отказные сценарии.  
**Готово, когда:** невозможно создать конфликтующую или неразрешённую замену через API, даже минуя UI.

### Этап 5. Экран календаря и Drawer

1. Заменить заглушку `/admin/network/schedules` на календарь текущего дизайна.
2. Добавить фильтры месяца, магазина, сотрудника, статуса и проблем.
3. Добавить режимы «По магазинах» и «По працівниках».
4. Реализовать Drawer создания/редактирования с предзаполнением основного магазина.
5. При выборе магазина-замены показать текст «Заміна» и основание доступа.
6. Показать last changed, автора и причину в истории.
7. Реализовать понятные empty/error/loading состояния без фиктивных KPI.

**Проверка:** desktop 1280px, collapsed sidebar, планшетная ширина и keyboard navigation.  
**Готово, когда:** admin создаёт обычную смену и замену, видит результат после reload, а 409 конфликт не затирает чужое изменение.

### Этап 6. Импорт Google Sheets

1. Не подключать автоматическую двустороннюю синхронизацию.
2. Реализовать read-only получение согласованного листа только по выделенной service account с доступом к одному документу; ключи только в server environment.
3. Если service account ещё не выделен, выполнять только ручной одноразовый импорт подготовленного файла после отдельного одобрения. Не строить production-интеграцию на публичном export URL.
4. Создать экран предварительной проверки: период, лист, число строк, сопоставленные и ошибочные строки.
5. Никогда не применять импорт с `failed > 0` без явного ручного решения по каждой ошибке.
6. `apply` создаёт shifts идемпотентно по `source_hash` и `work_schedule_import_rows`; повторный apply не дублирует смены.
7. После импорта выполнить сравнение количества назначений по дате/магазину с исходным листом.
8. До публикации импорта администратор подтверждает предварительный просмотр.

**Проверка:** тестовый импорт содержит дубликат ФИО, неизвестный магазин, неактивного сотрудника и допустимую замену.  
**Готово, когда:** ошибки видны до записи в график; успешный повтор импорта не создаёт ни одной лишней смены.

### Этап 7. Приёмка и production release

1. Провести UAT на staging с реальными, но не production-данными.
2. Проверить migration readback, routes, UI, аудит и импорт.
3. Принять период в статусе `draft`, не публиковать его автоматически.
4. Создать backup/export согласованного Google Sheet перед production import.
5. Применить migration в production только после явного подтверждения пользователя.
6. Выполнить production readback без тестовых вставок.
7. Развернуть admin-панель сначала в Preview, затем в Production только по явно указанному SHA.
8. Выполнить smoke test: просмотр календаря, фильтр, просмотр истории. Создание production-смены — только с отдельным разрешением бизнес-владельца.

**Готово, когда:** production migration, admin deployment и read-only smoke проверены отдельно; Google Sheets не перезаписывался.

## 13. Подготовка к зарплате

Следующая фаза возможна только после стабильной работы графика.

Для неё добавляются отдельно, не в этой migration:

1. Подтверждение фактической смены (`actual_start_at`, `actual_end_at`, причина расхождения).
2. Версионные ставки сотрудника с датой начала действия.
3. Payroll period и snapshot закрытых фактических смен.
4. Правила доплат: замена, ночные, выходные, переработка — только после утверждения политики.
5. Отдельный расчётный журнал и отчёт расхождений «план — факт — начисление».

Правило безопасности: после создания payroll snapshot изменения графика не могут переписать уже рассчитанную зарплату. Любая корректировка идёт отдельным начислением/исправлением с audit trail.

## 14. Критерии готовности

Функция готова, когда одновременно выполнены все пункты:

1. Источник истины и значения старых цветов утверждены.
2. Migration применена и подтверждена readback на staging.
3. У браузерных ролей нет прямого доступа к новым данным.
4. API не позволяет создать конфликт, неразрешённую замену или изменение закрытого периода.
5. Каждая mutation оставляет доменное событие и запись общего аудита.
6. Календарь и карточка сотрудника показывают реальные данные после reload.
7. Импорт не создаёт дубли и не скрывает нераспознанные строки.
8. Все T-01…T-38 имеют фактический статус `passed`, `failed` или `blocked` с доказательством. Статус «готово в коде» не принимается.
9. Production deployment и production read-only smoke проверены отдельно.

## 15. Откат

До первого рабочего импорта допустим полный rollback новой migration только после проверки, что новые таблицы пусты и приложение не развёрнуто с зависимостью от них.

После появления рабочих смен:

- не удалять таблицы и историю;
- не откатывать migration назад;
- исправлять только новой forward-only migration;
- при критической ошибке выключить route/UI feature flag или ограничить доступ, сохранив данные и аудит для расследования.
