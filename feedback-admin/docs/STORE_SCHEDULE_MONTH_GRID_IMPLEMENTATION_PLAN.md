# Графіки роботи магазинів: місячна сітка, статистика та заміни

## 1. Мета

Зробити у маршруті `/admin/network/schedules` три робочі вкладки для HR та адміністраторів:

1. **Сітка місяця** — магазини по горизонталі, дати по вертикалі, у клітинці картки продавців зі змінами.
2. **Статистика** — планові години, зміни, скасування та заміни за вибраний місяць.
3. **Заміни** — окремий журнал усіх змін не в основному магазині продавця.

Картка продавця у сітці має переноситися мишкою у клітинку іншої дати й/або іншого магазину. Перенесення змінює **існуючу** зміну; воно не створює дубль.

## 2. Межі та інваріанти

- Джерело істини — `feedbackgb.store_work_shifts`; інтерфейс не має зберігати графік локально.
- Час і дата трактуються у `Europe/Kyiv`.
- Усі магазини виводяться навіть коли за вибраний місяць у них немає змін.
- Картка показує: ПІБ, локальний час, позначку «Заміна», коли `is_replacement=true`.
- Після перенесення сервер повторно визначає, чи є це заміною; клієнт цього статусу не визначає сам.
- Заборонено: зміна у закритому/архівному періоді, вихід за межі місяця, перетин часу одного продавця, призначення неактивного або не-продавця, заміна без активного дозволу `seller_store_permissions`.
- У published-періоді будь-яке перенесення потребує причини. У draft — причина необов'язкова. У locked/archived drag-and-drop вимкнений.
- Планові зміни не є фактом присутності і не є даними для зарплати.

## 3. Макет та поведінка

### 3.1. Вкладка «Сітка місяця»

- Верхня фіксована панель: місяць, фільтр магазинів, фільтр продавців, статус періоду, дії періоду.
- Перший стовпець — дата. Далі — окремий стовпець для кожного магазину. Верхній рядок магазинів залишається видимим при вертикальному прокручуванні, дата — при горизонтальному.
- Рядок = локальна дата. Клітинка = дата + магазин. Картки в клітинці розміщуються одна під одною.
- Це щільна spreadsheet-сітка, не набір великих карток: висота рядка дати — мінімальна, ширина колонки магазину автоматично ділить доступний desktop-екран між усіма магазинами. У клітинці в один рядок показується ФІО; повне ФІО, час і статус доступні через tooltip. Якщо в клітинці кілька продавців, показується перший і `+N`; hover показує інших. Скасована зміна не перетягується і показується лише за ввімкненого фільтра історії (у першій версії прихована).
- Drag start не змінює дані. Drop відкриває підтвердження з «було → стане». Тільки після підтвердження викликається PATCH.
- При переміщенні на іншу дату зберігаються локальні час початку, час завершення та перерва. При переміщенні на інший магазин зберігається час, а сервер валідує дозвіл на заміну.
- Якщо зміна перетинає опівніч, її перетягування між датами не входить у першу версію: картка має відкрити звичайне редагування. Це виключає неочевидну зміну тривалості на DST.
- На touch-пристроях та клавіатурі є доступна альтернатива: кнопка «Перемістити» у картці відкриває форму з датою і магазином. Drag не є єдиним способом.

### 3.2. Вкладка «Статистика»

- Чотири факт-карти: заплановані зміни, планові години, скасовані зміни, кількість замін.
- Таблиця магазинів: магазин, заплановані зміни, продавці у графіку, планові години, заміни, скасування.
- Таблиця продавців: продавець, основний магазин, зміни, години, заміни, скасування.
- Значення формуються тільки з обраного періоду; жодних довільних «оцінок ефективності» або фактичної присутності.

### 3.3. Вкладка «Заміни»

- Один рядок = зміна з `is_replacement=true`.
- Колонки: дата/час, продавець, основний магазин, магазин заміни, причина, статус, історія.
- Фільтри успадковують місяць і магазин; додатково — продавець та статус.
- Натискання «Історія» відкриває append-only події `store_work_shift_events`.

## 4. Дані та API

### Крок D-01. Розширити місячні підсумки магазину

Створити forward-only міграцію `032_store_schedule_month_grid.sql` з view `feedbackgb.v_store_schedule_store_month`.

Колонки: `period_id`, `period_start`, `period_end`, `period_status`, `store_id`, `store_name`, `scheduled_shift_count`, `cancelled_shift_count`, `replacement_shift_count`, `scheduled_employee_count`, `planned_minutes`.

Джерело — `feedbackgb.v_store_schedule_calendar`; агрегати повинні мати `filter (where shift_status = ...)`. View доступне тільки `service_role`; `anon`, `authenticated` і `public` не отримують прав. Міграція не змінює існуючі зміни.

**Перевірка:** view повертає один рядок на магазин, що має зміни у періоді; сума `planned_minutes` дорівнює сумі неперервних scheduled-змін календарної view.

### Крок D-02. Додати read-only endpoint статистики

`GET /api/admin/network/schedule-stores?month=YYYY-MM`:

- лише авторизований адміністратор;
- strict-перевірка `month`;
- читає `v_store_schedule_store_month`;
- не створює і не змінює дані;
- повертає лише дані обраного місяця.

**Перевірка:** неавторизований запит — `403`, хибний місяць — `400`, валідний — масив даних view.

### Крок D-03. Використати наявний endpoint перенесення

Перенесення застосовує наявний `PATCH /api/admin/network/schedules?id=<shift_uuid>` з:

- `row_version` поточної картки;
- новими `starts_at` і `ends_at`, сформованими з цільової київської дати й збережених локальних годин;
- новим `store_id`;
- `change_reason`, якщо період published.

Використовується наявна optimistic-lock перевірка та DB trigger. Новий окремий «drag API» не створюється, щоб не обходити правила редагування.

**Перевірка:** при конфлікті версії сервер повертає `409`, при перетині — `422`, при недозволеній заміні — `422`; UI перезавантажує сітку і не лишає картку у неправильній клітинці.

## 5. Послідовність реалізації

### Етап 1. Контракт і тестові дані

1. Зафіксувати цей макет і правила drag-and-drop.
2. Додати unit-тести перетворення дати/часу в `Europe/Kyiv`, у тому числі DST та нічну зміну.
3. Додати endpoint-тести існуючого PATCH: valid move, version conflict, replacement allowed/denied, published without reason, locked period.
4. Не застосовувати міграцію у Production до локального тесту SQL та окремого підтвердження.

**Gate:** усі нові тести мають бути green до зміни UI.

### Етап 2. Дані статистики

5. Написати `032_store_schedule_month_grid.sql` і rollback-блок у коментарі.
6. Перевірити SQL на чистій staging-базі/SQL lint.
7. Додати API `schedule-stores` і тести.
8. Вручну застосувати міграцію тільки після надання SQL користувачу.
9. Зробити readback: view, права, агрегати, відсутність змін у `store_work_shifts`.

**Gate:** API повертає тільки схвалені дані й не має write side-effect.

### Етап 3. Сітка місяця

10. Замінити наявну первинну таблицю «Зміни» на вкладки Ant Design, без зміни глобальних шрифтів, кольорів або shell.
11. Побудувати матрицю `local_date × store_id` з усіх магазинів server page й даних `v_store_schedule_calendar`.
12. Додати картки, tooltip з повною інформацією, порожню доступну клітинку та індикатор завантаження.
13. Реалізувати native HTML Drag and Drop без нової бібліотеки; додати альтернативну дію «Перемістити».
14. Показати confirmation modal перед PATCH; на published — поле причини 3–500 символів.
15. Після успіху reload з сервера; при помилці — повідомлення й жодного optimistic-переносу.

**Gate:** drag не може записати дані без підтвердження; клавіатурний шлях функціонально рівний drag.

### Етап 4. Статистика та заміни

16. Додати вкладку «Статистика» із чотирма агрегатами й двома робочими таблицями.
17. Додати вкладку «Заміни» з реальними картками замін, не окремою копією даних.
18. Повторно використати історію зміни; не дублювати event API.
19. Перевірити порожній період, 0 замін, скасовану зміну та кілька змін одного продавця за день.

**Gate:** суми статистики збігаються з реєстром зміни після перезавантаження сторінки.

### Етап 5. Повний контроль якості

20. Запустити unit/API tests, `typecheck`, `next build`.
21. Провести E2E в окремому тестовому періоді або зі спеціальними тестовими обліковками: створити, drag+confirm, drag+cancel, заміна, denied заміна, conflict, publish, lock.
22. Перевірити браузерну консоль: 0 errors і 0 нових warnings.
23. Перевірити mobile: таблиця не ламає shell, альтернативне «Перемістити» доступне.
24. В окремому readback перевірити audit-події та `store_work_shift_events` для одного підтвердженого перенесення.
25. Commit тільки після усіх green-gates; `.playwright-cli/` не додається.

## 6. Мінімум тестів (20)

1. Некоректний `month` у schedule-stores дає 400.
2. Неавторизований schedule-stores дає 403.
3. Schedule-stores читає лише один місяць.
4. Заплановані години магазину виключають cancelled shifts.
5. Лічильник замін магазину рахує тільки `is_replacement=true` і `scheduled`.
6. Сітка має стовпець для магазину без змін.
7. Сітка має рядок для кожного дня обраного місяця.
8. Картка показує ім'я, час та позначку заміни.
9. Вибір іншого місяця перезавантажує сітку без змішування даних.
10. Drag у ту саму клітинку нічого не записує.
11. Drop без підтвердження нічого не записує.
12. Draft: valid drop на іншу дату зберігає локальні час і перерву.
13. Draft: valid drop на магазин заміни отримує `is_replacement=true` лише від сервера.
14. Недозволений магазин заміни повертає 422 і картка повертається на місце.
15. Перетин часу повертає 422 і дані не змінюються.
16. Застарілий `row_version` повертає 409 і UI reload-иться.
17. Published: перенесення без причини заблоковано у UI й API.
18. Locked: drag, редагування й переміщення недоступні.
19. Нічна зміна відкриває форму замість drag.
20. Кнопка «Перемістити» дає той самий результат, що й drag.
21. Статистика дорівнює сумі рядків сітки після переміщення.
22. У «Замінах» відображається подія перенесення та її історія.

## 7. Відкат

- До застосування 032: відкотити лише незакомічений код.
- Після застосування 032: не видаляти таблиці чи зміни; при необхідності відкотити UI до таблиці, а view залишити безпечним і read-only.
- Якщо міграцію треба скасувати до появи залежностей: `drop view if exists feedbackgb.v_store_schedule_store_month;` після окремого підтвердження і перевірки залежностей.
